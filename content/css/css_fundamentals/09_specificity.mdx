## 왜 명시도가 필요한가

08편에서 캐스케이드(cascade, 계단식 적용)가 여러 스타일시트의 충돌을 해결하는 첫 단계로 **출처**(origin)와 **`!important`** 여부를 본다는 것을 배웠습니다. 그런데 출처도 같고(둘 다 저자 스타일시트) `!important`도 안 붙은 두 규칙이 같은 요소의 같은 속성을 두고 싸우는 경우가 훨씬 흔합니다.

```css
.card a { color: blue; }
nav .card a { color: red; }
```

두 규칙 모두 같은 `<a>` 요소에 `color`를 지정합니다. 브라우저는 여기서 다음 판단 기준으로 넘어갑니다. 바로 **명시도**(specificity, 구체성)입니다. 이름 그대로, "이 선택자가 얼마나 구체적으로 대상을 콕 집었는가"를 숫자로 매긴 것입니다.

> **쉽게 말하면:** 명시도는 선택자의 "정확도 점수"입니다. 이름을 콕 집어 부르는 선택자(ID)가 대충 부르는 선택자(태그 이름)보다 항상 더 정확하다고 브라우저가 취급합니다.

## 명시도를 세 자리 숫자로 계산하기

### (a, b, c) — 세 자리 가중치

명시도는 하나의 정수가 아니라 (**a, b, c**)라는 세 자리 튜플(tuple, 순서 있는 묶음)로 계산됩니다. 각 자리는 서로 다른 종류의 선택자 개수를 셉니다.

| 자리 | 무엇을 세는가 | 포함되는 선택자 예 |
|------|---------------|---------------------|
| a | ID 선택자 개수 | `#header`, `#main-nav` |
| b | 클래스류 선택자 개수 | 클래스(`.card`), 속성 선택자(`[type="email"]`), 의사 클래스(`:hover`, `:nth-child()`) |
| c | 타입류 선택자 개수 | 타입 선택자(`div`, `a`, `li`), 의사 요소(`::before`) |

결합자(` `, `>`, `+`, `~`)와 전체 선택자 `*`는 아무 자리에도 점수를 주지 않습니다. "관계를 표현할 뿐 무언가를 콕 집지 않기 때문"입니다.

<Callout type="warning">
  **비교 방식이 중요합니다.** (a, b, c)는 10진수로 합쳐서 비교하지 않습니다. **a 자리부터 순서대로** 비교합니다. a가 크면 b, c가 아무리 작아도 무조건 이깁니다. b가 같아야 비로소 c를 봅니다. ID 선택자 하나가 클래스 선택자 100개보다 항상 강한 이유가 여기 있습니다.
</Callout>

### 계산 연습 1 — 자리마다 하나씩

```css
.card a { color: blue; }          /* 클래스 1개, 타입 1개 */
nav .card a { color: red; }       /* 클래스 1개, 타입 2개 */
```

| 선택자 | a (ID) | b (클래스류) | c (타입류) | 튜플 |
|--------|--------|--------------|------------|------|
| `.card a` | 0 | 1 (`.card`) | 1 (`a`) | (0, 1, 1) |
| `nav .card a` | 0 | 1 (`.card`) | 2 (`nav`, `a`) | (0, 1, 2) |

**대조 순서:** a 자리부터 봅니다. `0 = 0`이라 무승부, 다음 b 자리 `1 = 1`이라 또 무승부, 마지막 c 자리에서 `2 > 1`이므로 `nav .card a`가 이깁니다. "선택자가 더 길다"가 아니라 "타입류 개수가 더 많다"는 것이 이긴 진짜 이유입니다.

### 계산 연습 2 — ID 한 개가 클래스 여러 개를 이긴다

```css
nav .menu > a.link { color: green; }   /* 클래스 2개, 타입 1개 */
#main-nav a { color: purple; }          /* ID 1개, 타입 1개 */
```

| 선택자 | a | b | c | 튜플 |
|--------|---|---|---|------|
| `nav .menu > a.link` | 0 | 2 (`.menu`, `.link`) | 2 (`nav`, `a`) | (0, 2, 2) |
| `#main-nav a` | 1 (`#main-nav`) | 0 | 1 (`a`) | (1, 0, 1) |

**대조 순서:** a 자리에서 곧바로 `1 > 0`이 확정됩니다. b, c 자리는 비교할 필요조차 없습니다. 클래스 2개짜리 선택자가 "더 구체적으로 보여도" ID 선택자 앞에서는 지는 이유입니다. 실무에서 "분명 더 자세하게 썼는데 왜 안 먹히지" 하는 착각이 대부분 여기서 나옵니다.

### 계산 연습 3 — 속성 선택자와 의사 클래스도 b 자리

```css
input[type="email"]:focus { border-color: blue; }
form input { border-color: gray; }
```

| 선택자 | a | b | c | 튜플 |
|--------|---|---|---|------|
| `input[type="email"]:focus` | 0 | 2 (`[type="email"]`, `:focus`) | 1 (`input`) | (0, 2, 1) |
| `form input` | 0 | 0 | 2 (`form`, `input`) | (0, 0, 2) |

**대조 순서:** a는 `0 = 0`. b에서 `2 > 0`이므로 첫 번째 선택자가 즉시 이깁니다. 속성 선택자(`[attr=value]`)와 의사 클래스(`:focus`, `:hover`)는 클래스와 **같은 자리**(b)에서 점수를 받는다는 사실이 핵심입니다. 04편의 속성 선택자와 06편의 의사 클래스가 여기서 다시 만납니다.

## 인라인 스타일 — 튜플 밖의 특별 규칙

HTML 요소의 `style` 속성에 직접 적은 선언은 어떤 선택자보다도 강합니다.

```html
<p style="color: orange;">이 문단</p>
```

```css
#content p { color: navy; }
```

인라인 스타일은 애초에 선택자를 쓰지 않으므로 (a, b, c) 계산에 낄 자리가 없습니다. 대신 "ID보다도 앞선 특별 등급"으로 취급되어, `#content p`가 ID를 포함해도 인라인 스타일 `color: orange`를 이기지 못합니다. 단, `!important`가 붙은 저자 스타일시트 규칙은 인라인 스타일까지 뒤집을 수 있다는 것을 08편에서 이미 배웠습니다. 인라인 스타일이 "선택자 세계의 끝판왕"이 아니라 "선택자 세계 밖의 규칙"이라는 표현이 더 정확합니다.

## 명시도가 같으면 — 소스 순서가 결정한다

두 규칙의 (a, b, c)가 완전히 같으면, 명시도는 승부를 못 냅니다. 이때는 **소스 순서**(source order)로 넘어갑니다. **스타일시트에서 나중에 나온 규칙이 이깁니다.**

```css
.header .btn { background: gray; }   /* (0, 2, 0) — 1번째 */
.btn.large   { background: teal; }   /* (0, 2, 0) — 2번째, 나중에 등장 */
```

두 선택자 모두 클래스 2개, 타입 0개로 (0, 2, 0) 동률입니다. 이럴 때는 계산이 필요 없습니다. 파일 안에서 더 아래에 적힌 `.btn.large`가 이깁니다. `<link>` 태그가 여러 개라면 나중에 로드된 스타일시트가 "더 아래"로 취급됩니다.

<Callout type="warning">
  **자주 틀리는 점:** "규칙이 더 구체적으로 보이니까 이기겠지"라는 감으로 판단하다가 틀립니다. 감이 아니라 (a, b, c)를 실제로 세어야 합니다. 동률이면 그다음엔 "누가 더 아래(나중)에 있는가"만 봅니다. 08편에서 배운 `!important`는 이 모든 비교를 건너뛰고 최우선으로 적용되므로, 명시도 싸움에서 자꾸 지는 규칙에 `!important`를 붙이는 임시방편이 반복되면 그건 명시도 관리가 애초에 무너졌다는 신호입니다.
</Callout>

## 실전 충돌 디버깅 — DevTools에서 읽는 법

버튼 색이 CSS를 고쳤는데도 안 바뀔 때, DevTools의 Styles 패널을 열면 적용되지 않은 선언에 **취소선**이 그어져 있습니다. 이건 "브라우저가 이 선언을 계산했지만 다른 규칙에 졌다"는 뜻입니다. 확인 순서는 이렇습니다.

<Steps>

1. **취소선 그어진 규칙과 실제 적용된 규칙을 함께 찾는다.** Styles 패널은 보통 명시도가 높은 규칙을 위쪽에, 진 규칙을 아래쪽에 취소선과 함께 보여줍니다.
2. **두 선택자의 (a, b, c)를 직접 손으로 센다.** ID 개수, 클래스·속성·의사 클래스 개수, 타입·의사 요소 개수를 각각 적는다.
3. **a 자리부터 비교한다.** 다르면 거기서 승부가 난 것이다. 같으면 b, 그다음 c로 내려간다.
4. **완전히 같다면 소스 순서를 확인한다.** 스타일시트 안에서 더 아래(나중)에 있는 규칙, 또는 나중에 로드된 `<link>` 스타일시트가 이긴다.
5. **그래도 설명이 안 되면 `!important`나 출처(브라우저 확장 프로그램이 주입한 스타일 등)를 의심한다.** 08편의 캐스케이드 우선순위 전체를 다시 짚는다.

</Steps>

이 다섯 단계를 항상 같은 순서로 밟는 습관이 "왜 안 먹히지"를 감이 아니라 근거로 진단하는 능력입니다. DevTools를 이용한 실전 디버깅은 30편에서 명시도 외의 상황(마진 상쇄, 레이아웃)까지 포함해 더 깊이 다룹니다.

## 핵심 정리

- 명시도는 (a, b, c) 세 자리 튜플이다. a는 ID 개수, b는 클래스·속성·의사 클래스 개수, c는 타입·의사 요소 개수다.
- 비교는 자릿수 합산이 아니라 **a부터 순서대로** 한다. ID 하나가 클래스 수십 개보다 항상 이긴다.
- 인라인 스타일은 튜플 계산에 들어가지 않는 별도 등급으로, 어떤 선택자 기반 규칙보다도 강하다(단 `!important` 규칙은 예외).
- (a, b, c)가 완전히 같으면 소스 순서, 즉 스타일시트에서 나중에 나온 규칙이 이긴다.
- 명시도 대결은 속성 단위로 일어난다. 한 규칙이 특정 속성에서 졌어도 겹치지 않는 다른 속성은 그대로 적용된다.
