## 왜 이름부터 뜯어보는가

웹 개발을 처음 시작하면 `<div>`나 `<p>` 같은 기호를 손으로 흉내 내면서 배우게 됩니다. 그런데 그 기호들을 왜 "태그"라고 부르는지, 왜 꺾쇠(`<`, `>`)로 감싸는지, 심지어 왜 이 언어의 이름이 **HTML**인지는 설명하지 않고 넘어가는 경우가 많습니다.

이름을 제대로 이해하고 시작하면 이후에 나오는 개념들이 훨씬 자연스럽게 이어집니다. HTML이라는 이름 자체가 이 언어의 정체성을 정확히 담고 있기 때문입니다. 이번 편은 이 과목의 첫 편으로, 앞으로 24편 동안 계속 쓰게 될 세 가지를 미리 정리합니다. HTML이 무엇인지, CSS·JS와 어떻게 일을 나누는지, 그리고 "표준"이라는 말이 실제로 무엇을 가리키는지입니다.

## 1. HTML이라는 이름 풀어보기

> **쉽게 말하면:** HTML은 "문서 안의 어떤 부분이 어떤 의미를 갖는지 표시하기 위한 언어"입니다.

**HTML**은 **HyperText Markup Language**(하이퍼텍스트 마크업 언어)의 줄임말입니다. 세 단어를 하나씩 쪼개 보겠습니다.

### HyperText — 하이퍼텍스트

**하이퍼**(hyper)는 "넘어선다"는 뜻의 접두사이고, **텍스트**(text)는 글입니다. 즉 **하이퍼텍스트**(hypertext)는 "보통의 글을 넘어선 글"이라는 뜻으로, 한 문서 안에 다른 문서로 건너뛸 수 있는 연결 고리가 박혀 있는 글을 말합니다. 종이책은 페이지를 순서대로만 넘길 수 있지만, 하이퍼텍스트는 문장 중간의 어떤 단어를 누르면 전혀 다른 문서로 순간이동합니다. 이 "건너뛰는 연결 고리"가 바로 뒤에서 배울 링크(`<a>` 요소)입니다.

### Markup — 마크업

**마크업**(markup)은 원래 인쇄·출판 업계에서 쓰던 말입니다. 편집자가 원고 위에 "이 부분은 제목", "이 부분은 인용문"이라고 손으로 표시(mark up, 표시를 얹다)해 두면, 조판공이 그 표시를 보고 실제로 글자를 굵게 하거나 크게 만들었습니다. HTML의 마크업도 똑같은 역할을 합니다. 글 자체를 쓰는 게 아니라, **이미 있는 글의 각 부분이 무슨 의미인지 표시**하는 것입니다.

```html
<h1>제목입니다</h1>
<p>이것은 문단입니다.</p>
```

위 코드에서 "제목입니다", "이것은 문단입니다"는 콘텐츠(content, 실제 내용)이고, `<h1>`과 `<p>`는 그 내용에 붙인 표시(마크업)입니다. `<h1>`은 "이건 이 페이지에서 가장 중요한 제목"이라는 의미를 부여하고, `<p>`는 "이건 하나의 문단"이라는 의미를 부여합니다.

### Language — 언어

**언어**(language)라는 단어 때문에 HTML을 자바스크립트 같은 프로그래밍 언어로 착각하기 쉽지만, HTML에는 조건문도 반복문도 없습니다. HTML이 "언어"인 이유는 **정해진 문법 규칙에 따라 의미를 표현하는 체계**이기 때문입니다. 마크업 언어(markup language)는 프로그래밍 언어와는 다른 갈래로, "무엇을 계산할지"가 아니라 "무엇이 무엇인지"를 표현합니다.

<Callout type="warning">
  **자주 틀리는 점:** "HTML은 프로그래밍 언어가 아니라서 진짜 언어가 아니다"라는 말을 종종 듣습니다. 정확히는 **마크업 언어**(markup language)라는 별도의 분류이지, 언어가 아니라는 뜻이 아닙니다. HTML은 문서의 구조와 의미를 표현하는 언어이고, 계산과 로직을 표현하는 것은 자바스크립트(JavaScript)의 몫입니다.
</Callout>

## 2. HTML·CSS·JS의 역할 분담

### 왜 세 언어로 쪼갰는가

웹 페이지 하나를 만드는 데 왜 언어가 세 개나 필요할까요? 극단적인 예로, 만약 구조·스타일·동작을 전부 한 파일에 뒤섞어 놓았다고 생각해 보십시오. 버튼 색깔 하나를 바꾸려 해도 로직이 섞인 코드 사이를 헤집어야 하고, 문구 하나를 고치려 해도 스타일 규칙을 건드릴까 조심해야 합니다. 관심사를 분리(separation of concerns, 관심사의 분리)해 두면 이런 충돌이 줄어듭니다.

> **쉽게 말하면:** HTML은 뼈대, CSS는 옷과 화장, JS는 근육과 신경입니다. 뼈대가 없으면 아무것도 설 수 없고, 옷이 없으면 볼품없고, 근육과 신경이 없으면 움직이지 않습니다.

| 언어 | 정식 명칭 | 담당 역할 | 이 문서 표현 |
|------|-----------|-----------|--------------|
| HTML | HyperText Markup Language | 콘텐츠의 구조와 의미(semantics, 의미론) | "이 부분은 제목이고, 이 부분은 목록이다" |
| CSS | Cascading Style Sheets | 시각적 표현(색상·간격·레이아웃) | "제목은 크고 파란 글씨로 보이게 한다" |
| JS | JavaScript | 동작과 상호작용(interaction, 상호작용) | "버튼을 누르면 목록에 항목을 추가한다" |

**CSS**(Cascading Style Sheets, 종속형 스타일 시트)라는 이름도 지금 살짝 풀어 두겠습니다. **캐스케이딩**(cascading)은 "폭포처럼 위에서 아래로 흘러내린다"는 뜻으로, 여러 스타일 규칙이 충돌할 때 어떤 규칙이 최종적으로 이기는지를 정하는 우선순위 체계를 가리킵니다. **스타일 시트**(style sheet)는 "스타일을 정의해 둔 문서"라는 뜻입니다. CSS의 문법과 캐스케이드 규칙 자체는 이 과목이 아니라 `css/css_fundamentals` 과목에서 처음부터 다룹니다. 여기서는 "HTML과 역할이 어떻게 나뉘는가"만 짚고 넘어갑니다.

같은 원리로 **JS**(JavaScript, 자바스크립트)가 다루는 DOM(Document Object Model, 문서 객체 모델) 조작·이벤트 처리·비동기 통신 같은 주제는 `javascript/web_apis` 과목의 몫입니다. 이 과목에서는 자바스크립트 없이 HTML 자체만으로 가능한 동작(예: 폼의 기본 제출)까지만 다룹니다.

### 같은 결과, 다른 언어의 몫

아래 예시로 세 언어가 실제로 어떻게 나뉘어 일하는지 봅니다.

```html
<button id="좋아요-버튼">좋아요</button>
```

```css
#좋아요-버튼 {
  background-color: hotpink;
  border-radius: 8px;
}
```

```js
document.getElementById('좋아요-버튼').addEventListener('click', () => {
  alert('감사합니다!');
});
```

첫 번째 코드(HTML)는 "여기 버튼이 하나 있다"는 구조를 만듭니다. 두 번째 코드(CSS)는 그 버튼을 분홍색에 둥근 모서리로 꾸밉니다. 세 번째 코드(JS)는 클릭했을 때 벌어질 동작을 붙입니다. `<button>` 요소 자체는 CSS나 JS가 없어도 존재하고 클릭도 가능합니다 — HTML만으로도 최소한의 뼈대와 기본 동작(버튼 요소의 기본 상호작용 같은)은 이미 갖추어져 있다는 뜻입니다. 이 셋이 브라우저 안에서 실제로 어떻게 합쳐져 화면이 되는지(렌더링 파이프라인)는 `javascript/web_apis` 과목이 다룹니다. 이 과목에서는 텍스트로 된 HTML이 DOM 트리로 바뀌는 부분(22편)까지만 봅니다.

## 3. "표준"이라는 것 — WHATWG와 옛 버전 표기

### 표준 기구가 필요한 이유

만약 HTML의 규칙을 크롬을 만든 회사와 사파리를 만든 회사가 각자 정한다면 어떻게 될까요? 같은 `<p>` 태그를 브라우저마다 다르게 해석해, 내가 만든 페이지가 어떤 브라우저에서는 보이고 어떤 브라우저에서는 깨질 것입니다. 이런 혼란을 막기 위해 브라우저 제작사들이 모여 **표준**(standard)을 함께 정하고 지킵니다.

HTML의 표준을 정하는 곳은 **WHATWG**(Web Hypertext Application Technology Working Group, 웹 하이퍼텍스트 애플리케이션 기술 워킹 그룹)입니다. 애플·모질라·구글·마이크로소프트 같은 브라우저 제작사들이 실무진으로 참여하는 단체로, HTML과 DOM 표준을 만들고 계속 고쳐 나갑니다. 이 표준 문서를 **HTML Living Standard**(리빙 스탠더드, 살아있는 표준)라고 부릅니다.

### "Living Standard"란 무엇인가

과거 소프트웨어 표준은 보통 "1.0", "2.0"처럼 버전을 매기고, 한 번 확정되면(freeze, 얼려두다) 다음 버전이 나올 때까지 바뀌지 않았습니다. 그런데 HTML Living Standard는 버전 번호를 붙이지 않고 **계속 수정되는 하나의 문서**로 관리됩니다. 새 요소가 필요해지면 논의를 거쳐 그 자리에서 문서에 추가되고, 잘못된 설명이 발견되면 즉시 고쳐집니다. "살아있다(living)"는 표현은 이 문서가 멈추지 않고 계속 갱신된다는 뜻입니다.

### 그럼 "HTML5"는 왜 아직도 들리는가

과거에는 W3C(World Wide Web Consortium, 월드 와이드 웹 컨소시엄)라는 별도의 표준화 기구가 HTML을 버전으로 나누어 관리했습니다. 그 역사를 시대 순으로 정리하면 다음과 같습니다.

| 시기 | 표기 | 특징 |
|------|------|------|
| 1990년대 후반 | HTML4 | 버전 번호로 관리되던 마지막 세대 중 하나. `Strict`·`Transitional`처럼 문서 형식(doctype)을 세분화 |
| 2000년대 초중반 | XHTML | HTML을 XML(Extensible Markup Language, 확장 가능한 마크업 언어) 문법으로 엄격하게 다시 쓴 시도. 태그를 반드시 닫고 소문자로만 써야 하는 등 규칙이 엄격했다 |
| 2008년 이후 | HTML5 | WHATWG가 주도해 다시 만든 세대. 이후 사실상 버전 개념 자체가 사라지고 Living Standard로 흡수됨 |

즉 "HTML5"는 한때 실제 버전 번호였지만, WHATWG가 표준을 Living Standard 체제로 전환하면서 **더는 버전을 매기지 않게** 되었습니다. 오늘날 "HTML5 문법으로 작성한다"는 말은 사실 "지금 이 시점의 HTML Living Standard를 따른다"는 뜻으로 이해하는 것이 정확합니다. W3C는 이후 WHATWG의 문서를 표준으로 채택하는 방식으로 역할을 조정했고, 실질적인 원전(1차 출처, primary source)은 WHATWG 문서입니다.

<Callout type="warning">
  **자주 틀리는 점:** "지금 HTML5로 작성하고 있다"는 표현 자체가 완전히 틀린 말은 아니지만, 실무 문서나 학습 자료를 볼 때 **버전이 고정된 스펙**을 찾으면 안 됩니다. HTML에는 더 이상 "다음 버전"이 없습니다. 문서 맨 위에 쓰는 `<!doctype html>`도 특정 버전을 선언하는 것이 아니라 그저 "표준 모드로 렌더링해 달라"는 신호일 뿐입니다. 자세한 내용은 04편에서 다룹니다.
</Callout>

### XHTML이 남긴 것

XHTML은 지금 새로 배울 필요가 없는 과거의 시도지만, 그 유산은 남아 있습니다. 예를 들어 `<img>`나 `<br>`처럼 내용이 없는 요소를 `<br />`처럼 슬래시로 닫는 관습은 XHTML의 엄격한 문법에서 왔습니다. HTML Living Standard에서는 이 슬래시가 문법적으로 필요하지 않지만(있어도 무시됩니다), 여전히 습관적으로 쓰는 코드를 자주 보게 됩니다. 이 부분은 02편에서 빈 요소(void element)를 다룰 때 다시 짚습니다.

## 핵심 정리

- HTML은 HyperText(건너뛰는 연결이 있는 글) + Markup(내용에 의미를 표시함) + Language(정해진 규칙 체계)의 합성어다.
- HTML은 구조와 의미, CSS는 시각적 표현, JS는 동작과 상호작용을 맡는다. 이 역할 분담(separation of concerns)이 세 언어가 나뉜 이유다.
- HTML 표준은 WHATWG가 Living Standard(살아있는 표준)로 관리하며, 버전 번호 없이 계속 갱신된다.
- HTML4·XHTML·HTML5는 과거 버전 표기의 흔적이며, 오늘날 "HTML5"는 특정 버전이 아니라 관용적 표현으로 이해해야 한다.
- XHTML의 엄격한 문법(빈 요소를 슬래시로 닫는 관습 등)은 지금도 습관적으로 남아 있지만 필수는 아니다.
