## 왜 리스트를 별도 요소로 구분하는가

장보기 목록, 조리 순서, 메뉴, 목차 — 우리는 일상에서 늘 여러 항목을 나열합니다. 이 항목들이 줄바꿈된 문단으로만 보이면 사람 눈에는 그럭저럭 읽히지만, 스크린 리더(screen reader, 화면 낭독 프로그램)를 쓰는 사용자에게는 전혀 다른 문제가 생깁니다. "지금 몇 개짜리 목록의 몇 번째 항목을 읽고 있는지"를 알 방법이 없기 때문입니다.

**리스트**(list, 목록)를 전용 요소로 마크업하면 브라우저는 이 정보를 **접근성 트리**(accessibility tree, 스크린 리더가 실제로 읽는 뼈대 정보 — 05편에서 다룬 DOM과는 별개로, 보조 기술에 노출되는 요약 구조입니다)에 자동으로 채워 넣습니다. "목록, 항목 5개 중 2번째"라는 안내가 저절로 나옵니다. `<p>순서: 첫째, 재료 준비. 둘째, 끓이기.</p>`처럼 문단으로 흉내 내면 이 정보가 통째로 사라집니다.

> **쉽게 말하면:** 리스트 요소는 "이건 낱개 나열이 아니라 하나의 묶음이고, 개수와 순서가 있다"는 표지판을 브라우저에 붙이는 일입니다.

HTML은 목적에 따라 세 가지 리스트를 구분합니다.

| 요소 | 이름 | 순서 의미 | 쓰는 상황 |
|------|------|-----------|-----------|
| `ul` | 비순서 리스트(unordered list) | 없음 | 장보기 품목, 태그, 메뉴처럼 순서를 바꿔도 뜻이 같은 항목 |
| `ol` | 순서 리스트(ordered list) | 있음 | 조리 순서, 순위, 단계별 절차처럼 순서 자체가 정보인 항목 |
| `dl` | 설명 리스트(description list) | 짝 관계 | 용어-정의, 질문-답변처럼 이름과 값이 짝을 이루는 데이터 |

이 세 요소는 05편에서 배운 콘텐츠 카테고리(content category)로 보면 전부 **flow 콘텐츠**(flow content, 문서 흐름을 이루는 대부분의 요소가 속하는 큰 범주)에 속합니다. 즉 `body` 어디에나 놓을 수 있는 흔한 요소이면서도, 내부 구조는 각자 엄격한 규칙을 가집니다.

## 1. 비순서 리스트 — `ul`과 `li`

### 정의와 작은 예시

**언오더드 리스트**(unordered list, 순서 없는 목록)는 `<ul>` 태그로 감싸고, 그 안에 항목마다 `<li>`(list item, 목록 항목)를 하나씩 둡니다.

```html
<ul>
  <li>우유</li>
  <li>계란</li>
  <li>식빵</li>
</ul>
```

`ul`의 콘텐츠 모델은 단순합니다. **자식으로 `li`만 올 수 있습니다**(`script`·`template` 같은 스크립트 지원 요소는 예외로 허용되지만, 실제 콘텐츠로 셀 수 있는 것은 `li`뿐입니다). `li` 안에는 반대로 거의 모든 flow 콘텐츠가 들어갈 수 있어서, 문단·이미지·다른 리스트까지 품을 수 있습니다.

### 브라우저는 실제로 어떻게 처리하는가

브라우저는 `li` 앞에 **마커**(marker, 표시 기호 — 흔히 불릿(bullet)이라 부르는 점)를 자동으로 그립니다. 이 마커는 CSS의 `list-style-type`으로 모양을 바꿀 수 있지만(CSS 문법 자체는 `css/css_fundamentals` 과목 참조), 마커가 있고 없고와 무관하게 **접근성 트리에는 항상 "목록 항목"이라는 역할(role)이 남습니다.** CSS로 `list-style: none`을 줘서 점을 지워도 스크린 리더는 여전히 "목록, 3개 중 1번째"라고 안내합니다. 즉 시각적 마커와 의미상의 리스트 역할은 서로 다른 층입니다.

<Callout type="warning">
  **자주 틀리는 점:** "불릿 점이 필요 없으니까 `div`로 줄바꿈만 하면 된다"는 생각은 접근성 정보를 통째로 버리는 선택입니다. 시각적으로 점을 없애고 싶으면 CSS로 지우고, 요소는 여전히 `ul`/`li`를 씁니다.
</Callout>

## 2. 순서 리스트 — `ol`과 순서 제어 속성

### 왜 필요한가

조리 순서나 순위처럼 **항목의 나열 순서 자체가 의미를 가지는** 경우, `ul`을 쓰면 "이 순서가 우연인지 의도인지" 브라우저도 보조 기술도 알 수 없습니다. **오더드 리스트**(ordered list, 순서 있는 목록) `<ol>`은 "이 순서는 정보다"라고 선언하는 요소입니다.

```html
<ol>
  <li>물을 끓인다</li>
  <li>면을 넣는다</li>
  <li>3분 뒤 건진다</li>
</ol>
```

브라우저는 `li` 앞에 숫자를 자동으로 매깁니다(`1.`, `2.`, `3.`). 이 번호는 CSS로 색이나 스타일을 바꿀 수 있어도, 매기는 로직 자체는 HTML 요소가 담당합니다.

### 순서를 제어하는 속성 세 가지

`ol`에는 번호 매기기 동작을 바꾸는 전용 속성이 있습니다.

| 속성 | 뜻 | 예시 | 결과 |
|------|-----|------|------|
| `start` | 시작 번호 지정 | `<ol start="5">` | 5, 6, 7 ...로 시작 |
| `reversed` | 역순으로 매기기(boolean 속성) | `<ol reversed>` | 항목 수부터 거꾸로, 예: 3, 2, 1 |
| `type` | 번호 표기 형식 | `<ol type="A">` | A, B, C(로마자·로마 숫자 등) |

`type`이 받을 수 있는 값은 `1`(기본, 아라비아 숫자), `a`/`A`(소문자·대문자 알파벳), `i`/`I`(소문자·대문자 로마 숫자)입니다. 12편에서 다룰 boolean 속성 규약이 여기서도 그대로 적용되어, `reversed`는 값 없이 속성 이름만 적으면 참(true)이 됩니다.

```html
<ol start="3" reversed>
  <li>세 번째로 처리된 항목</li>
  <li>두 번째로 처리된 항목</li>
  <li>첫 번째로 처리된 항목</li>
</ol>
```

이 코드는 "1, 2, 3" 대신 "5, 4, 3"이 아니라, `start="3"`에서 시작해 역순으로 매기므로 실제로는 **3, 2, 1**이 표시됩니다. `start`는 시작점을, `reversed`는 증가 방향을 각각 독립적으로 결정한다는 점을 헷갈리기 쉽습니다.

## 3. 리스트 중첩 — 규칙과 흔한 실수

### 왜 중첩이 필요한가

메뉴의 하위 메뉴, 목차의 하위 항목처럼 리스트 안에 또 다른 리스트가 필요한 경우가 흔합니다. HTML은 이를 허용하지만, **중첩된 리스트는 반드시 `li` 요소 "안"에 있어야 합니다.**

```html
<!-- 올바른 중첩: li 안에 ul이 들어감 -->
<ul>
  <li>
    과일
    <ul>
      <li>사과</li>
      <li>바나나</li>
    </ul>
  </li>
  <li>채소</li>
</ul>
```

```html
<!-- 잘못된 중첩: ul의 직접 자식으로 ul이 옴 -->
<ul>
  <li>과일</li>
  <ul>
    <li>사과</li>
  </ul>
</ul>
```

두 번째 코드는 05편에서 배운 콘텐츠 모델 규칙 위반입니다. `ul`의 콘텐츠 모델은 "자식은 `li`만"이라고 정했으므로, `li`가 아닌 `ul`이 바로 자식으로 오면 규칙 위반입니다. **브라우저는 이런 경우에도 화면은 어떻게든 띄웁니다**(22편에서 다룰 파싱 오류 복구 덕분입니다). 하지만 렌더링 결과가 브라우저마다 다를 수 있고, 접근성 트리에서 두 번째 `ul`이 첫 번째 `ul`의 형제로 인식되어 계층 관계가 깨집니다. Nu HTML Checker(21편에서 자세히 다룹니다)는 이 위반을 정확히 잡아냅니다.

<Callout type="warning">
  **자주 틀리는 점:** 화면에 들여쓰기가 잘 나온다고 해서 마크업이 옳다는 뜻은 아닙니다. CSS는 잘못된 구조 위에도 그럴듯한 모양을 만들어 주므로, 눈으로 확인하는 습관만으로는 이 실수를 잡을 수 없습니다.
</Callout>

## 4. 설명 리스트 — `dl`, `dt`, `dd`

### 왜 필요한가

용어집, FAQ, 상품 스펙표처럼 "이름 하나에 설명 하나(또는 여럿)"가 짝을 이루는 데이터가 있습니다. `ul`이나 `ol`로 표현하면 이름과 설명이 그냥 나열된 항목처럼 보여서, "이게 짝이다"라는 관계 정보가 사라집니다. **디스크립션 리스트**(description list, 설명 목록) `<dl>`은 이 짝 관계를 표현하기 위한 전용 요소입니다.

> **쉽게 말하면:** `dl`은 국어사전입니다. 표제어(`dt`)와 그 뜻풀이(`dd`)가 항상 붙어 다닙니다.

```html
<dl>
  <dt>HTML</dt>
  <dd>웹 페이지의 구조를 만드는 마크업 언어</dd>

  <dt>CSS</dt>
  <dd>HTML 요소의 시각적 표현을 담당하는 언어</dd>
</dl>
```

- `dt`(description term, 용어): 설명할 대상의 이름
- `dd`(description definition, 정의): 그 이름에 대한 설명

`dt` 하나에 `dd`가 여러 개 붙을 수도 있고(한 용어에 여러 뜻), 반대로 `dt`가 여러 개 연달아 나온 뒤 `dd` 하나가 붙어 여러 이름을 한 설명으로 묶을 수도 있습니다.

```html
<dl>
  <dt>서울</dt>
  <dt>Seoul</dt>
  <dd>대한민국의 수도</dd>
</dl>
```

이 예시는 "서울"과 "Seoul"이라는 두 이름이 하나의 정의를 공유한다는 뜻을 정확히 전달합니다. 만약 이를 표(table)로 만들면 "이름" 칸과 "설명" 칸이라는 격자 구조가 강제되어 이런 다대일 관계를 표현하기 번거롭습니다. `dl`은 격자가 아니라 순수한 짝짓기 구조라서 이런 유연함이 자연스럽습니다.

### FAQ에 쓰는 경우

`dl`은 질문-답변 쌍에도 흔히 쓰입니다.

```html
<dl>
  <dt>배송은 얼마나 걸리나요?</dt>
  <dd>영업일 기준 2~3일 소요됩니다.</dd>

  <dt>교환·환불은 가능한가요?</dt>
  <dd>수령 후 7일 이내 가능합니다.</dd>
</dl>
```

<Callout type="warning">
  **자주 틀리는 점:** `dl`을 "정의 리스트(definition list)"라는 옛 이름으로 기억해, 사전적 정의에만 써야 한다고 오해하기 쉽습니다. WHATWG 스펙은 오래전에 이름을 "설명 리스트(description list)"로 바꾸며 용도를 "이름-값 그룹 전반"으로 넓혔습니다. FAQ, 메타데이터 목록(작성자·발행일 등)에 써도 규칙 위반이 아닙니다.
</Callout>

## 5. 접근성 관점 — 목록 개수와 위치 안내

스크린 리더 사용자는 리스트를 만나면 보통 "목록, N개 항목"이라는 안내를 먼저 듣고, 필요하면 목록 단위로 건너뛰는 단축키를 씁니다. 이 개수(N)는 실제 `li` 자식 개수를 브라우저가 세어 자동으로 계산한 값이라, 마크업이 정확할수록 안내도 정확해집니다. 리스트를 `div`로 흉내 내면 이 개수 정보가 아예 존재하지 않으므로, 사용자는 지금 보고 있는 것이 목록인지 개별 문단인지조차 구분하지 못합니다.

또한 `ol`과 `ul`은 접근성 트리에서 서로 다른 역할(`list` role은 같지만 순서 정보 유무가 다름)로 구분되므로, 순서가 있는 절차를 `ul`로 잘못 쓰면 "순서를 지켜야 한다"는 신호 자체가 사용자에게 전달되지 않습니다.

## 핵심 정리

- 순서가 뜻에 영향을 주지 않으면 `ul`, 순서 자체가 정보면 `ol`을 쓴다. 둘 다 `li` 자식만 허용하는 엄격한 콘텐츠 모델을 가진다.
- `ol`의 `start`(시작 번호)·`reversed`(역순, boolean 속성)·`type`(표기 형식)은 서로 독립적으로 작동한다.
- 리스트를 중첩할 때는 자식 `ul`/`ol`을 반드시 `li` 요소 안에 넣어야 한다. `ul`의 직접 자식으로 `ul`을 두면 콘텐츠 모델 위반이며, 브라우저는 화면을 띄워도 접근성 트리와 검증기 결과가 어긋난다.
- `dl`/`dt`/`dd`는 이름-값이 짝을 이루는 데이터(용어집, FAQ, 메타데이터)에 쓴다. 하나의 `dt`에 여러 `dd`, 또는 여러 `dt`에 하나의 `dd`가 붙는 다대다 짝짓기도 가능하다.
- 리스트 요소가 주는 "개수·순서·짝 관계" 정보는 시각적 마커를 CSS로 지워도 접근성 트리에는 그대로 남는다.
