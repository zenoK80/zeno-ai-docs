</Callout>

## 왜 인용과 코드에 전용 요소가 필요한가

남의 글을 옮겨 적을 때는 "이건 내 문장이 아니라 다른 사람의 말"이라는 표시가 필요합니다. 마찬가지로 기술 문서에서 코드·키보드 입력·프로그램 출력을 설명할 때도 "이 글자들은 평범한 문장이 아니라 코드다"라는 표시가 필요합니다. 이 구분을 그냥 따옴표나 들여쓰기 같은 시각적 장치로만 하면, 스크린 리더 사용자나 검색 엔진은 "이게 인용인지 강조인지, 코드인지 그냥 폰트가 다른 글씨인지" 구분할 수 없습니다.

HTML은 이 두 영역 모두에 **역할별로 세분화된 요소**를 준비해 두었습니다. 이번 편에서는 그 요소들을 정확히 구분해 쓰는 법을 다룹니다.

## 1. 짧은 인용 — `q`

**Q**(quotation, 인용)는 문장 중간에 짧게 끼워 넣는 인용에 씁니다.

```html
<p>그는 <q>내일 다시 오겠다</q>고 말했다.</p>
```

`q` 요소를 쓰면 브라우저가 **자동으로 따옴표를 붙여줍니다.** 즉 마크업 안에 직접 큰따옴표를 타이핑할 필요가 없습니다. 언어(`lang` 속성, 12편에서 다룹니다)에 따라 따옴표 모양이 달라지기도 합니다(영어권은 `" "`, 일부 언어권은 `« »`를 쓰는 식입니다).

<Callout type="warning">
  **자주 틀리는 점:** `<q>` 안에 큰따옴표를 직접 써서 `<q>"내일 다시 오겠다"</q>`처럼 만들면 따옴표가 이중으로 겹칩니다. `q`가 이미 따옴표를 그려주므로 내용에는 인용된 말만 넣습니다.
</Callout>

## 2. 긴 인용 — `blockquote`

**블록쿼트**(blockquote, 블록 단위 인용)는 문단 하나 이상 분량의 긴 인용, 즉 독립된 단락으로 다뤄야 할 인용에 씁니다.

```html
<blockquote>
  <p>가장 큰 위험은 목표를 너무 높게 잡고 놓치는 것이 아니라,
  너무 낮게 잡고 이루는 것이다.</p>
</blockquote>
```

`blockquote`는 콘텐츠 모델상 **flow 콘텐츠**(05편에서 다룬 문서 흐름 요소)를 자식으로 가질 수 있어서, 내부에 `p`·리스트·심지어 다른 `blockquote`까지 넣을 수 있습니다. `q`는 반대로 인라인 요소라 문장 속에 자연스럽게 섞입니다.

### `q`와 `blockquote`의 선택 기준

| 구분 | `q` | `blockquote` |
|------|-----|--------------|
| 분량 | 짧은 구절, 문장 일부 | 문단 이상의 긴 인용 |
| 콘텐츠 모델 | phrasing 콘텐츠(문장 안에 섞임) | flow 콘텐츠(독립된 블록) |
| 따옴표 | 브라우저가 자동으로 붙임 | 붙이지 않음(디자인은 CSS로) |
| 예시 상황 | 대화체 인용 한 마디 | 연설문·기사 발췌·긴 인터뷰 내용 |

이 판단은 순전히 **분량과 문서 흐름상 위치**로 하는 것이지, "중요해 보이니까 blockquote"처럼 강조 목적으로 고르는 것이 아닙니다. 강조가 목적이라면 6편에서 다룬 `strong`이나 `em`이 맞는 선택입니다.

## 3. 출처 표기 — `cite` 속성과 `cite` 요소

인용에는 "누가, 또는 어디서 한 말인가"라는 출처 정보가 따라붙는 경우가 많습니다. HTML은 이를 표현하는 방법을 두 가지 준비해 두었는데, 이름이 같아서 혼동하기 쉽습니다.

### `cite` 속성 — URL을 담는 속성

`q`와 `blockquote`에는 `cite`라는 **속성**을 붙일 수 있습니다. 이 속성은 인용의 출처가 되는 문서의 URL을 값으로 받습니다.

```html
<blockquote cite="https://example.com/speech-2024">
  <p>변화는 소수의 사람으로부터 시작된다.</p>
</blockquote>
```

이 값은 브라우저 화면에 **보이지 않습니다.** 오직 기계(검색 엔진, 브라우저 확장 프로그램 등)가 읽는 메타데이터입니다. 사람 눈에 출처를 보여주고 싶다면 별도로 텍스트를 적어야 합니다.

### `cite` 요소 — 화면에 보이는 출처 이름

`<cite>`는 속성이 아니라 **요소**로, 저작물의 제목이나 저자 이름처럼 화면에 실제로 표시할 출처 정보를 감쌉니다.

```html
<blockquote cite="https://example.com/speech-2024">
  <p>변화는 소수의 사람으로부터 시작된다.</p>
</blockquote>
<p>— <cite>2024년 신년사</cite> 중에서</p>
```

브라우저 기본 스타일은 `cite` 요소 내용을 흔히 기울임체(이탤릭)로 표시합니다. 속성 `cite`(URL, 기계용)와 요소 `cite`(제목, 사람이 보는 텍스트)는 이름만 같을 뿐 완전히 다른 용도라는 점이 이 편에서 가장 헷갈리기 쉬운 지점입니다.

<Callout type="warning">
  **자주 틀리는 점:** "URL을 화면에 보여주고 싶어서 `cite` 요소 안에 URL 문자열을 그대로 적는" 경우가 흔한데, `cite` 요소는 URL이 아니라 **제목·이름**을 위한 자리입니다. URL은 속성으로, 사람이 읽을 이름은 요소로 분리해서 씁니다.
</Callout>

## 4. 공백을 그대로 보존하기 — `pre`

### 왜 필요한가

HTML은 기본적으로 **공백 접기**(whitespace collapsing, 화이트스페이스 병합)라는 동작을 합니다. 소스 코드에 스페이스를 몇 개를 연달아 넣든, 줄바꿈을 몇 번 하든, 브라우저는 이를 공백 하나로 뭉쳐서 화면에 그립니다. 문장을 쓸 때는 이 동작이 편리하지만(들여쓰기를 아무리 해도 결과가 일정합니다), 코드나 아스키 아트처럼 **들여쓰기와 줄바꿈 자체가 의미인 콘텐츠**에는 치명적입니다.

**프리**(pre, preformatted text의 줄임 — 미리 서식이 갖춰진 텍스트라는 뜻)는 이 공백 접기 동작을 끄는 요소입니다. `pre` 안의 공백·줄바꿈·들여쓰기는 소스에 적힌 그대로 화면에 나타납니다.

```html
<pre>
function 합계(a, b) {
  return a + b;
}
</pre>
```

이 코드를 `pre` 없이 그냥 문단으로 적었다면, 들여쓰기용 스페이스 두 칸이 전부 무시되어 함수 본문과 나머지 줄이 같은 들여쓰기로 붙어버립니다.

### `code`와 함께 쓰는 관용구

`pre` 자체는 "공백 보존"만 담당할 뿐, "이 내용이 코드"라는 의미까지 담지는 않습니다. 그래서 여러 줄짜리 코드를 마크업할 때는 관용적으로 `pre`와 `code`를 함께 씁니다.

```html
<pre><code>function 합계(a, b) {
  return a + b;
}</code></pre>
```

`pre`는 "공백을 접지 마라"는 지시, `code`는 "이건 코드다"라는 의미 표시로 역할이 나뉩니다.

## 5. 코드 관련 인라인 요소 — `code`, `kbd`, `samp`, `var`

한 줄짜리 짧은 코드 조각을 문장 속에 넣을 때는 아래 네 요소 중 상황에 맞는 것을 고릅니다. 넷 다 겉모습은 브라우저 기본 스타일에서 모노스페이스(monospace, 고정폭 서체 — 글자마다 너비가 같은 서체) 글꼴로 비슷하게 보이지만, **의미는 전혀 다릅니다.**

| 요소 | 뜻 | 쓰는 상황 | 예시 |
|------|-----|-----------|------|
| `code` | 코드 조각 그 자체 | 함수 이름, 변수, 코드 줄 | 이 함수는 `parseInt`를 호출합니다 |
| `kbd` | keyboard input, 키보드 입력 | 사용자가 눌러야 할 키 | `Ctrl` 키와 `S` 키를 함께 누르세요 |
| `samp` | sample output, 표본 출력 | 프로그램이 실제로 출력한 결과 | 실행하면 화면에 `Hello, world!`가 뜹니다 |
| `var` | variable, 변수 | 수식이나 프로그램의 변수 이름 | 넓이는 `가로` 곱하기 `세로`입니다 |

```html
<p>터미널에서 <kbd>npm install</kbd>을 입력하면 화면에</p>
<pre><samp>added 42 packages in 3s</samp></pre>
<p>같은 메시지가 출력됩니다. 이때 <code>package.json</code>의
<var>dependencies</var> 항목이 갱신됩니다.</p>
```

이 네 요소를 구분하는 이유는 시각 효과 때문이 아니라, 스크린 리더나 검색 엔진, 나아가 문서를 재가공하는 도구가 "이 글자는 사용자가 입력할 키인지, 프로그램이 뱉은 결과인지, 코드 자체인지"를 명확히 구분할 수 있게 하기 위해서입니다. 넷을 전부 `code` 하나로 뭉뚱그려 써도 화면은 비슷하게 보이지만, 의미 정보는 사라집니다.

<Callout type="warning">
  **자주 틀리는 점:** "모노스페이스 글꼴로 보이면 다 `code`"라고 생각해 `kbd`나 `samp`가 필요한 자리까지 `code`로 채우는 경우가 흔합니다. 겉모습이 비슷한 것은 브라우저 기본 스타일이 우연히 비슷하게 정했을 뿐이며, CSS로 각각 다르게 꾸밀 수도 있습니다.
</Callout>

## 6. 접근성 관점

`blockquote`는 스크린 리더에서 "인용문 시작"과 "인용문 끝"을 안내하는 경계로 쓰입니다. 인용이 아닌 콘텐츠를 단지 들여쓰기 효과를 노리고 `blockquote`로 감싸면, 스크린 리더 사용자는 실제로는 인용이 아닌 내용을 "누군가의 말"로 잘못 안내받게 됩니다. 마찬가지로 `code`/`kbd`/`samp`는 코드 편집기나 스크린 리더의 코드 낭독 모드에서 발음 방식이나 강세를 다르게 처리하는 근거가 되기도 하므로, 의미에 맞는 요소를 고르는 것이 시각 효과보다 우선합니다.

## 핵심 정리

- 짧은 인용은 `q`(자동으로 따옴표가 붙는 인라인 요소), 문단 단위의 긴 인용은 `blockquote`(flow 콘텐츠를 담는 블록 요소)를 쓴다.
- `cite` **속성**(URL, 기계용 메타데이터)과 `cite` **요소**(제목·이름, 화면에 보이는 텍스트)는 이름만 같을 뿐 역할이 다르다.
- `pre`는 공백 접기를 끄고 소스에 적힌 그대로 공백·줄바꿈을 보존한다. 여러 줄 코드는 관용적으로 `pre`와 `code`를 함께 쓴다.
- `code`(코드 자체)·`kbd`(키보드 입력)·`samp`(프로그램 출력)·`var`(변수)는 겉모습이 비슷해도 의미가 다르므로 상황에 맞게 구분해 쓴다.
- 인용·코드 요소를 시각 효과(들여쓰기, 고정폭 글꼴)만 노리고 오용하면 스크린 리더가 잘못된 의미로 안내한다.
