</Callout>

## 왜 `<input>`만으로는 부족한가

13·14편에서 다룬 `<input>`은 한 줄짜리 값 하나를 받는 데 최적화된 요소입니다. 하지만 실제 폼에는 이런 것들이 필요합니다.

- 미리 정해진 여러 선택지 중 하나를 고르는 목록(국가, 배송 방법)
- 여러 줄에 걸친 자유로운 글(문의 내용, 후기)
- "제출"이 아니라 "초기화"나 다른 동작을 하는 버튼

이 세 가지를 위한 요소가 각각 `<select>`, `<textarea>`, `<button>`입니다. 셋 다 `<input>`처럼 흔하지만, 콘텐츠 모델과 값이 결정되는 방식이 `<input>`과 다릅니다.

## 1. `<select>`/`<option>`/`<optgroup>` — 목록에서 고르기

### 기본 구조

`<select>`는 그 자체로는 아무 선택지도 갖지 않는 컨테이너입니다. 실제 선택지는 자식 요소인 `<option>`이 하나씩 정의합니다.

```html
<label for="배송방법">배송 방법</label>
<select id="배송방법" name="shipping">
  <option value="standard">일반 배송</option>
  <option value="express" selected>빠른 배송</option>
  <option value="pickup">매장 픽업</option>
</select>
```

`selected` 역시 14편에서 배운 것과 같은 **불리언 속성**입니다. 존재하면 그 `<option>`이 처음부터 선택된 상태로 화면에 나타납니다.

### value 생략 시 무슨 값이 전송되는가

`<option>`의 `value` 속성은 생략할 수 있습니다. 생략하면 브라우저는 **`<option>` 태그 사이의 텍스트 내용**을 그대로 제출 값으로 씁니다.

```html
<select name="color">
  <option value="RED">빨강</option>   <!-- 선택 시 color=RED -->
  <option>파랑</option>               <!-- 선택 시 color=파랑 (텍스트 그대로) -->
</select>
```

화면에 보이는 문구와 서버로 가는 실제 값이 같아야 한다면 `value`를 생략해도 되지만, 화면 문구는 사용자용으로 예쁘게 쓰고 서버로는 별도의 코드값(`RED`, `KR` 같은)을 보내고 싶다면 반드시 `value`를 명시해야 합니다. 이 구분을 모르고 `value`를 생략했다가, 사용자가 화면 문구를 나중에 한국어에서 영어로 바꾸는 순간 서버로 가는 값까지 덩달아 바뀌어 버리는 실수가 흔합니다.

### `<optgroup>`으로 묶어서 보여주기

선택지가 많아지면 `<optgroup>`(옵션그룹)으로 시각적인 소제목을 붙여 묶을 수 있습니다.

```html
<select name="menu">
  <optgroup label="음료">
    <option value="coffee">커피</option>
    <option value="tea">차</option>
  </optgroup>
  <optgroup label="디저트">
    <option value="cake">케이크</option>
  </optgroup>
</select>
```

`<optgroup>`의 `label` 속성 문구는 화면에 굵게 표시되는 소제목일 뿐, 그 자체는 선택할 수 없고 제출 데이터에도 포함되지 않습니다. `<fieldset>`/`<legend>`가 여러 입력을 묶어 접근성 트리에 이름을 붙이는 것과 비슷한 역할을, `<select>` 안에서는 `<optgroup>`이 맡습니다.

## 2. `<textarea>` — 여러 줄 텍스트

### `<input>`과의 근본적인 차이

`<textarea>`는 겉보기엔 "여러 줄 되는 `<input>`" 같지만, 콘텐츠 모델이 완전히 다릅니다. `<input>`은 빈 요소라 값이 `value` **속성**에 담기지만, `<textarea>`는 여는 태그와 닫는 태그를 가진 요소이며 값이 **태그 사이의 텍스트 콘텐츠**로 담깁니다.

```html
❌ <textarea value="기본 문구입니다"></textarea>   <!-- value 속성은 무시된다 -->
✅ <textarea>기본 문구입니다</textarea>            <!-- 태그 사이 텍스트가 초기값 -->
```

이 차이는 04·05편에서 배운 "요소마다 콘텐츠 모델이 다르다"는 원칙이 실제로 드러나는 지점입니다. `value` 속성에 익숙한 채로 `<textarea>`를 만나면 거의 반드시 이 실수를 한 번은 저지릅니다.

### 줄바꿈 처리와 속성

사용자가 `<textarea>` 안에서 `Enter`를 눌러 만든 줄바꿈은 텍스트 콘텐츠 안에 실제 개행 문자로 그대로 보존됩니다. 제출될 때는 운영체제마다 다른 줄바꿈 표기(`\n`만 쓰는 방식, `\r\n`을 쓰는 방식)가 `CRLF`(`\r\n`)로 통일되어 전송됩니다 — 이 정규화는 16편에서 다루는 인코딩 과정의 일부입니다.

`rows`와 `cols` 속성으로 기본 크기(보이는 줄 수와 가로 문자 수)를 지정할 수 있지만, 실제 화면 크기는 CSS로 조정하는 것이 일반적입니다(CSS 크기 지정은 `css/css_fundamentals` 과목 참조).

<Callout type="warning">
  **자주 틀리는 점:** 스펙은 `<textarea>` 시작 태그 바로 뒤에 오는 **첫 번째 줄바꿈 문자 하나**를 값에서 제외하도록 정합니다. 즉 `<textarea>`를 여는 태그 다음 줄에 코드를 들여 쓰면, 그 줄바꿈 하나는 무시되어 실제 초기값에 포함되지 않습니다(단, 그 뒤에 이어지는 추가 줄바꿈이나 공백은 그대로 남습니다). 마크업을 보기 좋게 들여 썼다가 "왜 앞에 빈 줄이 안 생기지"라며 당황하지 않으려면 알아 두어야 하는 사실입니다.
</Callout>

## 3. `<button>` — 세 가지 타입

### 타입에 따라 동작이 완전히 달라진다

| `type` 값 | 폼 안에서의 동작 |
|-----------|-------------------|
| `submit` | 폼을 제출한다. **`type`을 생략하면 이 값이 기본값이다** |
| `reset` | 폼의 모든 입력을 초기 상태로 되돌린다(사용자가 입력한 내용을 전부 지운다) |
| `button` | 아무 기본 동작도 하지 않는다. 자바스크립트로 직접 동작을 붙일 때 쓴다 |

<Callout type="warning">
  **자주 틀리는 점:** `<form>` 안에 있는 `<button>`은 `type`을 지정하지 않으면 **자동으로 `submit`이 됩니다.** "모달 닫기", "다음 단계로" 같은 단순 동작을 위해 넣은 버튼이 실은 폼 전체를 의도치 않게 제출해 버리는 사고가 실무에서 매우 흔합니다. 제출을 의도하지 않는 모든 버튼에는 반드시 `type="button"`을 명시적으로 적어야 합니다.
</Callout>

### `<button>`과 `<input type="submit">`의 차이

전통적으로 제출 버튼은 `<input type="submit" value="보내기">`로도 만들 수 있었습니다. 둘 다 폼을 제출한다는 점은 같지만 콘텐츠 모델이 다릅니다.

| 비교 항목 | `<button type="submit">` | `<input type="submit">` |
|-----------|---------------------------|---------------------------|
| 콘텐츠 모델 | 여는/닫는 태그가 있어 내부에 텍스트뿐 아니라 `<img>` 같은 다른 요소도 넣을 수 있다 | 빈 요소라 `value` 속성의 문자열만 표시 가능 |
| 화면에 보이는 문구를 바꾸는 법 | 태그 사이 콘텐츠를 수정 | `value` 속성 값을 수정 |

아이콘과 글자를 함께 보여주는 버튼처럼 내부 구조가 필요하면 `<button>`을, 순수 텍스트 하나로 충분하면 둘 중 아무거나 써도 동작은 같습니다. 다만 새 마크업을 작성할 때는 `<button>`이 더 유연하므로 우선적으로 고려됩니다.

## 접근성 — 스크린 리더가 각 요소를 읽는 법

`<select>`는 운영체제의 네이티브(native, 브라우저 자체 제공) 드롭다운 위젯을 사용하는 경우가 많아, 방향키로 옵션을 이동하고 문자 키를 눌러 그 글자로 시작하는 옵션으로 바로 건너뛰는 동작(타입어헤드, type-ahead)이 별도 코드 없이 기본 제공됩니다. `<textarea>`는 우측 하단의 크기 조절 손잡이가 마우스 전용인 경우가 있어, 키보드만 쓰는 사용자를 위해 CSS `resize` 속성을 임의로 끄기보다는 기본 동작을 유지하는 것이 안전합니다(관련 CSS는 `css/css_fundamentals` 과목 참조). `<button>`은 스크린 리더가 태그 사이의 텍스트 콘텐츠를 접근 가능한 이름(accessible name)으로 읽으므로, 아이콘만 있고 텍스트가 없는 버튼에는 반드시 `aria-label` 같은 대체 텍스트를 채워야 합니다.

## 자주 틀리는 점

- `<textarea>`에 `value` 속성을 써서 기본값을 넣으려다 반영되지 않는다 — 태그 사이 텍스트가 값이다.
- `<option>`의 `value`를 생략해 놓고 화면 문구와 서버 전송값이 같다고 착각한다.
- 폼 안의 `<button>`에 `type`을 안 써서 의도치 않게 `submit`으로 동작한다.
- `<optgroup>`의 `label`이 선택 가능한 옵션이라고 착각한다.

## 핵심 정리

- `<select>`의 실제 선택지는 자식 `<option>`이 정의하며, `value`를 생략하면 태그 사이 텍스트가 제출값이 된다. `<optgroup>`은 시각적 묶음일 뿐 그 자체는 선택되거나 제출되지 않는다.
- `<textarea>`는 값이 `value` 속성이 아니라 태그 사이 텍스트 콘텐츠에 담긴다는 점에서 `<input>`과 콘텐츠 모델이 다르다. 줄바꿈은 그대로 보존되고 제출 시 `CRLF`로 정규화된다.
- `<button>`의 기본 `type`은 `submit`이다. 제출을 의도하지 않는 버튼에는 반드시 `type="button"`을 명시해야 한다.
- `<button>`은 내부에 다른 요소를 담을 수 있어 `<input type="submit">`보다 유연하다.
