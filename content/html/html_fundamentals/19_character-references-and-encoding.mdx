## 왜 어떤 문자는 그대로 못 쓰는가

HTML 문서에 "3은 5보다 작다"는 문장을 그냥 다음처럼 쓰면 어떻게 될까요.

```
3 < 5 그리고 5 > 3
```

브라우저의 파서(parser, 구문 분석기)는 홑화살괄호(`<`)를 만나는 순간 "태그가 시작된다"고 해석합니다. `< 5`는 여는 태그를 시작하려다가 알 수 없는 요소 이름을 만난 것으로 처리되어 파싱 오류가 나거나, 최악의 경우 뒤 내용이 통째로 태그 속성처럼 먹혀버립니다. 이것이 05편에서 배운 콘텐츠 모델과는 다른 층위의 문제입니다 — 여기서는 **문자 자체가 마크업 문법의 예약 기호와 충돌**하는 상황입니다.

앰퍼샌드(`&`)도 마찬가지입니다. `&`는 그 뒤에 오는 문자열을 **문자 참조**(character reference)의 시작 기호로 해석하려고 시도합니다. `AT&T`라고 그냥 쓰면, 파서는 `&T`를 문자 참조로 오인하려다가 세미콜론이 없어 실패하는 식으로 처리합니다(대부분의 브라우저는 이런 경우를 관대하게 복구하지만, 검증기는 오류로 잡아냅니다).

> **쉽게 말하면:** `<`와 `&`는 HTML 세계의 특수 기호입니다. 수학에서 `+`나 `=`을 문장 속에 아무렇게나 섞어 쓰면 계산식으로 오해받듯이, 이 두 문자는 브라우저에게 "이제부터 태그다" 또는 "이제부터 특수 코드다"라는 신호로 읽힙니다.

## 문자 참조 — 이름 붙은 것과 숫자로 된 것

이 충돌을 피하려고 HTML은 **문자 참조**라는 이스케이프(escape, 탈출) 표기법을 정의합니다. "이스케이프"라는 말은 원래 뜻(탈출) 그대로, 그 문자가 "지금은 특수 기호가 아니라 그냥 평범한 글자다"라고 문법 해석에서 빠져나가게(탈출하게) 해준다는 뜻입니다. 문자 참조는 두 종류입니다.

| 종류 | 표기 예시 | 설명 |
|------|-----------|------|
| 이름 붙은 문자 참조 (named character reference) | `&lt;`, `&gt;`, `&amp;` | 미리 정해진 이름으로 문자를 가리킨다. `lt`는 less-than(보다 작다), `gt`는 greater-than(보다 크다), `amp`는 ampersand(앰퍼샌드)의 줄임말 |
| 숫자 문자 참조 (numeric character reference) | `&#60;`, `&#x3C;` | 유니코드(Unicode) 코드 포인트 번호로 문자를 직접 가리킨다. `#` 뒤에 십진수, `#x` 뒤에 16진수 |

세 개는 특히 자주 씁니다.

```html
<p>3 &lt; 5 그리고 5 &gt; 3</p>
<p>AT&amp;T는 통신 회사입니다.</p>
```

**중요한 예외**가 하나 있습니다. `>`(보다 크다 기호)는 문법상 대부분의 위치에서 그대로 써도 파싱에 문제가 없습니다. 태그를 여는 신호는 `<`뿐이기 때문입니다. 그래도 코드 예시나 표에서 `<`와 `>`를 쌍으로 다룰 때는 일관성을 위해 둘 다 이스케이프하는 것이 일반적인 관행입니다.

전체 이름 붙은 문자 참조 목록의 **1차 출처**(원전)는 WHATWG 스펙의 "Named character references" 절입니다. 예전에는 W3C의 HTML4 문자 엔티티 표가 기준처럼 쓰였지만, 지금은 그 표가 하위 호환을 위한 목록일 뿐이고 실제 원전은 WHATWG 쪽입니다.

## 실제로 어떻게 처리되는가 — 파서가 보는 것과 화면에 그려지는 것

아래 실습기는 이스케이프하지 않은 `<`가 실제로 어떻게 처리되는지 눈으로 확인하는 예시입니다. `/index.html` 안에서 `3 < 5`를 이스케이프한 줄과 안 한 줄을 비교해 보세요.

## UTF-8과 meta charset — 인코딩이라는 또 다른 층위

문자 참조가 "예약 기호와의 충돌"을 해결하는 도구라면, **인코딩**(encoding)은 그보다 한 단계 아래층의 문제를 다룹니다. 컴퓨터는 결국 0과 1만 저장합니다. "가"라는 한글 한 글자, "A"라는 영문 한 글자를 각각 어떤 숫자로 바꿔 저장할지 정하는 규칙이 **문자 인코딩**(character encoding)입니다.

**UTF-8**(8-bit Unicode Transformation Format, 8비트 유니코드 변환 형식)은 지금 웹에서 사실상 유일한 표준 인코딩입니다. 전 세계 문자(한글, 한자, 이모지 포함)를 하나의 체계로 표현할 수 있고, 영문 알파벳은 기존 ASCII(아스키)와 완전히 호환되도록 설계되어 효율적입니다.

문서가 어떤 인코딩으로 저장되었는지를 브라우저에게 알려주는 것이 `<head>` 안의 `<meta charset="utf-8" />`입니다(문서 뼈대와 `head`의 다른 필수 메타데이터는 [04편](/html/html_fundamentals/04_document-skeleton-and-head) 참조). 이 선언이 없거나 실제 파일 저장 인코딩과 다르면, 한글이 "占쏙옙" 같은 모양으로 깨져 보이는 **문자 깨짐**(mojibake, 모지바케) 현상이 생깁니다. 브라우저가 바이트를 엉뚱한 인코딩 규칙으로 해석했기 때문입니다.

<Callout type="warning">
  **자주 틀리는 점:** `meta charset` 선언 문자열과 에디터가 실제로 파일을 저장한 인코딩이 다르면 아무 소용이 없습니다. 선언은 "이 파일은 UTF-8이다"라는 **약속**일 뿐이고, 실제 저장 인코딩이 다르면 브라우저는 잘못된 약속을 믿고 잘못 해석합니다. 에디터의 "다른 이름으로 저장" 메뉴에서 인코딩을 UTF-8로 맞추는 습관이 필요합니다.
</Callout>

## 문자 참조 vs 인코딩 — 헷갈리기 쉬운 두 개념

| 구분 | 문자 참조 | 인코딩 |
|------|-----------|--------|
| 해결하는 문제 | `<`·`&` 같은 마크업 예약 기호와 실제 텍스트의 충돌 | 문자를 바이트로 저장·전송하는 규칙 |
| 표기 위치 | HTML 소스 코드 안 (`&lt;`, `&amp;`) | 파일 저장 방식 + `meta charset` 선언 |
| 깨지면 나타나는 증상 | 태그로 오인되어 파싱 오류, 내용 사라짐 | 문자 깨짐(모지바케), 물음표나 네모로 표시 |
| 적용 범위 | HTML 문서 안의 특정 예약 문자 몇 개 | 문서 전체의 모든 문자 |

두 개념은 서로 다른 층위지만 자주 한 문장에 등장해 혼동됩니다. "한글이 깨졌다"는 인코딩 문제이고, "`<div>`라는 글자를 화면에 그대로 보여주고 싶은데 진짜 태그로 해석돼 버렸다"는 문자 참조 문제입니다.

## 핵심 정리

- `<`와 `&`는 HTML 문법의 예약 기호라 산문에 그대로 쓰면 태그나 문자 참조로 오인되어 파싱이 어긋난다.
- 이름 붙은 문자 참조(`&lt;`, `&gt;`, `&amp;`)와 숫자 문자 참조(`&#60;`, `&#x3C;`)로 이스케이프한다. 1차 출처는 WHATWG의 named character references 절이다.
- 문자 참조는 소스 코드 표기일 뿐이며, 파싱이 끝나면 텍스트 노드 안에서 원래 문자로 되돌아간다.
- `UTF-8`은 사실상 표준 문자 인코딩이고, `<meta charset="utf-8" />`은 브라우저에게 이 문서의 인코딩을 알려주는 선언이다. 선언과 실제 저장 인코딩이 다르면 문자 깨짐이 생긴다.
- 문자 참조(예약 기호 충돌)와 인코딩(바이트 저장 규칙)은 서로 다른 층위의 문제이며 헷갈리지 않아야 한다.
