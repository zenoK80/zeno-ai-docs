## 왜 "일부러 틀린 코드"로 연습하는가

21편에서 Nu HTML Checker(누 에이치티엠엘 체커) 사용법과 대표적인 실수 유형을 이미 배웠습니다. 하지만 검증기 메시지를 실제로 **읽고 해석하는 능력**은 예제를 눈으로 보는 것만으로는 늘지 않습니다. 사람이 짠 코드에 파묻힌 진짜 실수를 찾아내려면, 먼저 "이런 실수는 이런 문장으로 지적당한다"는 감을 몸에 익혀야 합니다.

> **쉽게 말하면:** 의사가 되려면 정상 엑스레이 사진만 봐서는 안 됩니다. 골절된 사진을 보고 "여기가 부러졌다"고 짚어내는 연습이 필요합니다. 이 편은 일부러 부러뜨린 HTML을 보여주고 여러분이 짚어내게 하는 자리입니다.

이 편도 새 개념을 배우지 않습니다. `<Steps>`로 대표적인 오류 유형 다섯 가지를 하나씩 훑고, 마지막에 다섯 가지가 전부 섞인 `<CodePlayground>`를 제공합니다. 실제 검증은 [Nu HTML Checker](https://validator.w3.org/nu/)에 실습기의 코드를 복사해 붙여 넣고 돌려 보는 것을 권합니다. 실습기 자체는 브라우저 렌더링만 보여주고 검증기 기능은 내장하지 않으므로, 브라우저가 "그냥 화면에 띄워 버리는" 관대함과 검증기가 "규칙 위반을 콕 집는" 엄격함의 차이를 직접 대비해 보세요.

## 대표 오류 다섯 가지

<Steps>

### 1. 콘텐츠 모델 위반 — p 안에 div

05편에서 배운 규칙입니다. `p`는 phrasing 콘텐츠(phrasing content, 문장 흐름 콘텐츠)만 담을 수 있는데 `div`는 flow 콘텐츠(flow content)에 속해 phrasing보다 큰 범주입니다.

```html
<!-- 틀린 코드 -->
<p>
  오늘의 공지사항입니다.
  <div>중요: 내일은 휴무입니다.</div>
</p>
```

Nu HTML Checker는 이런 코드를 만나면 대략 다음과 같은 메시지를 냅니다.

```
Error: Element div not allowed as child of element p in this context.
```

브라우저는 이 상황을 조용히 "복구"합니다. `div`를 만나는 순간 열려 있던 `p`를 자동으로 닫아 버리고, `div`를 `p`의 형제로 새로 시작합니다(22편에서 배운 파싱 오류 복구입니다). 그래서 화면은 큰 문제 없이 뜨지만, 여러분이 의도한 "이 문단 전체가 하나의 `p`"라는 구조는 사라지고 둘로 쪼개진 `p`와 `div`가 됩니다.

```html
<!-- 고친 코드 -->
<p>오늘의 공지사항입니다.</p>
<div>중요: 내일은 휴무입니다.</div>
```

### 2. 필수 속성 누락 — alt 없는 img

08편에서 배운 규칙입니다. `img`는 `alt` 속성이 필수입니다. 장식용이라 대체 텍스트가 필요 없다고 판단했더라도 속성 자체를 생략하면 안 되고, `alt=""`(빈 문자열)로 명시해야 합니다.

```html
<!-- 틀린 코드 -->
<img src="logo.png" width="120" height="40" />
```

```
Error: An img element must have an alt attribute, except under certain conditions.
```

이 오류는 브라우저 화면에는 아무 영향이 없습니다. 이미지는 평소처럼 뜹니다. 하지만 스크린 리더 사용자에게는 이 이미지가 무엇인지 알려줄 방법이 아예 없어지고, 이미지 로딩이 실패했을 때 화면에 남는 대체 텍스트도 없습니다.

```html
<!-- 고친 코드: 정보성 이미지라면 -->
<img src="logo.png" alt="소보로 카페 로고" width="120" height="40" />

<!-- 고친 코드: 순수 장식용이라면 -->
<img src="logo.png" alt="" width="120" height="40" />
```

### 3. label 연결 누락

13편에서 배운 규칙입니다. `input`에 `label`이 아예 없거나, `for`와 `id`가 일치하지 않으면 검증기가 잡아냅니다.

```html
<!-- 틀린 코드 -->
<label>이메일</label>
<input type="email" id="이메일" name="email" />
```

```
Warning: The label's for attribute doesn't match any element id.
```

이 경우는 `label`이 있긴 하지만 `for` 속성 자체가 빠져서 어떤 입력과도 연결되지 않은 채 그냥 화면에 떠 있는 텍스트가 됩니다. 클릭해도 입력에 포커스가 가지 않고, 스크린 리더는 이 `label`과 `input`을 별개로 읽습니다.

```html
<!-- 고친 코드 -->
<label for="이메일">이메일</label>
<input type="email" id="이메일" name="email" />
```

### 4. 헤딩 레벨 건너뛰기

18편에서 배운 실무 규칙입니다. 스펙 오류는 아니지만(문서 아웃라인 알고리즘 자체가 스펙에서 제거되었으므로 "건너뛰면 안 된다"는 하드 에러 규칙은 없습니다), 접근성 검사기와 검증기 모두 랭크(rank, 순위)를 건너뛰는 구조를 경고로 잡아냅니다.

```html
<!-- 틀린 코드 -->
<h1>메뉴</h1>
<h4>커피</h4>
```

```
Warning: Heading levels should not be skipped.
```

스크린 리더 사용자는 제목만 골라 들으며 문서를 탐색하는 경우가 많습니다. `h1` 다음에 `h4`가 오면 "`h2`와 `h3`에 있었어야 할 중간 단계 구조가 어디로 갔는가"라는 혼란을 줍니다. 형제 섹션이 아니라 하위 섹션이라면 랭크를 하나씩만 낮춰야 합니다.

```html
<!-- 고친 코드 -->
<h1>메뉴</h1>
<h2>커피</h2>
```

### 5. 시맨틱 오용 — 클릭 이벤트만을 위한 div

17·21편에서 다룬 실무 실수입니다. 검증기가 하드 에러로 잡지는 않지만(문법상 `div`는 어디에나 쓸 수 있으므로), 접근성 관점에서는 치명적인 실수입니다. 클릭할 수 있게 만들 의도라면 `button` 요소를 써야 키보드 포커스·Enter/Space 키 활성화·스크린 리더의 "버튼" 역할 안내가 전부 공짜로 따라옵니다.

```html
<!-- 틀린 코드: 시각적으로는 버튼처럼 보이지만 -->
<div class="button" onclick="submitForm()">제출</div>
```

이 `div`는 마우스 클릭에는 반응하지만, 키보드로 `Tab` 키를 눌러도 포커스가 가지 않고 `Enter` 키를 눌러도 아무 일이 일어나지 않습니다. 스크린 리더는 이것을 그냥 "제출"이라는 텍스트로만 읽어 버튼인지 알 수 없습니다.

```html
<!-- 고친 코드 -->
<button type="button" onclick="submitForm()">제출</button>
```

</Steps>

## 다섯 가지가 섞인 실습기 — 직접 찾아 고치기

아래 `index.html`에는 방금 배운 다섯 가지 오류가 모두 섞여 있습니다. 브라우저 미리보기는 문제없이 뜨는 것을 먼저 확인하세요(오류 복구 덕분입니다). 그다음 코드를 직접 읽으며 다섯 곳을 찾아 고쳐 보세요. 확신이 서지 않으면 코드를 [Nu HTML Checker](https://validator.w3.org/nu/)에 붙여 넣어 실제 메시지를 확인하는 것을 권합니다.

## 검증기 결과를 읽는 순서

검증기가 한 번에 여러 메시지를 쏟아내면 어디부터 봐야 할지 막막할 수 있습니다. 다음 순서로 읽으면 효율이 좋습니다.

| 순서 | 확인할 것 | 이유 |
|------|-----------|------|
| 1 | Error(오류)부터, Warning(경고)은 나중에 | Error는 스펙 위반이 확정된 것이고, Warning은 대개 접근성·관행 권고다 |
| 2 | 메시지에 적힌 줄 번호(line)·칸(column) | 대부분의 메시지가 정확한 위치를 알려준다 |
| 3 | 같은 유형 오류가 여러 번 반복되는지 | 하나를 고치면 같은 실수로 생긴 다른 오류가 한 번에 사라지는 경우가 많다 |
| 4 | 오류를 고친 뒤 반드시 재검증 | 오류 복구 과정에서 트리 구조가 예상과 달라져, 고친 자리 근처에 새 오류가 드러나기도 한다 |

<Callout type="warning">
  **자주 틀리는 점:** 검증기에서 Error가 하나도 없다고 해서 접근성까지 완벽하다는 뜻은 아닙니다(20편에서 배운 원칙입니다). Nu HTML Checker는 **문법과 콘텐츠 모델**을 검사하는 도구이지, 대체 텍스트의 품질이나 색 대비 같은 실질적인 접근성 수준까지 판단하지는 않습니다. "클릭용 div" 실수도 검증기는 하드 에러로 잡지 않는다는 점이 이를 잘 보여줍니다.
</Callout>

## 핵심 정리

- 콘텐츠 모델 위반은 브라우저가 조용히 트리를 다시 짜서 화면은 뜨지만, 의도한 구조와는 달라진다.
- `alt` 누락, `label`-`input` 연결 끊김은 화면에는 티가 안 나고 스크린 리더 사용자에게만 문제가 되므로 검증기 없이는 스스로 발견하기 어렵다.
- 헤딩 레벨 건너뛰기는 하드 에러가 아니라 경고이지만, 제목만 훑어 탐색하는 스크린 리더 사용자에게는 실질적인 장애물이다.
- 클릭 가능한 `div`는 검증기가 잡지 못하는 대표적인 시맨틱 오용이다. 검증 통과가 접근성 완성을 뜻하지 않는다.
- 검증기 결과는 Error부터, 줄 번호를 따라, 고친 뒤 재검증까지가 한 세트다.
