## 왜 필요한가 — CSS 선택자는 늘 "아래쪽"만 봤다

`css_fundamentals`에서 배운 결합자(combinator)들을 떠올려 보세요. 자손 결합자(띄어쓰기), 자식 결합자(`>`), 인접 형제 결합자(`+`), 일반 형제 결합자(`~`) — 전부 **왼쪽에 적은 요소를 기준으로 오른쪽, 즉 뒤에 오거나 아래에 있는 요소**를 고릅니다. CSS 선택자는 문서를 위에서 아래로, 앞에서 뒤로만 훑을 수 있었습니다.

그런데 실무에서 정말 자주 필요한 것은 정반대 방향입니다.

- 폼(form)에서 `input` 하나가 잘못 입력됐을 때, 그 `input`을 감싼 `label`이나 `div.field` 전체에 빨간 테두리를 주고 싶다.
- 카드 안에 이미지가 있을 때만 카드 레이아웃을 다르게 하고 싶다.
- 라디오 버튼 하나가 선택됐을 때, **그 라디오 버튼 자신이 아니라** 앞뒤에 있는 다른 카드의 스타일을 바꾸고 싶다.

이 세 가지 모두 "자식이나 형제의 상태를 보고 부모나 다른 형제를 고른다"는 요구입니다. 오랫동안 CSS만으로는 방법이 없어서, 개발자들은 자바스크립트로 클래스를 붙이거나 떼는 코드를 따로 짰습니다. **`:has()`** 는 이 방향을 CSS 선택자 문법 안으로 끌고 들어온 첫 번째 기능입니다.

> **쉽게 말하면:** `:has()`는 "다음 조건을 만족하는 무언가를 안에 가지고 있는(has) 요소"를 고르는 필터입니다. 부모가 자식을 검사한 뒤 "너, 그런 자식이 있으면 나를 스타일링해"라고 CSS에 처음으로 물어보는 셈입니다.

## 정의와 기본 문법

`:has()`는 **관계 선택자**(relational pseudo-class, 관계 의사 클래스)입니다. 괄호 안에 다른 선택자 목록을 넣으면, "그 선택자 목록 중 하나라도 만족하는 무언가를 자손이나 형제로 가진 요소"를 고릅니다.

```css
/* img를 자손으로 가진 article */
article:has(img) {
  border: 1px solid gray;
}

/* 유효하지 않은 input을 자손으로 가진 label */
label:has(input:invalid) {
  color: crimson;
}

/* h2 바로 다음에 오는 형제 중 p가 있는 h2 */
h2:has(+ p) {
  margin-bottom: 0.25rem;
}
```

괄호 안에는 결합자를 그대로 쓸 수 있습니다. 이 점이 `:has()`의 진짜 힘입니다.

- `:has(img)` — 자손 결합자(공백)와 같은 방향. "어딘가 아래에 img가 있으면"
- `:has(> img)` — 자식 결합자. "바로 아래에 img가 있으면"
- `:has(+ p)` — 인접 형제 결합자. "바로 다음 형제가 p이면"
- `:has(~ p)` — 일반 형제 결합자. "뒤쪽 형제 중 p가 있으면"

괄호를 비워두지 않는 이상, `:has()`가 고르는 대상은 **괄호 앞에 적은 요소 자신**입니다. `label:has(input:invalid)`는 `input:invalid`를 고르는 게 아니라, 그런 `input`을 가진 `label`을 고릅니다.

## 지원 상태 — 널리 사용 가능

`:has()`는 2026년 9월 기준 **널리 사용 가능**(Widely available) 상태입니다. 2023년 12월에 Baseline 신규 진입(newly available)했고, 마지막까지 미지원이던 Firefox가 121 버전에서 합류하면서 2026년 6월 Baseline 전면 사용 가능(widely available)으로 넘어갔습니다. 즉 최신 주요 브라우저(Chrome, Edge, Firefox, Safari) 전부에서 실무에 바로 써도 되는 기능입니다. 다만 아래에서 다룰 **성능** 문제는 지원 여부와 별개로 여전히 신경 써야 합니다.

## `:has()` 이전과 이후 — 실전 패턴 세 가지

### 패턴 1 — 폼 유효성에 따라 부모 꾸미기

`input:invalid`만으로는 `input` 자신만 꾸밀 수 있습니다. 그 `input`을 감싼 `label`이나 필드 전체 컨테이너를 꾸미려면 `:has()`가 필요합니다.

```css
.field:has(input:invalid) {
  border-color: crimson;
  background: color-mix(in oklch, crimson 8%, white);
}

.field:has(input:focus-visible) {
  outline: 2px solid dodgerblue;
}
```

`color-mix()`는 16편에서, `:focus-visible`은 27편에서 자세히 다룹니다. 여기서는 "부모가 자식 상태를 감지해 스타일을 바꾼다"는 구조만 눈여겨보세요.

### 패턴 2 — 형제가 형제를 반응시키기

라디오 버튼으로 카드 하나를 고르면, **선택된 카드가 아니라 다른 카드**의 스타일을 흐리게 하고 싶다고 합시다. 인접 형제 결합자만으로는 "선택 안 된 카드가 선택된 카드를 스타일링"하는 역방향이 안 됩니다. `:has()`를 결합하면 가능합니다.

```css
.card:has(~ .card input:checked) {
  opacity: 0.5;
}
```

### 패턴 3 — "비어 있음"을 감지하기

CSS에는 자식이 없는 요소를 고르는 `:empty`가 있지만, 텍스트 노드까지 완전히 없어야 합니다. 특정 자식이 **없다**는 조건은 `:has()`와 `:not()`을 겹쳐 표현합니다.

```css
ul:not(:has(li)) {
  display: none;
}

ul:not(:has(li)) + p.empty-message {
  display: block;
}
```

## 비교: `:has()` vs 형제 결합자(`+`, `~`)

| 구분 | 형제 결합자 (`+`, `~`) | `:has()` |
|------|------------------------|----------|
| 방향 | 앞에 적은 요소 기준으로 뒤쪽 형제를 고른다 | 괄호 앞 요소를 고르되, 조건은 자손·자식·형제 어디든 검사한다 |
| 부모 선택 | 불가능 — 부모는 항상 자식보다 문서에서 앞에 온다 | 가능 — `article:has(img)`처럼 부모가 자식을 검사한다 |
| 역방향 형제 | 불가능 — 뒤 형제가 앞 형제를 못 본다 | 가능 — `.card:has(~ .card input:checked)` |
| 명시도 | 결합자 자체는 명시도에 기여하지 않는다 | `:has()` 안 선택자 중 **가장 높은 명시도**가 전체 명시도에 더해진다 |

명시도 항목이 중요합니다. `:has()`는 `:is()`(04편에서 다뤘습니다)와 똑같은 규칙을 씁니다 — 괄호 안에서 가장 명시도가 높은 항목이 `:has()` 전체의 명시도가 됩니다. `div:has(#target)`는 `id` 선택자 하나만큼의 명시도(0,1,0,0)를 가지는 셈입니다.

## 브라우저가 실제로 처리하는 방식

일반 선택자는 브라우저가 "요소 하나를 놓고, 그 요소와 조상들만 보면" 매칭 여부를 판단할 수 있습니다. 하지만 `:has()`가 걸린 요소는 **자신의 자손이나 형제 트리 전체가 바뀔 때마다 다시 검사**해야 합니다. 자식 하나에 클래스가 붙거나 떨어질 때마다, 그 자식을 감싼 `:has()` 셀렉터를 쓴 조상들을 브라우저가 역으로 훑어 올라가며 재평가합니다.

주요 브라우저 엔진은 이를 위해 "이 하위 트리를 감시해야 한다"는 표시를 최적화해 두었지만, 감시 범위가 넓을수록 비용이 커지는 구조 자체는 바뀌지 않습니다. 특히 다음 두 가지는 실무에서 반드시 피해야 합니다.

- `body:has(.어떤-클래스)`처럼 **감시 범위가 문서 전체**인 선택자를 자주 바뀌는 상태(hover, 타이핑 중 입력값)와 함께 쓰는 것
- `:has()`를 여러 겹 중첩해 자손 검사 범위를 계속 넓히는 것

실무 기준은 "`:has()`의 검사 범위를 최대한 좁은 컨테이너로 한정한다"입니다. 문서 전체가 아니라 `.field`, `.card`처럼 이미 좁혀둔 컴포넌트 루트에 붙이면 재평가 비용이 그 컴포넌트 안으로만 국한됩니다.

## 접근성 관점

`:has()`는 CSS 선택자일 뿐 DOM(Document Object Model, 문서 객체 모델) 구조나 접근성 트리(accessibility tree)를 전혀 바꾸지 않습니다. 시각적으로 부모의 배경색이나 테두리가 바뀌어도, 스크린 리더(screen reader)는 그 변화를 알지 못합니다. 그래서 `:has()`로 폼 오류를 시각적으로 강조했다면, `aria-invalid="true"`나 오류 메시지를 가리키는 `aria-describedby` 같은 실제 접근성 속성도 함께 자바스크립트나 마크업으로 관리해야 합니다. "빨간 테두리가 보이니 접근성도 챙겼다"는 착각이 이 선택자에서 특히 자주 일어납니다.

## 핵심 정리

- `:has()`는 CSS 역사상 처음으로 "자식이나 형제의 상태를 보고 부모·다른 형제를 고르는" 관계 선택자다.
- 괄호 안에 자손(공백)·자식(`>`)·형제(`+`, `~`) 결합자를 그대로 쓸 수 있고, 고르는 대상은 항상 괄호 앞에 적은 요소다.
- 명시도는 `:is()`와 동일하게 괄호 안에서 가장 높은 항목을 따른다.
- 2026-09 기준 널리 사용 가능(Widely available)이지만, 감시 범위가 넓은 `:has()`는 하위 트리가 바뀔 때마다 재평가 비용이 들어 성능 주의가 필요하다.
- 시각적 스타일만 바꿀 뿐 접근성 트리는 바꾸지 않으므로, 실제 접근성 속성은 별도로 관리해야 한다.
