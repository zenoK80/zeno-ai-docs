<Callout type="info">
  **이번 문서의 목표:** 이 실습을 끝내면 컨테이너 쿼리(container query)로 카드 자신의 폭에 반응하는 내부 레이아웃을 만들고, 서브그리드(subgrid)로 카드마다 제각각인 내용 길이를 한 줄에 맞춰 정렬하고, `@scope`로 그 스타일이 다른 컴포넌트로 새어 나가지 않게 막고, 앵커 포지셔닝(anchor positioning)으로 버튼에 붙는 툴팁을 `@supports` 폴백까지 갖춰 배치할 수 있게 됩니다.
</Callout>

## 이 실습에서 하나로 모으는 것

07·08편에서 컨테이너 쿼리가 "부모 뷰포트가 아니라 부모 컨테이너의 크기"에 반응한다는 것을, 10편에서 서브그리드가 자식 그리드에 부모의 트랙을 그대로 물려준다는 것을, 09편에서 `@scope`가 Shadow DOM(그림자 DOM) 없이 일반 DOM에서 CSS 스타일 범위를 격리한다는 것을, 24편에서 앵커 포지셔닝이 요소를 다른 요소에 기준 삼아 배치한다는 것을 각각 배웠습니다. 이번 실습은 네 기능을 실제 카드 컴포넌트 하나에 전부 얹습니다.

이 조합이 실무에서 흔한 이유는 간단합니다. 카드 컴포넌트는 어디에 놓이느냐(사이드바냐 본문이냐)에 따라 폭이 달라지고, 카드마다 제목·본문 길이가 제각각이라 정렬이 흐트러지기 쉽고, 카드 스타일이 페이지 전역 스타일과 충돌하지 않아야 하며, 카드 위의 "더 보기" 버튼에는 정보를 보여주는 툴팁이 자주 필요합니다. 네 기능이 각각 이 네 가지 문제에 정확히 대응합니다.

## 준비 — 무엇을 이미 안다고 전제하는가

Flexbox·Grid 기본 문법, 미디어 쿼리 기초는 `content/web/css/css_fundamentals`에서 다뤘으므로 반복하지 않습니다. 이 실습은 "그리드 트랙을 어떻게 나누는가"가 아니라 "그리드가 부모 폭과 부모 트랙에 어떻게 반응하고 물려받는가"에 집중합니다.

## 구현 절차

<Steps>

1. **카드 묶음에 컨테이너 자격을 부여한다**: `container-type`으로 카드 묶음(래퍼)이 자신의 자식들에게 크기 기준을 제공하는 컨테이너가 되게 한다.
2. **각 카드에도 독립된 컨테이너 자격을 준다**: 카드 묶음 폭이 아니라 카드 한 장 한 장의 폭에 따라 내부 레이아웃(이미지 위치)이 바뀌도록, 카드 자신도 컨테이너로 선언한다.
3. **카드 묶음에 명시적 행 트랙을 만들고 각 카드가 서브그리드로 물려받게 한다**: 제목·본문·바닥글 세 부분의 높이가 카드마다 다르더라도, 같은 줄에 놓인 카드끼리는 각 부분의 높이가 맞춰지도록 한다.
4. **`@scope`로 카드 스타일의 영향 범위를 카드 안쪽으로 한정한다**: 카드 안에 다시 다른 컴포넌트가 중첩돼도 그 컴포넌트의 스타일까지 덮어쓰지 않도록 한계(limit)를 정한다.
5. **앵커 포지셔닝으로 버튼에 붙는 툴팁을 만들고, 지원하지 않는 브라우저를 위한 `@supports` 폴백을 준비한다**: 핵심 함수는 2026년 1월 Baseline newly available이지만 아직 모든 환경에 퍼지지 않았으므로, 폴백 없이 배포하면 일부 사용자에게 툴팁이 엉뚱한 위치에 뜬다.

</Steps>

## 1·2단계 — 두 겹의 컨테이너

컨테이너 쿼리는 "누가 기준이 되는 상자인가"를 `container-type`으로 선언하는 데서 시작합니다. 이번 실습은 컨테이너를 두 겹으로 씁니다.

```css
/* 바깥 컨테이너 — 카드 묶음 전체의 폭 기준 */
.card-grid {
  container-type: inline-size;
  container-name: card-grid;
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(200px, 1fr));
  gap: 1.25rem;
}

/* 안쪽 컨테이너 — 카드 한 장 한 장의 폭 기준 */
.card {
  container-type: inline-size;
  container-name: card;
}
```

`inline-size`는 "가로 폭만 기준으로 삼는다"는 뜻입니다(논리 속성 관점에서 인라인 축은 가로쓰기에서 가로 방향입니다, 12편). 이렇게 두 겹으로 선언하면 두 종류의 질문에 각각 답할 수 있습니다.

| 질문 | 기준 컨테이너 | 쿼리 예시 |
|------|----------------|-----------|
| 카드 묶음 전체가 좁아졌을 때 열 개수를 줄일까 | card-grid | `@container card-grid (max-width: 480px)` |
| 카드 한 장이 넓어졌을 때 이미지를 옆에 놓을까 | card | `@container card (min-width: 280px)` |

미디어 쿼리는 이 중 첫 번째 질문조차 뷰포트 폭으로만 답할 수 있어서, 같은 카드 컴포넌트를 사이드바(좁음)와 본문(넓음)에 동시에 쓰면 미디어 쿼리 값 하나로는 두 자리를 동시에 만족시킬 수 없습니다. 컨테이너 쿼리는 "이 컴포넌트가 지금 실제로 차지한 폭"을 보기 때문에 두 자리 모두에서 올바르게 반응합니다.

```css
@container card (min-width: 280px) {
  .card-body {
    grid-template-columns: 96px 1fr;
    grid-template-areas: "media title" "media excerpt";
  }
}
```

<Callout type="warning">
  **자주 틀리는 점:** `container-type: inline-size`를 선언한 요소는 그 요소 자신에게는 크기 봉쇄(containment)가 걸려, **자기 자신을 향한** `@container` 쿼리에서 일부 값(예: 콘텐츠 기반 자동 높이)이 예상과 다르게 계산될 수 있습니다. 컨테이너 역할과 쿼리 대상 역할을 같은 요소에 몰아넣기보다, 필요하면 래퍼를 하나 더 둬 분리하는 편이 안전합니다.
</Callout>

## 3단계 — 서브그리드로 카드 내부 정렬 맞추기

카드 묶음 자체를 명시적인 행(row) 그리드로 만들고, 각 카드가 그 행 트랙을 물려받게(subgrid) 하면 카드마다 제목 줄 수가 달라도 본문 시작 위치가 나란히 맞습니다.

```css
.card-grid {
  container-type: inline-size;
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(200px, 1fr));
  grid-auto-rows: auto;
  gap: 1.25rem;
}

.card {
  display: grid;
  grid-row: span 3;
  grid-template-rows: subgrid;
  gap: 0.5rem;
}

.card > .title   { grid-row: 1; }
.card > .excerpt { grid-row: 2; }
.card > .footer  { grid-row: 3; }
```

`grid-row: span 3`은 이 카드가 부모 그리드의 행 트랙 3개를 차지하겠다는 선언이고, `grid-template-rows: subgrid`는 "그 3개 트랙의 실제 크기는 내가 새로 정하지 않고 부모가 정한 크기를 그대로 물려받는다"는 뜻입니다. 그 결과, **같은 줄에 나란히 놓인 카드들끼리** 제목 영역의 높이가 가장 긴 제목에 맞춰 함께 늘어나고, 본문 시작 줄도 나란히 맞습니다.

<Callout type="warning">
  **자주 틀리는 점:** 서브그리드 정렬은 **같은 시각적 줄(row band)에 놓인 카드끼리만** 맞습니다. 줄바꿈으로 다음 줄에 내려간 카드는 그 줄 안에서 독립적으로 다시 맞춰지므로, "모든 카드의 제목 높이가 페이지 전체에서 하나로 통일된다"고 오해하면 안 됩니다.
</Callout>

서브그리드(2023-08 newly available → 2026-03 widely available)는 현재 널리 사용 가능한 상태이므로 별도 폴백 없이 본론 기능으로 써도 됩니다.

## 4단계 — @scope로 카드 스타일 가두기

카드 안에 "더 보기" 같은 별도 위젯이 중첩될 수 있습니다. `.title`처럼 흔한 클래스 이름이 카드 스타일과 위젯 내부 스타일에 동시에 쓰이면 의도치 않게 서로 덮어씁니다. `@scope`는 이 문제를 스코프 루트(scope root)와 한계(limit)로 해결합니다.

```css
@scope (.card) to (.widget) {
  .title { font-weight: 700; color: var(--color-text); }
  .excerpt { color: var(--color-text-muted); }
}
```

`(.card)`가 스코프 루트, `to (.widget)`가 한계입니다. 이 규칙은 `.card` 안에서 시작해 `.widget`을 만나는 지점에서 멈춥니다. 즉 카드 바깥의 `.title`에는 전혀 영향을 주지 않고, 카드 안이라도 `.widget` 내부에 있는 `.title`에는 적용되지 않습니다. `.widget` 내부의 `.title`이 스코프 밖으로 남는 이 현상을 **도넛 스코프**(donut scope)라고 부릅니다 — 가운데 구멍(위젯 내부)만 비어 있는 도넛 모양이라는 비유입니다.

| 구분 | `@scope` | Shadow DOM 기반 캡슐화 |
|------|----------|------------------------|
| 격리 대상 | CSS 스타일 적용 범위만 | DOM 구조 자체와 스타일 모두 |
| 외부 스타일 침투 | 명시적으로 `:host` 등을 쓰지 않는 한 상속은 그대로 통과 | 기본적으로 외부 스타일이 들어오지 않음 |
| 구현 난이도 | 일반 DOM에 클래스만 있으면 됨 | 커스텀 엘리먼트(Custom Element) 정의가 필요 |
| 적합한 상황 | 페이지 안에서 이름 충돌만 막고 싶을 때 | 완전히 독립된 재사용 컴포넌트를 배포할 때 |

Shadow DOM과 Custom Element 자체의 구현 방법은 `javascript/web_component` 과목에서 다룹니다. 이 표의 핵심은 `@scope`가 "가볍게 이름 충돌만 막는 도구"이고, Shadow DOM은 "구조까지 완전히 봉인하는 도구"라는 역할 차이입니다.

## 5단계 — 앵커 포지셔닝 툴팁과 @supports 폴백

앵커 포지셔닝은 한 요소(앵커)에 이름을 붙이고, 다른 요소가 그 이름을 기준으로 자기 위치를 계산하게 하는 기능입니다. 핵심 함수(`anchor-name`, `anchor()`)는 2026년 1월 Baseline newly available에 진입했지만, `position-try`의 뒤집기(flip) 동작 등 일부 세부 기능은 더 늦게 지원되는 브라우저가 있습니다(01편 사실 확인 표). 그래서 이 기능은 반드시 `@supports`로 감싸 지원 여부를 직접 확인한 뒤 써야 합니다.

```css
.info-button {
  position: relative; /* 폴백 기준점 */
}

.tooltip {
  position: absolute;
  inset-block-start: 100%;
  inset-inline-start: 0;
  margin-block-start: 0.25rem;
}

/* 앵커 포지셔닝을 지원하는 브라우저에서만 새 배치 방식으로 덮어쓴다 */
@supports (anchor-name: --info-anchor) {
  .info-button {
    anchor-name: --info-anchor;
  }

  .tooltip {
    position: fixed;
    position-anchor: --info-anchor;
    inset-block-start: anchor(bottom);
    inset-inline-start: anchor(left);
    margin-block-start: 0.25rem;
    position-try-fallbacks: flip-block;
  }
}
```

이 코드가 **점진적 향상**(progressive enhancement)의 정석입니다. `@supports` 블록 밖의 기본 규칙(`position: relative` + `position: absolute`)이 모든 브라우저에서 우선 동작하는 안전한 바닥입니다. `anchor-name` 속성을 실제로 이해하는 브라우저만 `@supports (anchor-name: --info-anchor)` 조건을 만족해 앵커 기반 배치로 **교체**됩니다. `position-try-fallbacks: flip-block`은 툴팁이 화면 아래로 넘칠 것 같으면 자동으로 위쪽에 뒤집어 붙이라는 지시입니다.

<Callout type="warning">
  **자주 틀리는 점:** `@supports not (anchor-name: --info-anchor)`처럼 부정 조건으로 폴백을 따로 감싸는 방식도 가능하지만, 그러면 기본 스타일과 향상 스타일이 서로 다른 블록에 흩어져 유지보수 중 어느 한쪽만 고치는 실수가 잦습니다. 이번 실습처럼 **기본 스타일을 항상 먼저 적고, 지원하는 경우에만 덮어쓰는 순서**가 더 안전합니다.
</Callout>

## 접근성 — 툴팁과 카드에서 놓치기 쉬운 것

툴팁을 여닫는 버튼에는 `aria-expanded` 속성을 붙여, 스크린 리더(screen reader, 화면 낭독 프로그램) 사용자가 지금 툴팁이 펼쳐져 있는지 접혀 있는지 알 수 있게 해야 합니다. 위 예제의 `index.js`가 클릭할 때마다 이 값을 뒤집는 것이 그 역할입니다. 또한 `role="tooltip"`을 붙여 이 요소가 보조 설명이라는 것을 명시적으로 전달했습니다. 키보드만 쓰는 사용자를 위해서는 버튼이 `Tab` 키로 포커스를 받을 수 있어야 하는데, `<button>` 요소는 기본적으로 포커스를 받으므로 별도 처리가 필요 없습니다 — `<div>`에 클릭 이벤트만 붙이는 방식은 키보드 사용자를 배제하므로 피해야 합니다.

카드 그리드 자체에서는 카드 순서가 시각적 순서와 DOM 순서가 일치해야 스크린 리더 탐색이 자연스럽습니다. 컨테이너 쿼리나 서브그리드는 시각적 배치만 바꿀 뿐 DOM 순서를 바꾸지 않으므로 이 예제는 안전하지만, `order` 속성으로 시각 순서를 크게 뒤바꾸면 이 원칙이 깨질 수 있다는 점은 기억해 둘 필요가 있습니다.

## 핵심 정리

- 컨테이너 쿼리는 뷰포트가 아니라 "지정한 컨테이너의 실제 크기"에 반응한다. 카드 묶음 전체와 카드 한 장 각각에 `container-type`을 선언하면 두 층위의 질문에 독립적으로 답할 수 있다.
- 서브그리드는 부모 그리드의 행·열 트랙을 자식이 그대로 물려받게 해, 내용 길이가 제각각인 카드들의 내부 구획을 같은 줄 안에서 맞춘다.
- `@scope`는 스코프 루트와 한계(`to (...)`)로 CSS 적용 범위를 카드 안쪽, 중첩 위젯 바깥으로 한정한다. Shadow DOM처럼 구조 자체를 봉인하지는 않는, 가벼운 이름 충돌 방지 도구다.
- 앵커 포지셔닝은 핵심 기능만 2026년 초 Baseline에 갓 진입했다. `@supports` 조건 안에서만 새 배치 방식으로 덮어쓰고, 조건 밖에는 항상 동작하는 기본 배치를 남겨 두는 순서가 안전한 점진적 향상이다.
