## 왜 폼이 필요한가

지금까지 배운 요소들은 전부 **보여주기** 위한 것이었습니다. 문단(`p`)은 글을 보여주고, 표(`table`)는 데이터를 보여줍니다. 그런데 로그인 화면, 검색창, 회원가입 페이지는 방향이 반대입니다. **사용자가 입력한 내용을 서버로 보내야** 합니다.

자바스크립트 없이 HTML만으로 이 일을 하는 유일한 장치가 **폼**(form, 양식)입니다. 폼은 사용자가 채운 값들을 하나로 묶어 봉투에 담고, 서버 주소로 부치는 장치입니다. 이 편부터 16편까지 네 편에 걸쳐 이 봉투를 어떻게 조립하는지 순서대로 배웁니다. 이 편은 그 봉투의 **틀**(구조)과, 각 입력칸에 이름표를 정확히 붙이는 법(레이블 연결)을 다룹니다.

> **쉽게 말하면:** 폼은 사용자가 쓴 내용을 봉투에 담아 서버로 보내는 장치입니다. 이 편은 봉투를 만드는 법과, 봉투 안 각 칸에 무엇을 적는 칸인지 이름표를 정확히 붙이는 법을 다룹니다.

폼 안에서 값을 자바스크립트로 가로채거나 실시간으로 검증하는 것은 이 과목의 범위 밖입니다. 그 부분은 `javascript/web_apis` 과목이 다루고, 이 과목은 **브라우저가 아무 스크립트 없이도 알아서 해내는 기본 제출 동작**까지만 다룹니다.

## 1. `<form>` — 입력을 담는 컨테이너

### 정의와 콘텐츠 모델

`<form>`은 그 안의 입력 요소들을 하나의 제출 단위로 묶는 컨테이너 요소입니다. 05편에서 배운 콘텐츠 카테고리로 보면 `<form>` 자체는 flow 콘텐츠(문서 흐름 어디에나 놓일 수 있는 콘텐츠)에 속하고, 안에는 다시 flow 콘텐츠를 담을 수 있습니다. 즉 `<form>` 안에 `<p>`, `<label>`, `<input>`, 심지어 `<table>`까지 자유롭게 넣을 수 있습니다.

```html
<form>
  <p>
    <label for="이름입력">이름</label>
    <input type="text" id="이름입력" name="username" />
  </p>
  <button type="submit">보내기</button>
</form>
```

여기서 아직 `action`이나 `method` 속성을 넣지 않았습니다. `<form>`은 이 두 속성이 없어도 동작합니다 — 생략하면 브라우저는 **지금 보고 있는 페이지 주소로, `GET` 방식으로** 제출합니다. 어떤 페이지로 어떻게 보낼지 정확히 통제하는 법은 16편에서 다룹니다.

### 절대 중첩할 수 없다

HTML 명세는 `<form>` 요소 안에 또 다른 `<form>` 요소가 들어가는 것을 콘텐츠 모델 위반으로 규정합니다. 즉 `<form>`의 자손(descendant, 하위 요소) 목록에는 `<form>`이 있을 수 없습니다.

```html
❌ 절대 이렇게 쓰지 않는다
<form action="/search">
  <input type="search" name="q" />
  <form action="/login">
    <!-- 폼 중첩 — 콘텐츠 모델 위반 -->
  </form>
</form>
```

왜 이런 규칙이 있을까요? 사용자가 "제출" 버튼을 눌렀을 때 **어느 봉투에** 그 안의 입력값들을 담아야 하는지가 애매해지기 때문입니다. 중첩을 허용하면 안쪽 폼의 입력이 바깥 폼에도 속하는지, 버튼 하나가 두 봉투 중 어느 쪽을 부치는지 규칙을 세울 수 없습니다. 그래서 스펙은 아예 중첩 자체를 금지해 이 모호함을 원천 차단합니다. 서로 다른 두 개의 폼이 필요하면 형제(sibling) 관계로 나란히 두면 됩니다.

## 2. `<label>` — 이름표를 정확히 붙이기

### 왜 필요한가

`<input>` 옆에 그냥 글자만 써 두면 사람 눈에는 "이게 이름 입력칸이구나"라고 보입니다. 하지만 그 글자와 입력칸 사이에는 **아무 코드상의 연결이 없습니다.** 스크린 리더(screen reader, 화면 낭독기) 사용자는 입력칸에 초점(focus)이 갔을 때 "빈 텍스트 입력란"이라는 말만 듣게 됩니다. 무엇을 입력해야 하는지 알 방법이 없는 것입니다.

`<label>`(레이블, 이름표) 요소는 이 연결을 코드로 명시합니다. 연결이 되면 두 가지 효과가 생깁니다.

1. 스크린 리더가 입력칸에 초점이 갈 때 레이블 텍스트를 함께 읽어줍니다.
2. 레이블 텍스트를 클릭해도 입력칸에 초점이 가거나(텍스트 입력) 체크 상태가 바뀝니다(체크박스·라디오). 작은 체크박스를 정확히 클릭하기 어려운 사용자에게 클릭 가능 영역이 넓어지는 효과입니다.

> **쉽게 말하면:** 레이블은 입력칸에 붙이는 이름표입니다. 이름표와 칸을 코드로 묶어 두면, 이름표를 눌러도 칸이 반응하고 화면을 못 보는 사람도 이름표를 함께 듣습니다.

### 연결하는 두 가지 방법

| 방법 | 코드 형태 | 특징 |
|------|-----------|------|
| 명시적(explicit) 연결 | `<label for="이름입력">`과 `<input id="이름입력">`을 `for`/`id` 값으로 짝짓기 | 레이블과 입력칸이 코드상 떨어져 있어도 연결 가능. `id` 값은 문서 전체에서 유일해야 한다 |
| 암묵적(implicit) 연결 | `<label>` 태그 안에 `<input>`을 통째로 감싸기 | `for`/`id` 없이도 동작. 레이블과 입력칸을 시각적으로 가까이 둘 때 편리 |

```html
<!-- 명시적 연결: for와 id의 값이 정확히 일치해야 한다 -->
<label for="이메일입력">이메일</label>
<input type="email" id="이메일입력" name="email" />

<!-- 암묵적 연결: input을 label 안에 그대로 넣는다 -->
<label>
  이메일
  <input type="email" name="email" />
</label>
```

두 방법 모두 브라우저와 스크린 리더가 동일하게 인식합니다. 다만 명시적 연결은 레이블과 입력칸이 표(`table`)의 서로 다른 셀에 있는 등 마크업 구조상 떨어뜨려야 할 때 필수입니다. 암묵적 연결은 코드가 짧아지지만, 입력칸을 감싸는 텍스트 전부가 클릭 영역이 되므로 레이블 문구가 길면 예상치 못한 넓은 영역이 클릭 가능해질 수 있습니다.

### 자주 틀리는 점 — placeholder는 레이블이 아니다

`<input placeholder="이름을 입력하세요">`처럼 힌트 문구만 넣고 `<label>`을 생략하는 실수가 흔합니다. `placeholder`(플레이스홀더, 자리표시자) 속성은 레이블을 대신하지 못합니다.

- 사용자가 글자를 입력하는 순간 사라져서, 다시 확인할 방법이 없습니다.
- 스크린 리더의 지원이 브라우저·설정마다 일관되지 않아 레이블만큼 신뢰할 수 없습니다.
- 회색의 옅은 글자색으로 표시되는 경우가 많아 명도 대비(contrast)가 낮습니다.

`placeholder`는 "010-1234-5678처럼 입력하세요" 같은 형식 힌트를 **레이블에 더해** 보조로 쓰는 것이지, 레이블의 대체재가 아닙니다.

## 3. `<fieldset>`/`<legend>` — 관련 있는 입력을 묶기

### 왜 필요한가

레이블 하나는 입력 하나를 설명합니다. 하지만 "배송 주소"라는 묶음 안에 우편번호·주소·상세주소 세 칸이 있다면, 그 **묶음 자체**에도 이름이 필요합니다. 라디오 버튼 그룹처럼 "성별을 선택하세요"라는 질문 하나에 여러 개의 개별 입력이 딸린 경우는 더욱 그렇습니다. 이럴 때 쓰는 것이 `<fieldset>`(필드셋, 입력칸 묶음)과 `<legend>`(레전드, 묶음 제목)입니다.

```html
<fieldset>
  <legend>선호하는 연락 방법</legend>
  <label><input type="radio" name="contact" value="email" /> 이메일</label>
  <label><input type="radio" name="contact" value="phone" /> 전화</label>
  <label><input type="radio" name="contact" value="sms" /> 문자</label>
</fieldset>
```

`<legend>`는 반드시 `<fieldset>`의 **첫 번째 자식**이어야 콘텐츠 모델을 만족합니다. 스크린 리더는 사용자가 `<fieldset>` 안의 어느 라디오 버튼에 초점을 두더라도, "선호하는 연락 방법, 라디오 버튼, 이메일" 같은 식으로 `<legend>` 텍스트를 함께 읽어줍니다. `<legend>` 없이 라디오 버튼 세 개만 늘어놓으면, 사용자는 각 버튼의 레이블("이메일", "전화", "문자")만 듣고 이 셋이 애초에 하나의 질문에 대한 답이라는 사실을 알기 어렵습니다.

### `div`+제목과 무엇이 다른가

시각적으로만 보면 `<fieldset>` 대신 `<div>`와 `<h3>`로도 비슷한 모양을 만들 수 있습니다. 차이는 접근성 트리(accessibility tree, 스크린 리더가 읽는 구조)에 있습니다.

| 구성 | 접근성 트리에 나타나는 관계 | 스크린 리더 동작 |
|------|------------------------------|------------------|
| `fieldset`+`legend` | 그룹(group) 역할과 그 이름으로 공식 연결 | 그룹 안 아무 입력에 초점이 가도 그룹 이름을 함께 안내 |
| `div`+`h3` | 시각적으로만 근처에 있을 뿐, 코드상 연결 없음 | 제목과 입력 사이의 관계를 스크린 리더가 알 수 없음 |

라디오 버튼 그룹처럼 "여러 입력이 하나의 질문에 답한다"는 관계를 명확히 알려야 하는 자리에는 `div`+제목이 아니라 반드시 `fieldset`+`legend`를 씁니다.

## 핵심 정리

- `<form>`은 입력 요소를 하나의 제출 단위로 묶는 컨테이너다. `action`/`method`를 생략하면 현재 페이지로 `GET` 제출한다(상세는 16편). `<form>` 안에 또 다른 `<form>`을 넣는 것은 콘텐츠 모델 위반이다.
- `<label>`은 `for`/`id`로 짝짓는 명시적 연결과, `<input>`을 통째로 감싸는 암묵적 연결 두 가지로 입력칸과 이름표를 코드상 연결한다. 연결되면 스크린 리더가 함께 읽어주고 클릭 영역이 넓어진다.
- `placeholder`는 레이블의 대체재가 아니다. 입력 즉시 사라지고 대비가 낮으며 스크린 리더 지원이 일관되지 않는다.
- `<fieldset>`/`<legend>`는 관련 있는 여러 입력(특히 라디오 버튼 그룹)을 하나의 묶음으로 접근성 트리에 알린다. `<legend>`는 `<fieldset>`의 첫 자식이어야 한다.
