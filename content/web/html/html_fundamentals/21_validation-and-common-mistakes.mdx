## 왜 검증이 필요한가 — 브라우저는 관대하다는 것의 함정

지금까지 이 과목에서 배운 규칙들 — `<p>` 안에 `<div>`를 못 넣는다(05편), `<img>`에는 `alt`가 필요하다(08편), `<label>`의 `for`와 입력의 `id`가 연결돼야 한다(13편), `<section>`은 제목이 있어야 의미가 있다(17·18편) — 을 어긴다고 해서 화면이 당장 깨지지는 않습니다. 브라우저는 잘못된 마크업을 최대한 "알아서" 복구해 화면을 띄워 줍니다. 이 복구 동작의 원리는 다음 22편(브라우저는 HTML을 어떻게 파싱하는가)에서 자세히 다룹니다.

문제는 바로 그 관대함입니다. **눈으로 봐서 멀쩡한 페이지가 사실은 스크린 리더 사용자에게는 못 쓰는 페이지이거나, 검색 엔진이 잘못 해석하는 페이지일 수 있습니다.** `alt`가 없는 이미지, `for`가 어긋난 레이블, 제목 레벨을 건너뛴 문서는 화면에는 정상으로 보이지만 접근성 트리(accessibility tree, 보조 기술이 읽는 화면 뒤편의 구조)에서는 구멍투성이입니다.

> **쉽게 말하면:** 브라우저는 "일단 뭐라도 보여주자"는 태도이고, 검증기(validator)는 "규칙대로 썼는지" 깐깐하게 따지는 교정 담당자입니다. 둘 다 필요합니다. 브라우저 화면만 보고 "잘 됐다"고 넘기면, 검증기만 잡아내는 문제들을 영영 모르고 지나갑니다.

## W3C Markup Validation Service에서 Nu HTML Checker로

### 왜 검증기가 두 종류로 갈렸는가

2000년대에 널리 쓰이던 검증기는 `validator.w3.org`의 **W3C Markup Validation Service**였습니다. 이 검증기는 문서 맨 위 `<!doctype>`가 가리키는 **DTD**(Document Type Definition, 문서 타입 정의 — 어떤 태그·속성이 허용되는지 규칙을 기계가 읽을 수 있게 적어둔 명세 파일)를 내려받아, 문서가 그 DTD를 따르는지 검사하는 방식이었습니다. HTML4나 XHTML 시절에는 이 방식이 맞았습니다. 각 doctype이 실제로 DTD 파일을 하나씩 가리켰기 때문입니다.

그런데 04편에서 다뤘듯, HTML5(정확히는 WHATWG Living Standard)의 `<!doctype html>`은 **DTD를 참조하지 않습니다.** 그냥 "이 문서는 표준 모드로 렌더링해 달라"는 신호일 뿐입니다. DTD 자체가 없으니 DTD 기반 검증기로는 최신 HTML을 제대로 검사할 수 없습니다. `<article>`·`<section>` 같은 시맨틱 요소, `data-*` 커스텀 속성, `<video>`의 새 속성들은 옛 DTD에 아예 존재하지 않아 전부 오류로 잘못 표시됩니다.

그래서 등장한 것이 **Nu HTML Checker**(`validator.w3.org/nu`)입니다. DTD 대신 스펙 문서 자체를 코드로 구현한 검사기로, WHATWG Living Standard를 기준으로 삼습니다. **지금 HTML5 문서를 검증할 때 쓸 것은 이 Nu HTML Checker 하나뿐**이라고 기억해 두면 됩니다.

| 구분 | W3C Markup Validation Service (구) | Nu HTML Checker (현행) |
|------|-----------------------------------|------------------------|
| 검사 방식 | doctype이 가리키는 DTD와 대조 | WHATWG 스펙을 직접 구현한 검사기 |
| HTML5 시맨틱 요소(`article`·`section` 등) | 인식하지 못해 오류로 표시될 수 있음 | 정상 인식 |
| `data-*`, ARIA 속성 | DTD에 없어 오류 처리 | 스펙에 정의된 대로 정상 인식 |
| 지금 쓸 것 | 사용하지 않음 (구식 문서 유지보수 시에만 참고) | **이 편에서 다루는 도구** |

### 사용법 — 세 가지 입력 방식

Nu HTML Checker는 사이트에 접속해 세 가지 방법 중 하나로 검사할 문서를 넣습니다.

1. **Address**: 이미 배포된 페이지의 URL을 입력하면 그 페이지를 그대로 가져와 검사합니다.
2. **File Upload**: 로컬에 있는 `.html` 파일을 올립니다.
3. **Text Input**: HTML 코드를 텍스트 상자에 직접 붙여넣습니다. 아직 배포하지 않은 코드 조각을 빠르게 확인할 때 가장 많이 쓰는 방식입니다.

검사 버튼을 누르면 결과 목록이 위에서부터 순서대로 나옵니다. 각 항목은 다음 세 가지를 담고 있습니다.

- **심각도**: `Error`(빨강, 반드시 고쳐야 할 규칙 위반)와 `Warning`(노랑, 권장 사항이나 애매한 지점에 대한 주의) 두 등급입니다.
- **위치**: `Line 12, Column 5` 형태로 문제가 발생한 정확한 줄·칸 번호를 가리킵니다.
- **메시지**: 무엇이 왜 문제인지 스펙 용어로 설명합니다.

<Callout type="warning">
  **자주 틀리는 점:** `Warning`을 "무시해도 되는 것"으로 오해하는 경우가 많습니다. 예를 들어 `<img>`에 `alt`가 아예 없으면 `Error`지만, `alt`는 있는데 내용이 비어 있는 장식용 이미지에 대한 안내는 상황에 따라 `Warning`으로 뜨기도 합니다. 등급은 "고쳐야 하는가"가 아니라 "스펙이 얼마나 단정적으로 금지하는가"를 나타낼 뿐입니다. Warning도 반드시 읽고 판단해야 합니다.
</Callout>

### 메시지 해부하기

Nu HTML Checker의 메시지는 처음 보면 낯설지만 구조가 일정합니다. 예를 하나 뜯어봅니다.

```text
Error: Element "div" not allowed as child of element "p" in this context.
```

- `Element "div"` — 문제가 된 요소.
- `not allowed as child of element "p"` — 어디에 못 들어가는지. `<p>`의 콘텐츠 모델(05편)이 **phrasing content**(구절 콘텐츠 — 문단 안에 흐르는 텍스트 수준의 요소)만 허용하는데, `<div>`는 **flow content**(흐름 콘텐츠 — 블록 구조를 포함하는 더 넓은 범주)에 속해 이 규칙을 어깁니다.
- `in this context` — 항상 예외 없이 금지가 아니라, 지금 이 위치의 맥락에서 금지라는 뜻입니다. 같은 `<div>`라도 `<body>` 바로 아래라면 문제없습니다.

메시지를 읽을 때는 이 세 조각 — **무엇이 / 어디에 / 왜** — 을 분리해서 읽으면 스펙 용어를 몰라도 손 볼 지점을 찾을 수 있습니다.

## 콘텐츠 모델 위반 사례 다시 보기

05편에서 배운 콘텐츠 카테고리(flow·phrasing·sectioning·heading·embedded·interactive·metadata) 규칙은 검증기가 잡아내는 오류의 가장 큰 비중을 차지합니다. 실무에서 반복적으로 나오는 세 가지 패턴을 짚습니다.

| 위반 패턴 | 잘못된 코드 | 검증기 메시지 요지 | 고치는 법 |
|-----------|-------------|---------------------|-----------|
| `<p>` 안에 블록 요소 | `<p>글 <div>상자</div></p>` | `div`는 `p`의 자식으로 허용되지 않음 | `div`를 `p` 밖으로 꺼내거나, `span`처럼 phrasing content인 요소로 바꾼다 |
| 링크 중첩 | `<a href="/a"><a href="/b">글</a></a>` | interactive content는 다른 interactive content를 포함할 수 없음 | 바깥 `<a>`를 없애고 하나만 남긴다 |
| 리스트 항목 밖의 텍스트 | `<ul>안내 문구<li>항목</li></ul>` | `ul`의 자식은 `li`만 허용 | 안내 문구를 `<ul>` 앞의 `<p>`로 옮긴다 |

두 번째 규칙(링크 중첩 금지)은 특히 자주 놓칩니다. `<a>`는 **interactive content**(상호작용 콘텐츠 — 사용자가 직접 클릭·포커스할 수 있는 요소) 카테고리에 속하는데, 이 카테고리에 속한 요소는 서로 겹쳐 담을 수 없습니다. 이유는 접근성과도 직결됩니다. 스크린 리더나 키보드 사용자는 `Tab` 키로 상호작용 요소를 하나씩 옮겨 다니는데, 링크 안에 링크가 있으면 "이 링크를 눌렀을 때 어디로 가는가"가 모호해지고 포커스 순서도 꼬입니다.

## 필수 속성 누락 사례

콘텐츠 모델 위반이 "구조"의 문제라면, 필수 속성 누락은 "정보"의 문제입니다. 태그는 올바른 자리에 있는데, 그 태그가 꼭 들고 있어야 할 정보가 비어 있는 경우입니다.

### `alt` 누락과 빈 `alt`의 차이

08편에서 정리했듯, 이미지가 **정보성**(informative, 내용 이해에 필요한 정보를 담은 이미지)인지 **장식용**(decorative, 빼도 내용 이해에 지장 없는 이미지)인지에 따라 `alt`를 채우는 방식이 다릅니다.

| 상황 | 올바른 마크업 | 검증기·스크린 리더의 반응 |
|------|----------------|---------------------------|
| `alt` 속성 자체가 없음 | `<img src="chart.png">` | Error. 스크린 리더는 대개 파일명을 그대로 읽어 "chart점png"처럼 의미 없는 소리를 냅니다 |
| 정보성 이미지에 빈 `alt` | `<img src="chart.png" alt="">` | 검증기는 통과시키지만, 스크린 리더 사용자는 그래프 내용을 전혀 알 수 없습니다 — 사람이 봐야 잡히는 실수 |
| 장식용 이미지에 빈 `alt` | `<img src="deco.svg" alt="">` | 정상. 스크린 리더가 이 이미지를 건너뜁니다 |
| 정보성 이미지에 알맞은 설명 | `<img src="chart.png" alt="2024년 분기별 매출 증가 추이 막대그래프">` | 정상. 접근성 트리에 의미 있는 이름으로 등록됩니다 |

검증기는 "속성이 있는가 없는가"만 기계적으로 봅니다. **`alt=""`가 정상인지 실수인지는 사람이 판단해야 하는 부분**이라, 검증기 통과와 실제 접근성 확보는 다른 문제라는 점을 여기서도 확인할 수 있습니다.

### `label`과 입력의 연결 끊김

13편에서 배운 `<label>`의 `for`와 입력 요소의 `id`는 문자열이 정확히 일치해야 연결됩니다. 오타 하나로도 연결이 끊깁니다.

```html
<!-- 위반: for="email"인데 id는 "email-input" -->
<label for="email">이메일</label>
<input type="email" id="email-input" name="email" />
```

Nu HTML Checker는 이 경우 "레이블이 폼 컨트롤을 가리키지 못한다"는 취지의 경고를 냅니다. 눈으로 보면 레이블과 입력 칸이 나란히 붙어 있어 문제없어 보이지만, 실제로는 두 가지가 깨집니다. 첫째, 스크린 리더로 입력 칸에 포커스를 옮기면 "이메일"이라는 이름 대신 아무 설명 없이 "편집 텍스트"라고만 읽습니다. 둘째, 레이블 텍스트를 마우스로 클릭해도 입력 칸에 포커스가 가지 않습니다(암묵적 레이블이 아닌 이상, 이 클릭 시 포커스 이동은 `for`/`id` 연결에 의존합니다).

<Callout type="warning">
  **자주 틀리는 점:** `<label>` 안에 입력을 직접 넣는 암묵적 레이블(`<label>이메일 <input ...></label>`)을 쓰면 `for`/`id`가 필요 없다고 알고 있는 경우가 많습니다. 맞는 말이지만, 이 경우에도 **`id`를 생략해도 되는 것이지 폼과 무관해도 된다는 뜻은 아닙니다.** 자바스크립트로 그 입력을 나중에 참조하려면 여전히 `id`나 `name`이 필요합니다(13·14편 참조).
</Callout>

### `input`에 `name` 누락

`name` 속성이 없는 입력은 16편에서 다룬 제출 데이터에 아예 포함되지 않습니다. 검증기는 이를 오류로 잡지 않습니다(문법상 `name`은 필수 속성이 아니기 때문입니다). 하지만 실무에서는 "폼을 제출했는데 서버가 특정 값을 못 받는다"는 버그의 상당수가 이 누락입니다. **검증기가 통과시킨다고 실수가 아닌 것은 아니라는 점**을 보여주는 대표 사례입니다.

## 시맨틱 오용 사례

17·18편에서 배운 시맨틱 sectioning 요소는 문법적으로는 거의 항상 유효하게 쓰이지만("어디에나 넣을 수 있는" 요소들이라), **의미상으로는 잘못 쓰이는 경우**가 많습니다. 이건 검증기가 잡아내지 못하는 영역이라 더 위험합니다.

| 오용 패턴 | 문제 | 올바른 접근 |
|-----------|------|--------------|
| 페이지 안의 모든 상자를 `<section>`으로 감쌈 | `<section>`은 "제목이 있는 독립된 구획"이라는 의미를 갖는데, 제목 없는 상자에 쓰면 스크린 리더가 의미 없는 랜드마크를 무더기로 읽어줌 | 단순히 스타일을 위해 묶는 상자는 `<div>`를 쓴다(17편) |
| `<header>`를 페이지 전체에 하나만 두고, 그 안에 실제 헤더 내용이 아닌 광고를 넣음 | 랜드마크 역할(banner)의 의미가 사용자 기대와 어긋남 | 진짜 사이트 소개·로고·주 내비게이션만 페이지 최상위 `<header>`에 둔다 |
| `<article>` 안에 서로 무관한 콘텐츠 여러 개를 몰아넣음 | `<article>`은 "독립적으로 재배포 가능한 콘텐츠 단위"라는 의미인데, 이 규칙이 깨지면 리더 앱(read-it-later 앱 등)이 콘텐츠를 잘못 추출함 | 콘텐츠 단위마다 `<article>`을 따로 둔다 |
| 표 형태 데이터가 아닌 것을 `<table>`로 감쌈(레이아웃 목적) | 스크린 리더가 표로 읽어 "1행 1열, 2행 1열…"처럼 불필요한 안내를 함 — 10편에서 다룬 폐기된 관행 | 레이아웃은 CSS(Flexbox·Grid, css_fundamentals 과목 참조)로 처리하고 `<table>`은 실제 표 데이터에만 쓴다 |

이 표의 공통점은, **문법적으로는 전부 유효한 HTML이라 Nu HTML Checker가 오류로 잡지 않는다**는 것입니다. 검증기는 "허용된 자리에 있는가"만 확인하지, "그 의미가 실제 내용과 맞는가"는 판단하지 못합니다. 시맨틱 오용을 잡아내는 방법은 검증기가 아니라 **"이 요소의 이름을 스크린 리더 사용자가 들었을 때, 실제 내용과 기대가 일치하는가"를 스스로 되묻는 것**입니다.

## 핵심 정리

- HTML5 문서는 DTD가 없으므로 구식 `validator.w3.org`가 아니라 **Nu HTML Checker**(`validator.w3.org/nu`)로 검증한다.
- 검증기 메시지는 "무엇이 / 어디에 / 왜"라는 세 조각으로 나눠 읽으면 스펙 용어를 몰라도 손 볼 지점을 찾을 수 있다.
- 콘텐츠 모델 위반(구조), 필수 속성 누락(정보), 시맨틱 오용(의미) 은 서로 다른 종류의 실수다. 검증기는 앞의 두 가지 상당 부분을 잡아내지만, 시맨틱 오용은 문법상 유효한 경우가 많아 사람이 직접 판단해야 한다.
- `alt=""`, `for`/`id` 일치, `name` 존재 여부는 검증기 통과와 별개로 사람이 다시 확인해야 하는 지점이다.
- Warning은 무시해도 되는 표시가 아니다 — 등급은 "고쳐야 하는가"가 아니라 스펙이 얼마나 단정적으로 금지하는지를 나타낼 뿐이다.
