## 왜 이 편을 본론보다 먼저 두는가

01편에서 Baseline이라는 지표가 있다는 것을 배웠습니다. 그런데 이 과목의 본론 24편 중 상당수 — `details name` 아코디언(07편), `hidden="until-found"`(09편), Customizable `<select>`(26편) — 는 브라우저마다 지원 시점이 갈리는 기능을 다룹니다. 그때마다 "지원 상태를 어떻게 확인하는지"부터 설명하면 같은 절차가 계속 반복됩니다. 그래서 이 절차를 먼저 한 번에 배우고, 본론에서는 "02편에서 배운 방법대로 확인하면"이라고만 짚고 넘어갑니다.

## MDN 페이지에서 호환성 정보 찾는 법

<Steps>

### 1단계 — 기능 이름으로 MDN 페이지를 찾는다

예를 들어 `dialog` 요소가 궁금하면 `MDN dialog element`로 검색해 `developer.mozilla.org`의 레퍼런스(reference) 페이지로 들어갑니다.

### 2단계 — 페이지 상단의 Baseline 배지를 확인한다

MDN 페이지 상단에는 초록색(널리 사용 가능) 또는 노란색(새로 사용 가능) 배지가 붙어 있습니다. 이 배지에 마우스를 올리거나 클릭하면 "이 기능이 브라우저에 언제부터 들어왔는지" 짧은 설명이 나옵니다. 배지가 아예 없거나 회색으로 "Limited availability(제한적 사용 가능)"라고 되어 있으면 아직 Baseline에 도달하지 못한 것입니다.

### 3단계 — 페이지 맨 아래 "Browser compatibility(브라우저 호환성)" 표를 연다

배지는 요약일 뿐이고, 실제 판단 근거는 이 표입니다. 표는 보통 이런 열로 구성됩니다.

</Steps>

| 열 | 의미 |
|------|------|
| Feature(기능) | 요소 전체가 아니라 그 안의 세부 기능(예: `dialog` 요소 안의 `showModal()` 메서드, `close` 이벤트 등) 단위로 행이 나뉜다 |
| Chrome / Edge / Firefox / Safari | 각 데스크톱 브라우저에서 지원을 시작한 최소 버전 번호 |
| Chrome Android / Firefox for Android / Safari on iOS | 모바일 브라우저별 최소 버전 번호 |
| 각주(footnote) 번호 | 셀 옆에 작은 숫자가 붙어 있으면, 표 아래에 "이 버전에서는 플래그를 켜야 한다" 같은 단서가 달려 있다는 뜻 |

<Callout type="warning">
  **자주 틀리는 점:** 표의 맨 위 행(요소 전체)만 보고 "지원된다"고 판단하는 경우가 많습니다. 실제로는 요소는 오래전부터 있었지만 그 안의 특정 메서드나 속성만 최근에 추가된 경우가 흔합니다. 예를 들어 `dialog` 요소 자체는 오래됐지만 `closedby` 속성처럼 그 안의 세부 기능은 훨씬 늦게 들어온 경우가 있습니다. **행 단위로** 확인해야 합니다.
</Callout>

## Baseline 배지 세 단계와 실무 판단 기준

01편에서 정의한 세 단계를 실무 관점에서 다시 정리하면 다음과 같습니다.

| 배지 상태 | 실무에서의 의미 | 권장 행동 |
|------|------|------|
| 널리 사용 가능(Widely available) | 지원 시작 후 30개월이 지나 구형 브라우저 사용자 비율이 낮다고 볼 수 있다 | 폴백(fallback, 대체 수단) 없이 기본기로 바로 사용 |
| 최신 브라우저 기준(Newly available) | 최신 버전에는 다 있지만 구형 사용자가 아직 남아있을 수 있다 | 사용은 하되 `@supports`나 feature detection으로 감지해 폴백을 함께 제공 |
| 제한적·실험적 | 일부 브라우저에만 있거나 플래그 뒤에 있다 | 프로덕션 핵심 경로에는 쓰지 않고, 점진적 향상의 "덤" 정도로만 사용 |

이 세 단계 문구("널리 사용 가능", "최신 브라우저 기준", "제한적·실험적")는 이 과목 전체에서 통일해서 씁니다. 새 기능이 등장할 때마다 이 세 표현 중 하나가 함께 붙어 있을 것입니다.

## `@supports`로 CSS 기능 감지하기

**`@supports`**는 CSS 안에서 "브라우저가 이 속성이나 값을 이해하는가"를 직접 물어보는 규칙(at-rule)입니다. 이름 그대로 "지원하는가"(supports)를 묻습니다. 지원하면 그 블록 안의 스타일이 적용되고, 지원하지 않으면 무시됩니다.

```css
/* 기본값 — 모든 브라우저가 이해하는 안전한 스타일 */
.card {
  display: block;
}

/* CSS Grid의 최신 서브그리드 기능을 지원하는 브라우저에서만 덮어쓴다 */
@supports (grid-template-columns: subgrid) {
  .card {
    display: grid;
    grid-template-columns: subgrid;
  }
}
```

이 방식이 강력한 이유는 **버전 번호를 아예 몰라도 된다**는 점입니다. "크롬 120 이상이면"이라고 브라우저 이름과 버전을 직접 나열하는 대신, "이 속성을 이해하면"이라고 기능 자체를 물어보므로, 나중에 다른 브라우저가 지원을 추가해도 코드를 고칠 필요가 없습니다.

## 자바스크립트로 기능 감지하기

CSS가 아니라 자바스크립트 API의 지원 여부를 확인할 때는 **feature detection**(기능 감지) 패턴을 씁니다. 핵심 원리는 하나입니다. **실제로 그 이름의 속성이나 메서드가 객체 위에 존재하는지 직접 물어본다.**

아래 실습기에서 popover 관련 기능이 현재 이 브라우저에 있는지 직접 확인해 보세요. 이 방식은 05편에서 popover를 실제로 쓸 때도 그대로 재사용합니다.

<CodePlayground
  template="vanilla"
  activeFile="/index.js"
  showConsole
  label="자바스크립트 feature detection 패턴"
  files={{
    '/index.html': `<div id="app">
  <p>콘솔에서 이 브라우저의 지원 여부를 확인하세요.</p>
</div>`,
    '/index.js': `// 패턴 1: HTMLElement 프로토타입에 속성이 있는지 직접 확인
const popover지원 = "popover" in HTMLElement.prototype;
console.log("popover 속성 지원?", popover지원);

// 패턴 2: 요소를 하나 만들어서 메서드가 있는지 확인
const 임시dialog = document.createElement("dialog");
const showModal지원 = typeof 임시dialog.showModal === "function";
console.log("dialog.showModal() 지원?", showModal지원);

// 패턴 3: 감지 결과에 따라 분기 처리(점진적 향상의 실제 코드 형태)
if (popover지원) {
  console.log("→ popover 속성으로 가벼운 오버레이를 구현합니다");
} else {
  console.log("→ 대체 수단(직접 만든 오버레이)으로 폴백합니다");
}`,
  }}
/>

이 코드는 "브라우저에 물어보고, 답에 따라 분기한다"는 한 가지 원리만 반복합니다. 버전 번호 비교(`navigator.userAgent`를 파싱해 브라우저 이름과 버전을 알아내는 방식)는 쓰지 않습니다. 사용자 에이전트 문자열은 브라우저마다 형식이 다르고 위조되기도 쉬워 신뢰할 수 없는 정보이기 때문입니다.

<Callout type="warning">
  **자주 틀리는 점:** `navigator.userAgent.includes("Chrome")` 같은 방식으로 브라우저를 구분하려는 시도는 지양해야 합니다. 같은 이름의 브라우저라도 버전마다 기능 지원이 다르고, 사용자 에이전트 문자열은 다른 브라우저를 흉내 내는 경우도 흔해 정확하지 않습니다. 항상 "그 기능 자체가 있는지"를 직접 물어보세요.
</Callout>

## "작성 시점"과 "읽는 시점"이 다를 수 있다는 감각

이 과목의 모든 지원 상태 표기에는 "2026년 9월 기준"이라는 꼬리표가 붙어 있습니다. 여러분이 이 문서를 읽는 시점이 그보다 나중이라면, 다음 두 가지 방향으로 상황이 바뀌어 있을 수 있습니다.

- **좋아지는 방향**: "제한적·실험적"이라고 적힌 기능(예: 26편의 Customizable `<select>`)이 그 사이 Baseline에 도달했을 수 있습니다.
- **더 널리 퍼지는 방향**: "최신 브라우저 기준"이라고 적힌 기능이 30개월을 채워 "널리 사용 가능"으로 승격했을 수 있습니다.

반대로 명세 자체가 바뀌는(문법이 조정되는) 경우는 드물지만 아예 없지는 않으므로, 실무에 적용하기 전에는 항상 MDN 페이지를 그 시점에 다시 열어 확인하는 습관을 들이는 것이 좋습니다.

> **쉽게 말하면:** 이 책은 "2026년 9월에 찍은 사진"입니다. 사진이 찍힌 뒤에도 풍경(브라우저 지원 현황)은 계속 바뀝니다. 중요한 결정을 내리기 전에는 창밖을 다시 내다보세요.

## 핵심 정리

- MDN 페이지 상단의 Baseline 배지로 큰 그림을, 하단의 브라우저 호환성 표로 세부 기능 단위의 지원 버전을 확인한다.
- 호환성 표는 요소 전체가 아니라 세부 기능(메서드·이벤트·속성) 단위 행으로 나뉘므로 행 단위로 확인해야 한다.
- `@supports`는 CSS 속성·값의 지원 여부를 버전 번호 없이 기능 자체로 물어본다.
- 자바스크립트 feature detection은 `"속성명" in 객체` 또는 `typeof 메서드 === "function"` 패턴으로 실제 존재 여부를 확인하며, 사용자 에이전트 문자열 파싱보다 신뢰도가 높다.
- 이 과목의 모든 지원 상태 표기는 2026년 9월 기준이며, 실무 적용 전 다시 확인하는 습관이 필요하다.
