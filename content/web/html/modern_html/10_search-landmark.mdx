  **이번 문서의 목표:** 이 문서를 다 읽으면 페이지 안의 검색 UI를 `<search>`로 감싸야 하는 이유를 스크린 리더 사용자의 관점에서 설명하고, `<form>` 하나로 충분한 경우와 `<search>`가 추가로 필요한 경우를 구분할 수 있게 됩니다.
</Callout>

## 왜 필요한가 — "검색창이 어디 있지?"

큰 사이트를 스크린 리더(screen reader, 화면 낭독기)로 탐색하는 사용자를 떠올려 보세요. 이 사용자는 마우스로 화면을 훑어볼 수 없으므로, 페이지의 큰 구획(header, nav, main 등 — 자세한 시맨틱 sectioning 요소는 `/web/html/html_fundamentals/17_semantic-sectioning-elements` 참조)을 순서대로 건너뛰며 원하는 부분을 찾습니다. 이때 "검색창으로 바로 가고 싶다"는 요구는 매우 흔합니다.

문제는 지금까지 검색 UI를 감싸는 표준화된 시맨틱 요소가 없었다는 점입니다. 개발자들은 검색 폼을 그냥 `<div>`나 `<form>`으로만 감쌌고, 접근성을 신경 쓰는 팀만 `role="search"`라는 ARIA(Accessible Rich Internet Applications, 접근 가능한 리치 인터넷 애플리케이션) 속성을 수동으로 붙였습니다. 이 관행이 있는 사이트와 없는 사이트가 뒤섞여 있었고, "검색"이라는 아주 흔한 UI 패턴치고는 표준 지원이 늦게 들어온 편입니다. `<search>` 요소는 이 구멍을 표준 HTML 태그로 메웁니다.

## 정의 — search는 무엇을 표시하는가

> **쉽게 말하면:** `<search>`는 "여기부터 여기까지가 검색 관련 UI다"라고 브라우저와 보조 기술(assistive technology)에 알려주는 투명한 포장지입니다.

`<search>`는 검색 입력, 검색 관련 옵션(카테고리 선택, 필터), 검색 버튼을 감싸는 sectioning 요소입니다. 자신만의 시각적 스타일을 강제하지 않는다는 점에서 `<div>`와 비슷하지만, 접근성 트리(accessibility tree, 보조 기술이 읽는 요소 구조)에서는 **검색 랜드마크**(landmark, 표지)라는 특별한 역할로 노출됩니다.

```html
<search>
  <form action="/results" method="get">
    <label for="검색어">검색어</label>
    <input type="search" id="검색어" name="q" />
    <button type="submit">검색</button>
  </form>
</search>
```

이 마크업이 브라우저에서 어떻게 처리되는지 접근성 트리 관점으로 정리하면 다음과 같습니다.

| 요소 | 접근성 트리에서의 역할(role) | 스크린 리더 사용자가 얻는 것 |
|------|-------------------------------|-------------------------------|
| `<search>` | `search` 랜드마크 | "검색 랜드마크로 이동" 단축키로 바로 도달 |
| `<form>` (search 없이 단독 사용 시) | `form` 랜드마크(레이블이 있을 때만) | 랜드마크 목록에 뜨지만 "검색"이라는 의미는 없음 |
| `<input type="search">` | `searchbox` | 일반 텍스트 입력과 구분되는 검색 전용 컨트롤로 인식 |

## role="search"와의 관계

`<search>`가 등장하기 전, 접근성을 신경 쓰는 개발자들은 이미 `<div role="search">` 또는 `<form role="search">`처럼 ARIA 속성으로 같은 효과를 냈습니다. `<search>` 요소는 이 관행을 **네이티브 HTML로 승격**한 것입니다. 즉 `<search>`를 쓰면 `role="search"`를 따로 붙이지 않아도 브라우저가 암묵적으로 같은 역할을 부여합니다.

<Callout type="warning">
  **자주 틀리는 점:** `<search role="search">`처럼 역할을 중복해서 명시할 필요는 없습니다. 이미 시맨틱 요소 자체가 암묵적 역할(implicit role, 요소가 기본으로 갖는 접근성 역할)을 가지고 있으므로, 같은 역할을 ARIA로 다시 써주는 것은 불필요한 중복입니다. ARIA를 다루는 일반 원칙 — "네이티브 요소로 표현할 수 있으면 ARIA를 쓰지 않는다" — 이 여기서도 그대로 적용됩니다.
</Callout>

## 언제 form 대신 search를 쓰는가

`<form>`과 `<search>`는 서로 대체하는 관계가 아니라 **겹쳐 쓰는** 관계입니다. `<search>`는 "이 구획의 목적이 검색이다"를 알리고, `<form>`은 그 안에서 실제로 데이터를 제출하는 방법(전통적인 폼 구조와 제출 방식은 `/web/html/html_fundamentals/13_forms-structure-and-labels` 참조)을 담당합니다. 위 예시 코드처럼 `<search>` 안에 `<form>`을 넣는 것이 표준적인 조합입니다.

`<search>`를 붙일지 판단하는 기준은 단순합니다. **그 UI가 사용자에게 "검색"으로 인식되는가**입니다.

- 사이트 전체를 검색하는 헤더의 검색창 → `<search>`로 감쌉니다.
- 상품 목록 페이지의 "필터: 가격, 카테고리" 같은 정렬·필터 UI만 있고 텍스트 검색 입력이 없다면 → 검색이 아니라 필터링이므로 `<search>`를 붙이지 않습니다.
- 뉴스레터 구독처럼 텍스트 입력이 있어도 목적이 검색이 아니라 등록이라면 → `<search>`가 아니라 일반 `<form>`으로 충분합니다.
- 자유 텍스트 검색과 필터가 함께 있는 검색 UI(예: 검색어 입력 + 카테고리 드롭다운) → 전체를 `<search>`로 감쌉니다. 검색 결과를 좁히는 목적이라면 필터도 검색 랜드마크 안에 포함됩니다.

`<search>`는 페이지당 한 번만 쓸 수 있는 요소가 아닙니다. 헤더의 사이트 전체 검색과, 본문 안의 "이 표 안에서 검색" 같은 지역 검색이 공존한다면 각각 `<search>`로 감싸도 됩니다. 다만 접근성 트리에 검색 랜드마크가 여러 개 뜨므로, 서로 구분되도록 `aria-label`(예: `aria-label="사이트 전체 검색"`, `aria-label="표 내 검색"`)로 레이블을 달아주는 것이 좋습니다.

## 지원 상태

`<search>` 요소는 2026-09 시점 기준 **최신 브라우저 기준**으로 다뤄야 합니다. Baseline(베이스라인, 주요 브라우저 전반의 지원 상태 지표 — 읽는 법은 `/web/html/modern_html/02_reading-baseline-and-compat` 참조)에서 2023년 10월 무렵 "새로 사용 가능(Newly available)"으로 분류되었고, 이후 대부분의 최신 브라우저에서 사용할 수 있게 되었습니다. 다만 이 문서를 읽는 시점의 정확한 지원 범위는 MDN 호환성 표에서 다시 확인해야 합니다.

지원하지 않는 아주 오래된 브라우저에서는 `<search>`가 알려지지 않은 요소로 취급되어, HTML의 알려지지 않은 태그 처리 규칙에 따라 `<span>`처럼 동작합니다. 시각적으로는 문제가 거의 없지만(원래도 `<search>`는 자체 스타일이 없으므로) 검색 랜드마크로서의 접근성 이점만 사라집니다. 그래서 검색 UI에는 `<search>` 요소 자체 외에도, `<label>`로 입력에 이름을 붙이는 기본기(위 예시의 `<label for="검색어">`)를 항상 함께 갖추는 것이 이중 안전망이 됩니다.

## 핵심 정리

- `<search>`는 검색 관련 UI를 감싸는 sectioning 요소로, 접근성 트리에서 `search` 랜드마크로 노출된다.
- 시각적 스타일은 강제하지 않는다는 점에서 `<div>`와 비슷하지만, 의미상으로는 검색 UI라는 표지 역할을 한다.
- `<search>`가 이미 암묵적으로 `role="search"`를 부여하므로, ARIA `role="search"`를 따로 중복해서 붙이지 않는다.
- `<search>`와 `<form>`은 겹쳐 쓰는 관계다. `<search>`는 목적을, `<form>`은 제출 방식을 담당한다.
- 판단 기준은 "이 UI가 검색으로 인식되는가"다. 단순 필터·정렬이나 검색과 무관한 입력 폼에는 붙이지 않는다.
- Baseline Newly available(2023-10~) 상태이므로 "최신 브라우저 기준"으로 표기하고, 미지원 브라우저에서는 `<span>`처럼 취급되어 접근성 이점만 조용히 빠진다.
