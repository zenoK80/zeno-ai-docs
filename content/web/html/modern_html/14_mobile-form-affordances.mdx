<Callout type="info">
  **이번 문서의 목표:** 이 문서를 다 읽으면 `type`과 `inputmode`가 서로 다른 역할을 한다는 것을 설명하고, 숫자만 입력받아야 하지만 `type="number"`를 쓸 수 없는 상황에서 올바른 조합을 고르고, `enterkeyhint`로 모바일 가상 키보드의 엔터키 라벨까지 맞출 수 있습니다.
</Callout>

## 왜 `type`만으로는 부족한가

12편에서 `type="email"`·`type="tel"` 같은 새 입력 타입이 모바일에서 알맞은 가상 키보드를 띄워준다고 배웠습니다. 그런데 실무에서는 이런 상황이 자주 생깁니다.

- 우편번호나 카드 번호처럼 **자릿수를 앞에 0이 붙을 수 있는 숫자열**은 `type="number"`로 받으면 안 됩니다. 브라우저가 스핀 버튼(위아래 화살표)을 붙이고, 붙여넣은 값에 알파벳이 섞이면 값 자체가 사라지는 등 예상치 못한 부작용이 있습니다.
- 검색창처럼 `type="search"`를 쓰지 않고 `type="text"`를 유지하고 싶지만, 숫자 키패드를 띄우고 싶은 경우도 있습니다.

즉 "이 값이 의미상 무엇인가"(그래서 브라우저가 형식 검증까지 하게 할지)와 "가상 키보드가 어떤 배열로 뜰지"는 **서로 다른 축**입니다. 이 두 번째 축을 담당하는 것이 **`inputmode`**입니다.

> **쉽게 말하면:** `type`은 "이 칸의 값이 무엇인지 브라우저에게 알려주는 신분증"이고, `inputmode`는 "화면에 뜰 키보드 배열만 따로 지정하는 리모컨"입니다. 신분증은 그대로 두고 리모컨만 바꿀 수 있습니다.

## 1. `inputmode`가 하는 일

### 정의

`inputmode` 전역 속성은 값 자체의 형식 검증에는 관여하지 않고, **가상 키보드(virtual keyboard)의 레이아웃**만 브라우저에게 힌트로 알려줍니다. 값은 여전히 일반 문자열로 취급되며, `required`나 `pattern` 같은 다른 속성과 자유롭게 함께 쓸 수 있습니다.

| 값 | 뜨는 키보드 | 대표 용도 |
|---|---|---|
| `text` (기본값) | 일반 문자 키보드 | 이름, 주소 등 |
| `numeric` | 숫자 전용 키패드(0–9) | 우편번호, PIN, 카드 유효기간 |
| `decimal` | 숫자 + 소수점 키패드 | 가격, 몸무게처럼 소수를 포함하는 값 |
| `tel` | 전화번호용 키패드(숫자, `*`, `#`) | 전화번호 |
| `email` | `@`, `.`이 강조된 키보드 | 이메일 |
| `url` | `/`, `.`이 강조된 키보드 | URL |
| `search` | 일반 키보드 + 엔터키가 "검색"으로 표시 | 검색창 |
| `none` | 가상 키보드를 아예 띄우지 않음 | 커스텀 키패드를 직접 그리는 경우 |

### `type`과 `inputmode`의 관계

`type="number"`는 값의 **형식 자체**를 숫자로 강제하고, 브라우저가 스핀 버튼을 붙이고, `valueAsNumber`로 숫자 타입을 바로 꺼낼 수 있게 해줍니다. 반면 우편번호처럼 "보기엔 숫자지만 계산에는 안 쓰고, 0으로 시작할 수도 있는 값"은 형식은 문자열로 두고 키보드만 숫자로 띄우는 것이 맞습니다. 이럴 때 쓰는 조합이 다음과 같습니다.

```html
<!-- ❌ 0으로 시작하는 우편번호가 스핀 버튼과 함께 이상하게 동작할 수 있다 -->
<input type="number" name="postal">

<!-- ✅ 문자열로 값을 유지하면서 숫자 키패드만 띄운다 -->
<input type="text" inputmode="numeric" pattern="[0-9]*" name="postal">
```

| 상황 | 권장 조합 |
|---|---|
| 값 자체가 진짜 숫자 연산 대상(수량, 나이 등) | `type="number"` |
| 값이 숫자처럼 보이지만 계산하지 않는 식별자(우편번호, 카드번호) | `type="text" inputmode="numeric"` |
| 가격처럼 소수점이 필요한 숫자 입력 | `type="text" inputmode="decimal"` 또는 상황에 따라 `type="number" step="0.01"` |
| 전화번호 | `type="tel"` (이미 전화 키패드가 딸려 옴, `inputmode` 생략 가능) |

<Callout type="warning">
  **자주 틀리는 점:** `inputmode="numeric"`만 붙이고 `pattern`을 빼먹으면, 키보드는 숫자로 뜨지만 데스크톱 키보드나 붙여넣기로 문자가 섞여 들어오는 것을 브라우저가 막지 못합니다. `inputmode`는 **키보드 힌트일 뿐 값 검증이 아니므로**, 실제 형식을 강제하려면 13편의 Constraint Validation API나 `pattern`을 반드시 함께 씁니다.
</Callout>

## 2. `enterkeyhint` — 엔터키에 라벨 붙이기

### 왜 필요한가

모바일 가상 키보드의 엔터(줄바꿈) 키는 상황에 따라 "다음", "완료", "검색", "이동" 등 다른 동작을 할 수 있는데, 기본값은 항상 밋밋한 줄바꿈 화살표입니다. 사용자가 "이 버튼을 누르면 무슨 일이 일어나는지" 미리 알 수 있게 라벨을 바꿔주는 속성이 **`enterkeyhint`**입니다.

### 값과 의미

| 값 | 키보드에 표시되는 의미 | 사용 예 |
|---|---|---|
| `enter` (기본값) | 일반 줄바꿈 | 여러 줄 입력(`textarea`) |
| `done` | 완료 | 마지막 입력 필드 |
| `go` | 이동 | 주소창처럼 바로 이동하는 입력 |
| `next` | 다음 | 여러 단계 폼에서 다음 필드로 |
| `previous` | 이전 | 이전 필드로 되돌아가기 |
| `search` | 검색 | 검색창 |
| `send` | 보내기 | 메시지 입력창 |

```html
<form>
  <label>이름 <input type="text" enterkeyhint="next"></label>
  <label>이메일 <input type="email" enterkeyhint="next"></label>
  <label>메모 <input type="text" enterkeyhint="done"></label>
</form>
```

`enterkeyhint`는 실제로 포커스를 다음 필드로 옮기거나 폼을 제출하는 **동작 자체를 만들어주지는 않습니다.** 단지 키보드에 뜨는 라벨만 바꿉니다. `next`라고 표시해 놓고 실제로 눌렀을 때 다음 필드로 넘어가게 하려면, `keydown` 이벤트를 직접 듣고 `focus()`를 호출하는 자바스크립트를 붙여야 합니다.

<Callout type="warning">
  **자주 틀리는 점:** `enterkeyhint="done"`을 붙이면 엔터를 눌렀을 때 자동으로 폼이 제출된다고 착각하기 쉽습니다. 라벨이 "완료"로 바뀔 뿐이며, 실제 제출은 `form`의 `submit` 이벤트(또는 `type="submit"` 버튼)가 그대로 담당합니다. 라벨과 동작을 일치시키는 책임은 개발자에게 있습니다.
</Callout>

## 3. 모바일 폼 UX 체크리스트

지금까지의 내용과 12편의 입력 타입, 13편의 검증 API를 모바일 관점에서 한데 모으면 다음과 같은 점검표가 됩니다.

1. **의미에 맞는 `type`을 우선 선택**했는가 — `email`·`tel`·`url` 등은 `inputmode`를 따로 지정할 필요 없이 알맞은 키보드가 자동으로 뜹니다.
2. **숫자처럼 보이지만 계산 대상이 아닌 값**에는 `type="number"` 대신 `type="text" inputmode="numeric"` + `pattern`을 썼는가.
3. **여러 필드를 잇는 폼**에서 `enterkeyhint`의 라벨과 실제 포커스 이동/제출 동작이 일치하는가.
4. `autofocus`를 남용해 화면을 열자마자 키보드가 튀어 오르게 만들지 않았는가 — 특히 첫 화면 진입 시 사용자가 준비되지 않은 채로 키보드가 뜨면 오히려 방해가 됩니다.
5. 접근성 관점에서, `inputmode`나 `enterkeyhint`가 스크린 리더 사용자에게는 거의 영향을 주지 않으므로 — 이 속성들만으로 접근성이 확보됐다고 착각하지 않고, `label` 연결과 오류 메시지 안내(13편)는 별도로 챙겨야 합니다.

## 핵심 정리

- `type`은 값의 형식(검증 대상)을 정하고, `inputmode`는 가상 키보드의 레이아웃만 바꾼다. 둘은 독립적인 축이며 함께 쓸 수 있다.
- 숫자처럼 보이지만 연산 대상이 아닌 식별자(우편번호 등)는 `type="text" inputmode="numeric"` + `pattern` 조합을 쓴다.
- `inputmode`는 값 검증을 하지 않으므로, 형식을 강제하려면 `pattern`이나 13편의 Constraint Validation API를 함께 써야 한다.
- `enterkeyhint`는 엔터키의 라벨만 바꾸며, 실제 포커스 이동이나 제출 동작은 별도의 자바스크립트나 `submit` 이벤트가 담당한다.
- 가상 키보드의 실제 모양은 코드만으로 확인할 수 없으므로, 배포 전 실제 모바일 기기나 브라우저 개발자 도구의 기기 에뮬레이션으로 반드시 확인한다.
