<Callout type="info">
  **이번 문서의 목표:** 이 문서를 다 읽으면 `<script type="module">`이 일반(클래식) 스크립트와 로딩·실행 순서에서 무엇이 다른지 근거를 들어 설명하고, `<script type="importmap">`으로 짧은 이름을 실제 파일 경로에 연결하며, 번들러(bundler) 없이 모듈만으로 프로젝트를 조직할 때 어디서 한계에 부딪히는지 판단할 수 있게 됩니다.
</Callout>

## 왜 필요한가 — 스크립트를 쪼개면 순서가 문제가 된다

HTML 문서 하나에 자바스크립트 파일을 여러 개 붙이기 시작하면 금방 두 가지 문제가 생깁니다.

1. **순서 문제** — `b.js`가 `a.js`의 함수를 쓰는데, `<script>` 태그 순서를 실수로 바꾸면 "정의되지 않은 함수"라는 오류가 납니다. 개발자가 파일 사이의 의존 관계를 손으로 외워서 태그 순서를 맞춰야 했습니다.
2. **전역 오염 문제** — 클래식 스크립트(classic script, 일반 스크립트)는 전부 같은 전역(global) 공간을 공유합니다. `a.js`에서 만든 변수 `설정`을 `b.js`가 실수로 덮어써도 브라우저는 아무 경고도 하지 않습니다.

이 두 문제를 표준 차원에서 해결하려고 만든 것이 자바스크립트 **모듈**(module) 시스템이고, HTML에서 이를 쓰는 방법이 `<script type="module">`입니다. 이 편은 `html/html_fundamentals` 03편에서 다룬 `<script>` 태그의 `defer`/`async` 기본 동작을 이미 안다고 전제하고, 그 위에 "모듈이라는 스크립트 유형이 추가로 무엇을 바꾸는가"만 파고듭니다. 모듈 문법(`import`/`export`, live binding 등) 자체는 `javascript/ECMAscript` 29편에서 다뤘으므로, 여기서는 **HTML 문서 안에서 모듈 스크립트가 어떻게 로드·실행되는지**에 집중합니다.

## 1. 모듈 스크립트는 항상 `defer`처럼 동작한다

### 클래식 스크립트와 나란히 비교하기

HTML 파서(parser)는 `<script>` 태그를 만나면 기본적으로 **그 자리에서 파싱을 멈추고** 스크립트를 내려받아 실행한 다음에야 파싱을 이어갑니다. `defer` 속성을 붙이면 다운로드는 파싱과 동시에 하되, 실행은 "문서 파싱이 끝난 뒤, `DOMContentLoaded` 이벤트 직전"으로 미룹니다.

`<script type="module">`은 **`defer`를 명시적으로 붙이지 않아도 항상 이 defer 동작을 따릅니다.** 즉 모듈 스크립트는 기본값 자체가 "파싱을 막지 않고, 문서 파싱이 끝난 뒤 순서대로 실행"입니다.

| 구분 | 클래식 스크립트 (`<script src="...">`) | 클래식 + `defer` | 모듈 스크립트 (`type="module"`) |
|------|--------------------------------------|-------------------|-----------------------------------|
| HTML 파싱을 막는가 | 막는다(기본값) | 안 막는다 | 안 막는다(기본값) |
| 실행 시점 | 다운로드 즉시 | 파싱이 끝난 뒤, 순서 보장 | 파싱이 끝난 뒤, 순서 보장 |
| strict mode(엄격 모드) | 기본은 아님 | 기본은 아님 | 항상 자동 적용 |
| 전역 변수 공유 | 같은 전역 공유 | 같은 전역 공유 | 파일마다 독립된 모듈 스코프(scope, 유효 범위) |
| 반복 로드 시 | 매번 재실행 | 매번 재실행 | 같은 URL이면 **한 번만** 평가(캐시) |
| `<script>` 없이 로컬 파일(`file://`)에서 실행 | 가능 | 가능 | 브라우저에 따라 CORS 오류로 **막힘**(서버 필요) |

> **쉽게 말하면:** 클래식 스크립트는 "도착하는 순서대로 바로바로 처리하는 창구"이고, 모듈 스크립트는 "모두 접수부터 받아놓고, 문서가 다 준비된 뒤 순서표대로 한 번에 처리하는 창구"입니다.

### `async`와 함께 쓰면 순서가 깨진다는 점

클래식 스크립트에 `async`를 붙이면 "다운로드가 끝나는 대로 즉시" 실행되어 여러 스크립트 사이의 순서가 보장되지 않습니다. 모듈 스크립트도 `async` 속성을 붙일 수 있는데, 이때는 defer 동작(문서 파싱 완료까지 대기)을 포기하고 "이 모듈과 그 의존 모듈의 다운로드가 끝나는 대로 즉시" 실행됩니다. 다른 모듈과의 순서가 필요 없는 독립적인 위젯 스크립트에만 쓰는 것이 안전합니다.

### 실행 순서를 코드로 확인하기

  선언안한변수 = 10;
  console.log("여기는 실행되지 않습니다");

}

// (C) 모듈 스코프는 파일마다 독립적이다 — 여기서 만든 변수는
// 다른 모듈 파일의 전역을 오염시키지 않는다

console.log(이파일만의값);

  }}
/>

콘솔에서 `this`가 `undefined`로, 선언 없는 대입이 `ReferenceError`로 잡히는 것을 확인했다면 모듈 스크립트가 일반 스크립트와 다른 실행 환경 위에서 돈다는 점을 눈으로 본 것입니다.

<Callout type="warning">
  **자주 틀리는 점:** "모듈은 그냥 `import`/`export`를 쓸 수 있는 스크립트다"라고만 알면 절반만 아는 것입니다. `import`/`export` 문법은 `javascript/ECMAscript` 29편의 주제이고, 이 편의 핵심은 **로딩·실행 시점과 스코프 격리**입니다. 실무에서 "스크립트 순서가 꼬여서 정의되지 않은 함수" 버그가 나면, `type="module"`로 바꾸는 것만으로도 defer 보장과 스코프 격리 덕분에 해결되는 경우가 많습니다.
</Callout>

## 2. `import map` — 짧은 이름으로 모듈 경로 리매핑하기

### 왜 필요한가

모듈끼리는 상대 경로(`./utils.js`, `../lib/date.js`)나 절대 경로로 `import`할 수 있습니다. 그런데 외부 라이브러리를 쓸 때는 `import { chunk } from "lodash-es"`처럼 **패키지 이름(bare specifier, 맨몸 지정자)** 으로 부르고 싶은 경우가 많습니다. 브라우저는 원래 "lodash-es"라는 이름만으로는 어디서 그 파일을 받아와야 할지 알 방법이 없습니다(Node.js는 `node_modules` 폴더를 뒤지지만, 브라우저에는 그런 폴더 탐색 규칙이 없습니다). 예전에는 이 문제를 번들러가 대신 해결해 주었습니다.

**import map**(임포트 맵, 지정자 지도)은 이 매핑을 번들러 없이 브라우저 표준만으로 선언하는 방법입니다. `<script type="importmap">` 요소 하나에 JSON으로 "이 이름이 나오면 이 URL로 바꿔서 가져와라"는 표를 적어 둡니다.

```html
<script type="importmap">
  {
    "imports": {
      "date-utils": "/vendor/date-utils.js",
      "date-utils/": "/vendor/date-utils/"
    }
  }
</script>
<script type="module">
  import { 오늘날짜 } from "date-utils";
  console.log(오늘날짜());
</script>
```

- 맨 앞 키(`"date-utils"`) 값은 정확히 그 이름으로 `import`할 때 적용됩니다.
- 끝에 슬래시가 붙은 키(`"date-utils/"`)는 "이 접두사로 시작하는 경로 전체"를 그 폴더 아래로 리매핑하는 규칙입니다. 예를 들어 `import "date-utils/format.js"`는 `/vendor/date-utils/format.js`로 풀립니다.

`<script type="importmap">`은 그 문서 안의 모듈 `import`문보다 **먼저** 나와야 하며, 문서 안에 하나만 둘 수 있습니다. 지원 상태는 2026-09 기준 **널리 사용 가능**(2023-03부터, MDN 호환성 표 기준)입니다.

### 값을 바꿔가며 관찰하기

아래는 import map 없이 상대 경로로 모듈을 연결하는 예시입니다. import map은 정적인 선언(JSON 표)이라 그 자체의 "동작"을 실습기에서 관찰할 거리는 적지만, **상대 경로 지정자와 모듈 캐싱**은 값을 바꿔보면 이해가 달라지는 지점이라 실습으로 확인합니다.

## 3. 번들러 없이 모듈만으로 조직할 때의 한계

앞서 본 import map(임포트 맵)과 모듈 스크립트만으로도 상당히 큰 프로젝트를 번들러 없이 구성할 수 있게 되었지만, 다음 지점에서는 여전히 한계가 있습니다.

| 항목 | 브라우저 네이티브 모듈만 쓸 때 | 번들러(예: Vite, esbuild)를 쓸 때 |
|------|-------------------------------|-----------------------------------|
| 요청 수 | 모듈 그래프의 파일 수만큼 요청 발생(HTTP/2 다중화로 완화되지만 0은 아님) | 결과물을 소수의 청크(chunk)로 합쳐 요청 수를 줄임 |
| 트리 셰이킹(tree shaking, 안 쓰는 코드 제거) | 없음 — 라이브러리 전체를 내려받음 | 정적 분석으로 안 쓰는 export를 제거 |
| 압축(minify) | 직접 해야 함 | 빌드 과정에 포함 |
| CommonJS 라이브러리 | `require`를 못 읽으므로 직접 사용 불가(ESM 빌드 필요) | 대부분 자동 변환 |
| 구형 브라우저 지원 | `<script nomodule>` 폴백을 손으로 준비해야 함 | 타깃에 맞춰 자동 트랜스파일 |
| 개발 중 새로고침 속도 | 파일을 그대로 서빙하므로 빠름 | 도구에 따라 다르지만 대체로 빠름(HMR) |

<Callout type="warning">
  **단정하지 않기:** "이제 import map이 있으니 번들러가 필요 없다"고 단정하지 않습니다. 소규모 프로젝트나 프로토타입, 혹은 이미 각 파일이 최적화된 CDN 배포물이라면 번들러 없이도 충분합니다. 하지만 트리 셰이킹·레거시 브라우저 대응·수백 개 파일 규모의 요청 수 관리가 필요한 프로덕션 프런트엔드는 여전히 번들러를 쓰는 것이 일반적입니다. 상황에 맞는 도구를 고르는 문제이지, 한쪽이 항상 우월한 문제가 아닙니다.
</Callout>

## 핵심 정리

- `<script type="module">`은 속성을 붙이지 않아도 `defer`처럼 동작한다. HTML 파싱을 막지 않고, 문서 파싱이 끝난 뒤 선언 순서대로 실행된다.
- 모듈 스크립트는 항상 strict mode(엄격 모드)이고, 파일마다 독립된 모듈 스코프를 가지며, 같은 URL의 모듈은 한 번만 평가되어 캐시된다.
- `<script type="importmap">`은 JSON으로 짧은 지정자(specifier)를 실제 URL에 매핑해, 번들러 없이도 패키지 이름 같은 `import` 문법을 쓸 수 있게 해준다. 반드시 첫 모듈 `import`보다 먼저 와야 하고 문서당 하나만 둘 수 있다.
- import map은 널리 사용 가능한 기능(2023-03~)이지만, 트리 셰이킹·압축·CommonJS 호환·구형 브라우저 대응까지 대체하지는 못한다. 규모가 커지면 여전히 번들러가 필요하다.
