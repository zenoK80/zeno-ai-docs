## 왜 필요한가 — HTML 태그 하나가 보안 구멍이 될 수 있다

지금까지의 편들은 대부분 "이 태그로 무엇을 더 잘 만들 수 있는가"를 다뤘습니다. 이 편은 반대로 접근합니다. **외부 콘텐츠를 끌어오는 태그**(`<iframe>`, `<a target="_blank">`, `<img>`, `<script>` 등)는 잘못 쓰면 그 자체로 공격 통로가 됩니다. 다른 사이트의 광고를 `<iframe>`으로 끼워 넣었는데 그 안의 스크립트가 내 페이지를 자기 마음대로 조작하거나, 사용자가 외부 링크를 새 탭으로 열었을 뿐인데 원래 탭이 피싱 페이지로 바뀌는 일이 실제로 일어납니다. 21편에서 `<script type="module">`이 실행 방식을 바꾸는 것을 봤다면, 이 편은 "실행 방식이 아니라 **권한** 자체를 태그 속성으로 좁히는" 이야기입니다.

이 편은 보안 헤더(HTTP 응답 헤더) 전체를 다루는 자리가 아닙니다. 서버가 보내는 헤더는 서버 설정의 영역이므로, 여기서는 **HTML 태그의 속성으로 표현하는 보안 설정**만 깊게 다룹니다.

## 1. `<iframe>`의 `sandbox` — 외부 콘텐츠의 권한을 기본 전체 차단부터 시작하기

### 왜 필요한가

`<iframe>`(인라인 프레임, 문서 안에 다른 문서를 끼워 넣는 요소)은 광고·지도·결제 위젯처럼 다른 출처(origin)의 콘텐츠를 내 페이지 안에 넣을 때 씁니다. 문제는 아무 설정 없는 `<iframe>`은 그 안의 콘텐츠에게 **일반 페이지와 똑같은 권한**을 내어준다는 점입니다. 폼 제출, 팝업 창 띄우기, 자바스크립트 실행, 최상위 페이지 이동 시도까지 전부 허용됩니다.

**`sandbox`** 속성은 이 권한을 **기본값 전체 차단**으로 뒤집습니다. `sandbox` 속성만 붙이고 아무 값도 주지 않으면 스크립트 실행, 폼 제출, 팝업, 최상위 탐색까지 모두 막힙니다. 그리고 필요한 권한만 토큰(token, 허용 항목 이름)으로 하나씩 다시 열어 줍니다.

```html
<!-- 스크립트 실행과 같은 출처 취급만 허용, 나머지는 전부 차단 -->
<iframe src="https://widget.example.com" sandbox="allow-scripts allow-same-origin"></iframe>
```

| 토큰 | 다시 허용하는 것 |
|------|-------------------|
| `allow-scripts` | 자바스크립트 실행 |
| `allow-same-origin` | 자신을 자신의 출처인 것처럼 취급(쿠키·저장소 접근 등) |
| `allow-forms` | 폼 제출 |
| `allow-popups` | `window.open` 같은 팝업 창 띄우기 |
| `allow-top-navigation` | 최상위 페이지(`iframe`을 포함한 부모 탭) 자체를 다른 주소로 이동시키기 |
| `allow-modals` | `alert`/`confirm` 같은 모달 대화상자 띄우기 |

> **쉽게 말하면:** `sandbox`가 없는 `<iframe>`은 손님에게 내 집 열쇠 전체를 맡기는 것이고, `sandbox`를 붙이는 것은 "일단 문을 다 잠그고, 손님이 꼭 필요하다는 방만 하나씩 열어 주는" 것입니다.

<Callout type="warning">
  **자주 틀리는 점:** `allow-scripts`와 `allow-same-origin`을 **동시에** 주면, 이론적으로는 그 iframe 안의 스크립트가 자신의 sandbox 제약을 스스로 해제할 수 있는 경로가 생길 수 있다고 알려져 있습니다(같은 출처 콘텐츠일 때). 신뢰하지 않는 외부 콘텐츠라면 이 두 토큰을 함께 주는 조합을 특히 신중하게 검토해야 합니다.
</Callout>

## 2. `rel="noopener"`/`"noreferrer"` — `window.opener`를 노린 공격 막기

### 문제 상황

`<a href="https://외부사이트" target="_blank">`로 링크를 새 탭에서 열면, 새로 열린 탭의 자바스크립트는 `window.opener`라는 참조로 **원래 탭의 window 객체에 접근할 수 있습니다.** 여기서 널리 알려진 공격 패턴이 나옵니다. **탭내빙**(tabnabbing, 탭 가로채기)이라 부르는 이 공격은, 새로 열린 악성 탭이 `window.opener.location`을 조작해 사용자가 원래 보고 있던(신뢰하던) 탭을 몰래 피싱 로그인 페이지로 바꿔치기하는 방식입니다. 사용자는 뒤로 돌아가서 익숙한 사이트라고 믿고 아이디·비밀번호를 입력하게 됩니다.

### `rel` 값 두 개의 차이

```html
<a href="https://partner.example.com" target="_blank" rel="noopener noreferrer">
  제휴사 페이지 새 탭에서 열기
</a>
```

| 값 | 막는 것 |
|----|---------|
| `noopener` | 새 탭의 `window.opener`를 `null`로 만들어 원래 탭에 접근하지 못하게 막는다 |
| `noreferrer` | `noopener` 효과에 더해, 이동할 때 `Referer` 헤더(어느 페이지에서 왔는지 알리는 정보)까지 보내지 않는다 |

2026-09 기준 최신 브라우저는 `target="_blank"`인 링크에 `rel="noopener"`를 명시하지 않아도 **기본적으로 `noopener`처럼 동작**하도록 바뀌었습니다. 다만 이 기본 동작은 비교적 최근에 표준화된 관행이고 오래된 브라우저·특정 렌더링 경로에서는 다를 수 있으므로, 여전히 **명시적으로 `rel="noopener"`를 붙이는 것이 안전한 관행**으로 권장됩니다.

<Callout type="warning">
  **자주 틀리는 점:** "요즘 브라우저는 알아서 막아주니까 안 써도 된다"고 단정하지 않습니다. 정적 분석 도구(린터)와 코드 리뷰 관행 상으로도 명시적으로 `rel="noopener"`를 다는 것이 표준 권장 사항이며, 서드파티 콘텐츠를 그대로 렌더링하는 CMS·마크다운 렌더러 등 브라우저 기본 동작을 신뢰하기 어려운 경로에서는 특히 중요합니다.
</Callout>

## 3. CSP를 `<meta>` 태그로 걸 때의 한계

### CSP가 하는 일

**CSP**(Content Security Policy, 콘텐츠 보안 정책)는 "이 페이지는 어떤 출처의 스크립트·이미지·스타일만 불러올 수 있다"를 선언해, 공격자가 페이지에 악성 스크립트를 주입하는 **XSS**(Cross-Site Scripting, 교차 사이트 스크립팅) 공격의 피해 범위를 줄이는 정책입니다. 원래는 HTTP 응답 헤더(`Content-Security-Policy`)로 서버가 내려주는 것이 기본 방식이지만, 서버 설정 권한이 없는 경우 HTML의 `<meta>` 태그로도 선언할 수 있습니다.

```html
<meta http-equiv="Content-Security-Policy" content="default-src 'self'; img-src https:; script-src 'self'" />
```

### `<meta>` 방식의 한계

| 항목 | HTTP 헤더 방식 | `<meta>` 태그 방식 |
|------|-----------------|----------------------|
| 적용 시점 | 응답이 도착하는 즉시, HTML 파싱 시작 전부터 | HTML 파싱이 그 `<meta>` 태그에 도달한 뒤부터 — **그 이전에 로드된 리소스는 정책 적용 전** |
| `frame-ancestors` 지시어(다른 사이트가 나를 iframe으로 감싸는 것 제한) | 지원 | **지원하지 않음** |
| `report-uri`/`report-to`(정책 위반 보고 수집) | 지원 | **지원하지 않음** |
| 서버 코드 수정 권한 필요 여부 | 필요 | 불필요(HTML만 수정) |

> **쉽게 말하면:** HTTP 헤더로 거는 CSP는 건물 정문에 세우는 보안 검색대이고, `<meta>` 태그로 거는 CSP는 로비를 지난 뒤 복도 중간에 세우는 검색대입니다. 로비(문서 맨 앞부분)를 지나는 동안 이미 들어온 것은 검사하지 못합니다.

<Callout type="warning">
  **단정하지 않기:** "`<meta>` 태그로 CSP를 걸었으니 안전하다"고 단정하지 않습니다. `<meta>` 방식은 서버 헤더를 설정할 권한이 없을 때 쓰는 **차선책**이며, `frame-ancestors`처럼 아예 지원되지 않는 지시어가 있다는 점, 문서 맨 앞부분에 최대한 일찍 배치해도 그 앞의 리소스는 보호되지 않는다는 점을 함께 알아야 합니다.
</Callout>

## 4. `crossorigin`과 `referrerpolicy` — 각각 다른 것을 통제한다

이 두 속성은 이름이 비슷해 보이지만 통제 대상이 완전히 다릅니다.

| 속성 | 통제하는 것 |
|------|--------------|
| `crossorigin` | 다른 출처의 리소스를 요청할 때 **자격 증명(credential, 쿠키 등)을 함께 보낼지**와, 응답 본문을 자바스크립트로 읽을 수 있게 **CORS 헤더를 요구할지**를 결정 |
| `referrerpolicy` | 요청을 보낼 때 **이전 페이지 주소(Referer)를 얼마나 자세히 노출할지**를 결정 |

### `crossorigin`

```html
<script src="https://cdn.example.com/lib.js" crossorigin="anonymous"></script>
```

- `anonymous`: 자격 증명 없이 요청하고, 서버가 올바른 CORS 헤더를 보내야 브라우저가 응답을 스크립트에 노출한다.
- `use-credentials`: 쿠키 등 자격 증명을 포함해 요청한다.
- 특히 `<script>`의 오류 스택 트레이스를 온전히 읽거나, `<img>`를 `<canvas>`에 그려 픽셀 데이터를 읽으려면(캔버스 오염 방지 규칙) `crossorigin`과 서버의 CORS 헤더가 함께 맞아야 합니다.

### `referrerpolicy`

```html
<a href="https://partner.example.com" referrerpolicy="no-referrer-when-downgrade">파트너 링크</a>
```

| 값(대표) | 동작 |
|----------|------|
| `no-referrer` | Referer를 아예 보내지 않는다 |
| `same-origin` | 같은 출처로 이동할 때만 Referer를 보낸다 |
| `strict-origin-when-cross-origin` | 대부분 브라우저의 현재 기본값 — 다른 출처로 갈 때는 전체 경로 대신 출처(scheme+host+port)까지만 보낸다 |

<Callout type="warning">
  **자주 틀리는 점:** `crossorigin` 속성이 있으면 CORS 오류가 자동으로 해결된다고 착각하는 경우가 많습니다. `crossorigin`은 **브라우저가 요청을 어떻게 보낼지**를 정하는 클라이언트 쪽 설정일 뿐이고, 실제로 응답을 허용할지는 **서버가 CORS 헤더로 응답해야** 합니다. 서버가 협조하지 않으면 `crossorigin` 속성을 아무리 잘 써도 요청은 차단됩니다.
</Callout>

## 핵심 정리

- `<iframe>`의 `sandbox` 속성은 기본값을 전체 차단으로 뒤집고, 필요한 권한만 `allow-scripts`·`allow-same-origin`·`allow-forms`·`allow-popups` 같은 토큰으로 다시 연다. `allow-scripts`와 `allow-same-origin`을 함께 신뢰할 수 없는 콘텐츠에 주는 조합은 특히 주의한다.
- `rel="noopener"`는 새 탭의 `window.opener`를 끊어 탭내빙(tabnabbing) 공격을 막고, `rel="noreferrer"`는 여기에 더해 Referer 정보 전달까지 막는다. 최신 브라우저의 기본 동작과 무관하게 명시적으로 붙이는 것이 안전한 관행이다.
- CSP를 `<meta>` 태그로 걸면 서버 설정 없이도 적용할 수 있지만, 그 태그에 도달하기 전 로드된 리소스는 보호받지 못하고 `frame-ancestors`·리포팅 지시어는 지원하지 않는다.
- `crossorigin`은 자격 증명 포함 여부와 CORS 응답 요구 여부를 정하는 클라이언트 쪽 설정이고, `referrerpolicy`는 이동·요청 시 Referer 노출 범위를 정한다. 둘 다 서버 쪽 협조(CORS 헤더 등)가 없으면 원하는 대로 동작하지 않을 수 있다.
