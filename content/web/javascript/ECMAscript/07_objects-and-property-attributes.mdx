## 프로퍼티는 값이 아니다

객체를 처음 배울 때는 이렇게 이해합니다 — "객체는 **키**(key)와 **값**(value)의 짝을 모아둔 것."

```js
const 사용자 = { 이름: "철수", 나이: 20 };
```

틀린 설명은 아니지만, 딥 다이브에서는 이 모델로는 설명되지 않는 현상들을 만납니다.

- `for...in`으로 순회하면 어떤 프로퍼티는 나오는데 어떤 것은 나오지 않습니다.
- `Object.freeze` 후 값을 바꾸면 에러 없이 무시됩니다.
- `사용자.이름`을 읽었을 뿐인데 함수가 실행되기도 합니다.
- 배열의 `length`는 값을 대입하면 배열이 잘립니다.

이 현상들의 공통 원인은 하나입니다.

<Callout type="info">
  **프로퍼티는 값 하나가 아니라, 값을 포함한 네 개의 어트리뷰트 묶음이다.**
</Callout>

> **쉽게 말하면:** 프로퍼티는 **책이 아니라 도서관의 대출 카드**입니다. 카드에는 책 자체(값)뿐 아니라 **대출 가능 여부, 목록 공개 여부, 폐기 가능 여부**가 함께 적혀 있습니다.

## 1. 프로퍼티 어트리뷰트와 디스크립터

### 두 종류의 프로퍼티

명세는 프로퍼티를 두 종류로 나눕니다.

- **데이터 프로퍼티**(data property): 값을 직접 들고 있습니다. 우리가 아는 보통의 프로퍼티입니다.
- **접근자 프로퍼티**(accessor property): 값을 들고 있지 않고, **읽을 때와 쓸 때 실행할 함수**를 들고 있습니다.

각각이 가진 어트리뷰트는 다릅니다.

| 어트리뷰트 | 데이터 프로퍼티 | 접근자 프로퍼티 | 뜻 |
|------------|-----------------|-----------------|-----|
| `[[Value]]` | 있음 | 없음 | 저장된 값 |
| `[[Get]]` | 없음 | 있음 | 읽을 때 호출할 함수 |
| `[[Set]]` | 없음 | 있음 | 쓸 때 호출할 함수 |
| `[[Writable]]` | 있음 | 없음 | 값 변경 허용 여부 |
| `[[Enumerable]]` | 있음 | 있음 | 열거 대상 포함 여부 |
| `[[Configurable]]` | 있음 | 있음 | 어트리뷰트 변경·삭제 허용 여부 |

이 어트리뷰트 묶음을 코드에서 볼 수 있는 형태로 만든 객체를 **프로퍼티 디스크립터**(property descriptor, 프로퍼티 설명서)라고 합니다. `Object.getOwnPropertyDescriptor`로 꺼내볼 수 있습니다.

### 세 어트리뷰트의 정확한 의미

**`writable`** – "쓰기 가능한". `false`면 값 대입이 무시됩니다. sloppy mode에서는 조용히, strict mode에서는 `TypeError`로.

**`enumerable`** – "열거 가능한". `enumerate`는 "하나씩 세어 나열하다"라는 뜻입니다. `false`면 다음 동작들이 이 프로퍼티를 **건너뜁니다**.

| 동작 | enumerable false를 건너뛰는가? |
|------|-------------------------------|
| `for...in` | 건너뜀 |
| `Object.keys` / `values` / `entries` | 건너뜀 |
| 스프레드 `{ ...객체 }` | 건너뜀 |
| `JSON.stringify` | 건너뜀 |
| `Object.getOwnPropertyNames` | 포함 |
| `in` 연산자 | 포함 |

**`configurable`** – "구성 변경 가능한". `false`면 **프로퍼티 삭제와 어트리뷰트 변경**이 막힙니다. 이것이 가장 강력한 잠금이며 **한 번 `false`로 만들면 되돌릴 수 없습니다.** 단 하나의 예외로, `configurable`이 `false`이면서 `writable`이 `true`인 데이터 프로퍼티는 `writable`을 `false`로 바꿀 수 있습니다. 잠그는 방향으로만 한 걸음 더 갈 수 있다는 뜻입니다.

### 생성 방식에 따라 기본값이 다르다

여기가 실무에서 자주 걸리는 함정입니다.

| 생성 방식 | writable | enumerable | configurable |
|-----------|----------|------------|--------------|
| 객체 리터럴·단순 대입 | `true` | `true` | `true` |
| `Object.defineProperty` – 생략 시 | `false` | `false` | `false` |

`Object.defineProperty`로 프로퍼티를 만들면서 어트리뷰트를 명시하지 않으면 **전부 `false`가 기본값**입니다. "값만 넣었는데 왜 `for...in`에 안 나오지?" 하는 혼란이 여기서 나옵니다.

(b) 실험이 특히 중요합니다. 배열의 `length`가 `for...in`에 나오지 않는 이유는 **`enumerable`이 `false`**이기 때문입니다. 빌트인 객체의 메서드들도 마찬가지로 열거 불가로 정의되어 있습니다. 그래서 `Object.prototype`에 메서드가 잔뜩 있어도 `for...in`이 그것들을 쏟아내지 않습니다.

## 2. 접근자 프로퍼티 — getter와 setter

### 왜 필요한가

이런 요구를 생각해 봅시다. "사용자 객체에 `성`과 `이름`이 따로 있는데, `전체이름`도 읽고 싶다. 그런데 `전체이름`을 따로 저장하면 `성`이 바뀔 때 동기화를 잊어버릴 수 있다."

**접근자 프로퍼티**를 쓰면 `전체이름`을 **저장하지 않고 읽을 때마다 계산**할 수 있습니다.

> **비유:** 데이터 프로퍼티가 **창고에 쌓아둔 완제품**이라면, 접근자 프로퍼티는 **주문이 들어올 때마다 만드는 주문 제작품**입니다. 재고 관리가 필요 없으니 원재료가 바뀌어도 결과가 자동으로 최신입니다.

### 문법과 동작

```js
const 사용자 = {
  성: "김",
  이름: "철수",

  get 전체이름() {           // 읽을 때 실행
    return this.성 + this.이름;
  },

  set 전체이름(값) {          // 쓸 때 실행
    this.성 = 값[0];
    this.이름 = 값.slice(1);
  }
};
```

`사용자.전체이름`은 **함수 호출처럼 보이지 않지만 함수가 실행됩니다.** 괄호를 붙이지 않는다는 점이 핵심입니다.

(a) 실험의 무한 재귀는 getter를 처음 쓸 때 거의 모두가 한 번씩 겪는 실수입니다. getter 안에서 같은 이름의 프로퍼티를 읽으면 그 getter가 다시 호출됩니다. 그래서 실제 값은 `_값`처럼 **다른 이름의 프로퍼티**에 보관해야 합니다.

<Callout type="warning">
  **자주 틀리는 점:** 밑줄 접두사(`_잔액`)는 **"내부용이니 건드리지 마세요"라는 관례일 뿐** 언어가 막아주지 않습니다. 외부에서 `계정._잔액 = -100`으로 검증을 우회할 수 있습니다. 진짜 은닉이 필요하면 클로저나 `#` private 필드를 써야 합니다.
</Callout>

## 3. 복사 — 얕은 복사가 놓치는 것들

3편에서 얕은 복사와 깊은 복사의 차이를 봤습니다. 여기서는 **어트리뷰트 관점**에서 한 겹 더 들어갑니다.

### 복사 방법별로 무엇이 보존되는가

| 방법 | 중첩 객체 | enumerable false | 심볼 키 | getter/setter | 프로토타입 |
|------|-----------|------------------|---------|---------------|------------|
| 스프레드 | 참조 공유 | 누락 | 복사됨 | **값으로 평탄화** | 잃음 |
| `Object.assign` | 참조 공유 | 누락 | 복사됨 | **값으로 평탄화** | 잃음 |
| `structuredClone` | 새로 생성 | 누락 | 오류 | 값으로 평탄화 | 잃음 |
| `defineProperties` 조합 | 참조 공유 | 보존 | 보존 | **구조 보존** | 별도 지정 |

가장 놀라운 항목은 **getter가 값으로 평탄화된다**는 것입니다. 스프레드와 `Object.assign`은 프로퍼티를 **읽어서** 복사합니다. 읽는 순간 getter가 실행되고, 그 **결과값**이 새 객체에 데이터 프로퍼티로 들어갑니다. 계산 프로퍼티였던 것이 고정된 값이 되어버립니다.

디스크립터까지 그대로 옮기려면 `Object.getOwnPropertyDescriptors`와 `Object.defineProperties`를 조합해야 합니다.

```js
const 정확한복사 = Object.defineProperties(
  Object.create(Object.getPrototypeOf(원본)),
  Object.getOwnPropertyDescriptors(원본)
);
```

### 깊은 복사 방법 비교

| 방법 | 함수 | `undefined` 값 | `Date` | 순환 참조 | Map·Set |
|------|------|----------------|--------|-----------|---------|
| `JSON.parse(JSON.stringify(x))` | 사라짐 | 사라짐 | 문자열로 변형 | 오류 | 빈 객체가 됨 |
| `structuredClone(x)` | 오류 | 보존 | 보존 | 정상 처리 | 보존 |

`JSON` 왕복 방식이 오랫동안 쓰였지만, 위 표의 손실을 감안하면 **단순한 순수 데이터에만** 안전합니다. `structuredClone`은 ES 표준이 아니라 호스트 환경 API지만 브라우저와 Node.js 모두에서 쓸 수 있고, **순환 참조까지 정상 처리**한다는 큰 장점이 있습니다.

## 4. 객체 잠그기 — 세 단계

객체를 변경하지 못하게 막는 방법이 세 단계로 준비되어 있습니다. 각 단계는 앞 단계를 포함합니다.

```mermaid
graph LR
  A["preventExtensions<br/>추가만 금지"] --> B["seal<br/>추가·삭제 금지"]
  B --> C["freeze<br/>추가·삭제·수정 금지"]
```

| 메서드 | 프로퍼티 추가 | 프로퍼티 삭제 | 값 수정 | 내부적으로 하는 일 |
|--------|---------------|---------------|---------|--------------------|
| `Object.preventExtensions` | 금지 | 허용 | 허용 | 확장 가능 플래그를 끔 |
| `Object.seal` | 금지 | 금지 | 허용 | 위 + 모든 `configurable`을 `false`로 |
| `Object.freeze` | 금지 | 금지 | 금지 | 위 + 모든 `writable`을 `false`로 |

각각에 대응하는 확인 메서드는 `Object.isExtensible`, `Object.isSealed`, `Object.isFrozen`입니다.

### 세 가지 중요한 한계

**한계 1 — 전부 얕게 동작합니다.** `Object.freeze(객체)`는 1단계 프로퍼티만 얼립니다. 중첩 객체는 그대로 변경 가능합니다. 깊게 얼리려면 재귀 순회가 필요합니다.

**한계 2 — 되돌릴 수 없습니다.** `unfreeze` 같은 메서드는 없습니다. `configurable`을 `false`로 만드는 것이 비가역이기 때문입니다.

**한계 3 — 접근자 프로퍼티는 다르게 동작합니다.** `freeze`는 `writable`을 끄는데, 접근자 프로퍼티에는 `writable`이 없습니다. 그래서 **setter는 여전히 호출됩니다.** setter가 다른 객체를 건드리면 그 변경은 그대로 일어납니다.

## 5. 프로퍼티 열거 — 어떤 메서드가 무엇을 보는가

프로퍼티를 순회하는 방법이 여러 개인데, 각각 보는 범위가 다릅니다.

| 방법 | 자기 프로퍼티 | 상속받은 프로퍼티 | enumerable false | 심볼 키 |
|------|---------------|-------------------|------------------|---------|
| `for...in` | 포함 | **포함** | 제외 | 제외 |
| `Object.keys` | 포함 | 제외 | 제외 | 제외 |
| `Object.getOwnPropertyNames` | 포함 | 제외 | 포함 | 제외 |
| `Object.getOwnPropertySymbols` | 제외 | 제외 | – | 포함 |
| `Reflect.ownKeys` | 포함 | 제외 | 포함 | 포함 |

`for...in`만 **상속받은 프로퍼티까지 순회**한다는 점이 결정적 차이입니다. 프로토타입에 뭔가를 추가하면 모든 `for...in` 루프에 그것이 섞여 들어옵니다. 그래서 객체를 순회할 때는 `Object.keys`를 쓰거나, `for...in`을 쓴다면 `Object.hasOwn(객체, 키)`로 걸러내는 것이 안전합니다. 프로토타입과 상속의 구조는 13편에서 통째로 다룹니다.

또 하나 — **열거 순서**도 명세에 정해져 있습니다. 정수처럼 보이는 키가 **오름차순으로 먼저**, 그다음 문자열 키가 **추가된 순서대로**, 마지막에 심볼 키가 옵니다. 그래서 `{ "2": "b", "1": "a", "이름": "철수" }`를 순회하면 `1`, `2`, `이름` 순서로 나옵니다. 객체를 순서 있는 자료구조로 쓰면 안 되는 이유이며, 순서가 중요하면 `Map`을 쓰라는 조언이 여기서 나옵니다 — 23편에서 다룹니다.

## 핵심 정리

- 프로퍼티는 값 하나가 아니라 **어트리뷰트 묶음**이며, `Object.getOwnPropertyDescriptor`로 그 내용을 확인할 수 있다.
- **데이터 프로퍼티**는 `value`·`writable`을, **접근자 프로퍼티**는 `get`·`set`을 가지며 둘 다 `enumerable`·`configurable`을 갖는다.
- 리터럴로 만든 프로퍼티는 세 어트리뷰트가 모두 `true`지만, `Object.defineProperty`로 만들면 **생략 시 전부 `false`**다.
- `enumerable`이 `false`면 `for...in`·`Object.keys`·스프레드·`JSON.stringify`에서 빠지지만 `in` 연산자와 `getOwnPropertyNames`로는 잡힌다.
- 스프레드와 `Object.assign`은 **getter를 값으로 평탄화**하고 어트리뷰트를 보존하지 않는다. 정확한 복사에는 `getOwnPropertyDescriptors`와 `defineProperties` 조합을 쓴다.
- 잠금은 `preventExtensions` → `seal` → `freeze` 순으로 강해지며, 모두 **얕게 동작하고 되돌릴 수 없다.** 동결된 객체라도 **setter는 여전히 호출된다.**
