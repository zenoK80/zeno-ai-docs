## 1. JavaScript의 숫자는 딱 한 종류다

대부분의 언어는 정수와 실수를 나눕니다. C에는 `int`, `long`, `float`, `double`이 따로 있고 Java도 마찬가지입니다. JavaScript는 다릅니다.

```js
console.log(typeof 42);      // "number"
console.log(typeof 3.14);    // "number"
console.log(42 === 42.0);    // true — 정수와 실수의 구분이 없다
```

**모든 숫자가 `number` 타입 하나**이고, 내부적으로는 전부 **배정밀도 64비트 부동소수점**(double-precision 64-bit floating point)으로 저장됩니다. 이 형식은 **IEEE 754**라는 국제 표준이 정한 것으로, 754는 표준 번호이고 IEEE는 전기전자기술자협회(Institute of Electrical and Electronics Engineers)의 약자입니다.

> **쉽게 말하면:** JavaScript는 숫자 서랍이 하나뿐입니다. 1이든 3.14든 같은 규격의 상자에 담기고, 그 상자의 규격이 IEEE 754입니다. 상자 크기가 정해져 있으니 **담을 수 없는 숫자가 반드시 생깁니다.** 이 문서의 함정들은 전부 여기서 나옵니다.

### 64비트의 구성

64개의 비트(bit, 0 또는 1을 담는 최소 단위)는 세 부분으로 나뉩니다.

```mermaid
graph LR
  S["부호 1비트<br/>0이면 양수<br/>1이면 음수"]
  E["지수 11비트<br/>소수점을 어디로<br/>옮길지"]
  M["가수 52비트<br/>실제 숫자의<br/>유효한 자릿값"]
  S --- E --- M
```

값은 이렇게 조립됩니다.

$$
값 = (-1)^{부호} \times 1.가수 \times 2^{지수 - 1023}
$$

- $부호$ : 0이면 양수, 1이면 음수
- $가수$ (mantissa, 맨티사) : 유효 숫자를 담는 52비트. 이진 소수의 소수점 아랫부분입니다.
- $지수$ (exponent, 익스포넌트) : 2의 몇 제곱을 곱할지. 음수 지수도 표현하려고 1023을 빼서 조정합니다.

핵심은 **가수가 52비트로 유한하다**는 점입니다. 무한히 긴 이진 소수는 52비트에서 잘려 나갑니다.

## 2. 0.1 + 0.2 는 왜 0.3이 아닌가

### 이진수로 0.1을 써 보기

10진수 0.1을 2진수로 바꿔 봅시다. 방법은 소수 부분에 2를 계속 곱해 정수 부분을 떼어내는 것입니다.

$$
0.1 \times 2 = 0.2 \rightarrow 0
$$

$$
0.2 \times 2 = 0.4 \rightarrow 0
$$

$$
0.4 \times 2 = 0.8 \rightarrow 0
$$

$$
0.8 \times 2 = 1.6 \rightarrow 1
$$

$$
0.6 \times 2 = 1.2 \rightarrow 1
$$

$$
0.2 \times 2 = 0.4 \rightarrow 0 \; (반복 시작)
$$

여기서 소수 부분이 0.2로 되돌아왔습니다. 즉 **0.1은 이진법에서 무한소수**입니다.

$$
0.1_{(10)} = 0.0001100110011001100\cdots_{(2)}
$$

`0011`이 영원히 반복됩니다. 10진법에서 $1/3 = 0.333\cdots$이 끝나지 않는 것과 정확히 같은 현상입니다. **어떤 진법이든, 분모가 그 진법의 소인수로만 이루어지지 않으면 무한소수가 됩니다.** 2진법의 소인수는 2뿐이므로 $1/10$은 딱 떨어지지 않습니다.

### 잘린 뒤에 더하면

무한한 것을 52비트에 담으려면 **잘라야** 합니다. 그래서 컴퓨터에 저장된 0.1은 정확히 0.1이 아니라 **0.1에 가장 가까운 어떤 값**입니다.

```js
console.log(0.1.toFixed(20));  // "0.10000000000000000555"
console.log(0.2.toFixed(20));  // "0.20000000000000001110"
console.log((0.1 + 0.2).toFixed(20)); // "0.30000000000000004441"
console.log(0.1 + 0.2 === 0.3);       // false
```

두 개의 살짝 어긋난 값을 더하니 오차가 합쳐져 눈에 보이는 위치까지 올라온 것입니다. **버그가 아니라 유한한 상자에 무한한 값을 담은 필연적 결과**이고, Python·Java·C 등 IEEE 754를 쓰는 모든 언어에서 똑같이 일어납니다.

### 실무에서 어떻게 피하는가

**방법 1 — 오차 허용 범위로 비교하기**

두 실수가 "충분히 가까우면" 같다고 봅니다. 기준값으로는 `Number.EPSILON`을 씁니다. **엡실론**(epsilon, $\varepsilon$)은 수학에서 "아주 작은 값"을 뜻하는 그리스 문자로, 여기서는 1과 그다음으로 큰 표현 가능한 수 사이의 간격입니다.

```js
function 거의같다(a, b) {
  return Math.abs(a - b) < Number.EPSILON;
}
console.log(거의같다(0.1 + 0.2, 0.3));  // true
```

**방법 2 — 정수로 바꿔서 계산하기** (금액에 권장)

돈은 오차가 절대 허용되지 않습니다. 원 단위를 다룰 때는 **소수점을 없애고 정수로 계산**하세요.

```js
// 나쁨: 1250원의 10퍼센트
console.log(1250 * 0.1);            // 125.00000000000001

// 좋음: 원 단위 정수로
console.log(Math.round(1250 * 10) / 100);  // 125
```

금융 시스템에서는 아예 **최소 단위를 정수로 저장**(원, 센트 단위)하는 것이 표준 관행입니다.

**방법 3 — 소수 자릿수를 고정해 표시하기**

```js
console.log((0.1 + 0.2).toFixed(2));         // "0.30" — 문자열임에 주의
console.log(Number((0.1 + 0.2).toFixed(2))); // 0.3   — 숫자로 되돌리기
```

<Callout type="warning">
  **자주 틀리는 점:** `toFixed`는 **숫자가 아니라 문자열을 반환**합니다. `a.toFixed(2) + b.toFixed(2)`는 덧셈이 아니라 문자열 연결이 됩니다. 또 `toFixed`의 반올림은 부동소수점 표현 때문에 직관과 어긋날 때가 있습니다 — `(1.005).toFixed(2)`는 `"1.01"`이 아니라 `"1.00"`입니다. 1.005가 실제로는 1.00499…로 저장돼 있기 때문입니다.
</Callout>

## 3. 안전한 정수의 범위

가수가 52비트라는 사실은 **정수에도 한계**를 만듭니다. 암묵적인 1비트를 더해 53비트의 정밀도를 갖는데, 이를 넘어서면 정수조차 정확히 표현하지 못합니다.

$$
안전한\;최대\;정수 = 2^{53} - 1 = 9007199254740991
$$

```js
console.log(Number.MAX_SAFE_INTEGER);        // 9007199254740991
console.log(Number.MAX_SAFE_INTEGER + 1);    // 9007199254740992
console.log(Number.MAX_SAFE_INTEGER + 2);    // 9007199254740992 ← 같다!
console.log(9007199254740993 === 9007199254740992); // true ← 다른 수가 같아진다

console.log(Number.isSafeInteger(2 ** 53));      // false
console.log(Number.isSafeInteger(2 ** 53 - 1));  // true
```

`+1`과 `+2`가 같은 결과를 냅니다. 이 범위를 넘어서면 **표현 가능한 정수 사이에 틈이 생겨** 홀수를 표현할 수 없게 되기 때문입니다.

이것이 실무에서 문제가 되는 대표 사례는 **서버가 보내주는 큰 ID**입니다. 트위터·디스코드 같은 서비스의 64비트 정수 ID를 JSON으로 받아 파싱하면 뒷자리가 조용히 바뀝니다. 해결책은 **ID를 문자열로 주고받거나**, ES2020에 추가된 **BigInt**를 쓰는 것입니다.

```js
const 큰수 = 9007199254740993n;   // 끝에 n을 붙이면 BigInt
console.log(큰수 + 1n);           // 9007199254740994n — 정확하다
// console.log(큰수 + 1);         // TypeError — number와 섞을 수 없다
```

## 4. Number의 도구들 — 정적 메서드가 중요한 이유

15편에서 배웠듯 `Number`는 생성자이면서 정적 메서드의 서랍이기도 합니다. 여기서 **전역 함수와 이름이 겹치는 것들**이 함정입니다.

| 전역 함수 | `Number`의 정적 메서드 | 차이 |
|-----------|----------------------|------|
| `isNaN(x)` | `Number.isNaN(x)` | 전역은 숫자로 변환 후 판정, 정적은 변환 없이 판정 |
| `isFinite(x)` | `Number.isFinite(x)` | 위와 동일한 차이 |
| `parseInt(s)` | `Number.parseInt(s)` | 기능 동일 – 정적 쪽이 소속을 명확히 |

```js
console.log(isNaN("hello"));         // true  — "hello"를 숫자로 바꾸니 NaN
console.log(Number.isNaN("hello"));  // false — "hello"는 NaN이 아니다

console.log(isFinite("100"));        // true  — "100"을 100으로 변환
console.log(Number.isFinite("100")); // false — 문자열은 숫자가 아니다
```

**규칙**: `Number.` 붙은 것을 쓰세요. 강제 변환이 끼어들지 않아 질문이 왜곡되지 않습니다.

### NaN의 기묘한 성질

`NaN`(Not a Number, 숫자가 아님)은 숫자로 표현할 수 없는 연산 결과를 나타내는 **number 타입의 값**입니다. `typeof NaN`이 `"number"`인 것이 처음엔 이상하지만, "숫자 자리에 들어앉은 잘못된 숫자"라고 생각하면 자연스럽습니다.

```js
console.log(NaN === NaN);          // false — 자기 자신과도 같지 않다!
console.log([NaN].indexOf(NaN));   // -1    — === 를 쓰므로 못 찾는다
console.log([NaN].includes(NaN));  // true  — SameValueZero를 쓰므로 찾는다
console.log(Object.is(NaN, NaN));  // true
```

`NaN !== NaN`은 IEEE 754가 정한 규칙입니다. "값을 알 수 없음"끼리는 같다고 말할 근거가 없다는 논리죠. 이 성질 때문에 값이 `NaN`인지 검사하려면 반드시 `Number.isNaN`이나 `Object.is`를 써야 합니다.

### 진법 변환

```js
console.log((255).toString(2));    // "11111111" — 2진수
console.log((255).toString(16));   // "ff"       — 16진수
console.log(parseInt("ff", 16));   // 255        — 되돌리기
console.log((0.5).toString(2));    // "0.1"
```

`toString(진법)`은 2부터 36까지의 진법을 지원합니다. 36인 이유는 숫자 10개와 알파벳 26개를 합친 수이기 때문입니다.

### 표시용 메서드

```js
const 값 = 1234.5678;
console.log(값.toFixed(2));        // "1234.57"  — 소수점 이하 자릿수 고정
console.log(값.toPrecision(6));    // "1234.57"  — 전체 유효 자릿수 고정
console.log(값.toExponential(2));  // "1.23e+3"  — 지수 표기
console.log((1234567).toLocaleString("ko-KR")); // "1,234,567" — 지역 서식
```

`toLocaleString`은 통화·퍼센트 표시까지 해 줍니다. 직접 정규표현식으로 세 자리마다 쉼표를 찍는 코드를 쓰기 전에 이것부터 떠올리세요.

## 5. Math — 인스턴스 없는 도구 서랍

`Math`는 15편에서 확인했듯 생성자가 아닙니다. 상수와 함수만 담긴 객체입니다.

### 반올림 4형제의 차이

가장 많이 쓰면서 가장 많이 틀리는 부분입니다. **음수에서 동작이 갈립니다.**

| 값 | `Math.round` | `Math.floor` | `Math.ceil` | `Math.trunc` |
|-----|-------------|-------------|------------|-------------|
| 2.7 | 3 | 2 | 3 | 2 |
| 2.5 | 3 | 2 | 3 | 2 |
| 2.3 | 2 | 2 | 3 | 2 |
| -2.3 | -2 | -3 | -2 | -2 |
| -2.5 | -2 | -3 | -2 | -2 |
| -2.7 | -3 | -3 | -2 | -2 |

읽는 법을 정리하면 이렇습니다.

- `floor`는 **바닥**(floor) — 수직선에서 항상 **왼쪽**(작은 쪽)으로.
- `ceil`은 **천장**(ceiling) — 항상 **오른쪽**(큰 쪽)으로.
- `trunc`는 **잘라내기**(truncate) — 소수점 이하를 버림. 0 방향으로.
- `round`는 반올림인데, **`.5`는 항상 큰 쪽**, 즉 양의 방향으로 갑니다.

`-2.5`가 특히 중요합니다. `Math.round(-2.5)`는 `-3`이 아니라 **`-2`**입니다. "0.5는 올림"이라는 규칙을 절댓값이 아니라 **부호 있는 값 기준**으로 적용하기 때문입니다. 음수 데이터를 반올림하는 코드에서 조용히 1씩 어긋나는 버그의 원인입니다.

<Callout type="warning">
  **자주 틀리는 점:** 소수점 아래를 버리려고 `Math.floor`를 쓰는 습관은 **음수에서 배신합니다.** `Math.floor(-1.5)`는 `-2`입니다. "소수점 이하를 잘라낸다"가 목적이면 `Math.trunc`(또는 `x | 0`, `~~x` 같은 비트 연산 관용구)를 쓰세요. 다만 비트 연산은 32비트로 변환하므로 큰 수에서 깨집니다.
</Callout>

### 그 밖의 자주 쓰는 것들

```js
console.log(Math.abs(-5));           // 5    — 절댓값
console.log(Math.max(3, 9, 1));      // 9
console.log(Math.max(...[3, 9, 1])); // 9    — 배열은 스프레드로
console.log(Math.max());             // -Infinity — 인수 없으면!
console.log(Math.pow(2, 10), 2 ** 10); // 1024 1024 — ** 연산자가 더 읽기 좋다
console.log(Math.sqrt(16));          // 4
console.log(Math.random());          // 0 이상 1 미만 난수
```

`Math.max()`가 `-Infinity`인 것은 논리적으로 옳습니다. "최댓값의 항등원"이기 때문입니다 — 어떤 값과 비교해도 그 값이 이기므로, 비교 시작점으로 안전합니다. 하지만 빈 배열을 스프레드했을 때 `-Infinity`가 나오는 것은 실무에서 버그가 되므로 길이 검사를 붙이세요.

**난수 만들기 공식**도 정확히 알아야 합니다.

$$
결과 = \lfloor 난수 \times (최댓값 - 최솟값 + 1) \rfloor + 최솟값
$$

- $난수$ : `Math.random()`의 결과, 0 이상 1 미만
- $\lfloor \; \rfloor$ : 바닥 함수(floor) 기호, 소수점 이하 버림
- $+1$ : 최댓값을 결과에 포함시키기 위한 보정

```js
function 난수(최소, 최대) {           // 최소 이상 최대 이하
  return Math.floor(Math.random() * (최대 - 최소 + 1)) + 최소;
}
```

`+1`을 빼먹으면 최댓값이 절대 나오지 않는, 발견하기 어려운 버그가 됩니다.

console.log("=== 5. 소수 자릿수 반올림 유틸 ===");
function 자리반올림(값, 자릿수) {
  const 배수 = 10 ** 자릿수;
  return Math.round((값 + Number.EPSILON) * 배수) / 배수;
}
console.log("1.005를 2자리:", 자리반올림(1.005, 2));
console.log("2.675를 2자리:", 자리반올림(2.675, 2));

console.log("=== 6. Math.max의 경계 ===");
console.log("빈 인수:", Math.max());
console.log("빈 배열 스프레드:", Math.max(...[]));
console.log("NaN이 섞이면:", Math.max(1, NaN, 3));

// [바꿔보기] 1번에서 0.1 + 0.2 대신 0.25 + 0.5를 넣어 보세요. 왜 정확할까요?
//           (힌트: 0.25와 0.5는 2의 거듭제곱의 역수입니다)
// [바꿔보기] 4번 배열에 -0.5와 0.5를 추가하면 round 결과가 어떻게 되나요?`,
  }}
/>

실험 1의 "바꿔보기"가 핵심입니다. `0.25 + 0.5`는 정확히 `0.75`입니다. 0.25는 2의 마이너스 2제곱, 0.5는 2의 마이너스 1제곱이라 **이진법에서 유한소수**이기 때문입니다. 부동소수점 오차는 "실수를 다루면 항상 생긴다"가 아니라 "**이진법으로 딱 떨어지지 않는 값에서만 생긴다**"는 것을 확인할 수 있습니다.

## 6. Date — 시간을 다루는 낡은 도구

### 내부 구조는 숫자 하나

`Date` 객체가 담고 있는 것은 **1970년 1월 1일 0시 0분 0초 UTC로부터 흐른 밀리초 수** 하나뿐입니다. 이 기준 시각을 **에포크**(epoch, 기원)라고 부르고, 그 값을 **타임스탬프**(timestamp)라고 합니다.

```js
const 지금 = new Date();
console.log(지금.getTime());   // 예: 1756500000000 (밀리초)
console.log(Date.now());       // 객체 없이 타임스탬프만 얻기
```

년·월·일·시는 저장돼 있지 않습니다. 우리가 `getFullYear()`를 부를 때마다 **밀리초 하나에서 계산해 내는 것**입니다. 그래서 타임존이 바뀌면 같은 타임스탬프가 다른 날짜로 보입니다.

> **쉽게 말하면:** `Date`는 "1970년부터 몇 초 지났는지 적힌 스톱워치"입니다. 달력이 아니라 스톱워치라서, 그것을 사람이 읽는 날짜로 바꾸는 일은 매번 계산으로 이루어집니다.

### 생성 방법과 월 인덱스 함정

```js
new Date();                        // 현재 시각
new Date(1756500000000);           // 타임스탬프로
new Date("2026-08-30");            // 문자열 파싱 (ISO 형식 권장)
new Date(2026, 7, 30);             // 년, 월, 일 ...
```

마지막 줄을 보세요. **2026년 8월 30일을 만들려면 월에 7을 넣어야 합니다.**

**월만 0부터 시작합니다.** 년은 그대로, 일은 1부터, 시·분·초도 정상인데 월만 0~11입니다. 1995년 Netscape가 C 언어의 `struct tm` 구조를 그대로 가져오면서 생긴 유산인데, 이제는 고칠 수 없습니다.

```js
console.log(new Date(2026, 7, 30).toDateString());  // 8월 30일
console.log(new Date(2026, 8, 30).toDateString());  // 9월 30일 (실수!)
```

### 문자열 파싱의 위험

```js
new Date("2026-08-30");            // UTC 자정으로 해석 (ISO 날짜만 있는 형식)
new Date("2026-08-30T00:00:00");   // 로컬 자정으로 해석
new Date("2026/08/30");            // 로컬 자정 (비표준, 엔진마다 다를 수 있음)
```

같은 날짜를 쓴 것 같은데 **해석되는 시각이 다릅니다.** 첫 번째 형식은 UTC 기준이라, 한국(UTC+9)에서 `getDate()`를 부르면 30일이 아니라 **30일 오전 9시**로 나옵니다. 시간대가 UTC보다 뒤인 지역(예: 뉴욕 UTC-5)에서는 아예 **29일**이 됩니다. "왜 특정 사용자만 날짜가 하루 밀리지?"라는 유명한 버그의 정체입니다.

<Callout type="warning">
  **자주 틀리는 점:** 날짜 문자열은 반드시 **ISO 8601 형식**(`"2026-08-30T00:00:00Z"`처럼 시각과 타임존까지 명시)으로 주고받으세요. `"08/30/2026"` 같은 지역 형식은 엔진과 로케일에 따라 월과 일이 뒤바뀌어 해석될 수 있습니다.
</Callout>

### 날짜 계산 — setDate는 넘침을 자동 처리한다

```js
const 날짜 = new Date(2026, 0, 31);   // 2026년 1월 31일
날짜.setDate(날짜.getDate() + 1);
console.log(날짜.toDateString());     // 2026년 2월 1일 — 자동으로 넘어간다
```

`setDate(32)`처럼 범위를 넘는 값을 줘도 **다음 달로 알아서 넘어갑니다.** 윤년·월말 계산을 직접 하지 않아도 되는 편리한 성질입니다.

반면 `setMonth`는 함정이 있습니다.

```js
const 말일 = new Date(2026, 0, 31);   // 1월 31일
말일.setMonth(1);                     // 2월로 바꾸기
console.log(말일.toDateString());     // 3월 3일! (2월 31일 → 넘침 처리)
```

2월에는 31일이 없으므로 넘쳐서 3월로 갑니다. 이 때문에 "한 달 뒤" 계산은 생각보다 까다롭습니다.

### 표시 메서드와 대안

```js
const d = new Date(2026, 7, 30, 14, 30);
console.log(d.toISOString());      // "2026-08-30T05:30:00.000Z" — UTC 기준
console.log(d.toLocaleDateString("ko-KR"));  // "2026. 8. 30."
console.log(d.toLocaleString("ko-KR", { dateStyle: "full", timeStyle: "short" }));
```

`toISOString`은 서버와 데이터를 주고받을 때, `toLocaleDateString`은 사용자에게 보여줄 때 씁니다. **저장은 ISO, 표시는 로케일**이 원칙입니다.

<Callout type="info">
  **`Date`의 후계자:** `Date`는 가변 객체이고, 월 인덱스가 0부터이고, 타임존 처리가 불완전한 등 설계 결함이 많습니다. 그래서 새 표준 **Temporal**(테포럴) API가 만들어지고 있습니다. `Temporal.PlainDate`, `Temporal.ZonedDateTime`처럼 목적별로 타입이 나뉘고, 모든 객체가 불변입니다. 아직 브라우저 지원이 진행 중이라 당분간은 `Date` 또는 date-fns 같은 라이브러리를 쓰지만, 앞으로의 방향은 Temporal이라는 것을 알아 두세요.
</Callout>

## 핵심 정리

- JavaScript의 모든 숫자는 **IEEE 754 배정밀도 64비트 부동소수점** 하나로 저장된다. 가수 52비트가 유한하다는 사실이 모든 함정의 근원이다.
- `0.1 + 0.2 !== 0.3`은 **0.1이 이진법에서 무한소수**여서 잘린 값이 저장되기 때문이다. 비교는 `Number.EPSILON`으로, 금액은 정수 단위로 계산한다.
- **안전한 정수의 최대는 9007199254740991**이다. 큰 ID는 문자열이나 `BigInt`로 다뤄야 조용한 값 손상을 피한다.
- `NaN`은 자기 자신과도 같지 않다. 검사는 반드시 `Number.isNaN`으로, 전역 `isNaN`은 강제 변환이 끼어들어 질문이 왜곡된다.
- `Math`의 **반올림 4형제는 음수에서 갈린다.** 잘라내기가 목적이면 `floor`가 아니라 `trunc`.
- `Date`는 **에포크로부터의 밀리초 하나**를 담는다. **월만 0부터 시작**하고, 문자열 파싱 방식에 따라 UTC와 로컬 해석이 달라 하루가 밀린다.
