## 실습 1 — 스텝 카운터

### 요구사항

- 현재 카운트를 크게 표시한다.
- +1, -1, 리셋 버튼이 있다.
- **스텝**(step, 한 번에 더할 양)을 1·5·10 중에서 고를 수 있고, +·- 버튼은 선택된 스텝만큼 움직인다.
- 카운트가 0 미만으로는 내려가지 않는다.
- 카운트가 100 이상이면 "한계 도달!" 문구를 보여주고 + 버튼을 비활성화한다.

### 단계 안내

<Steps>

### 상태 설계하기

화면을 결정하는 값이 무엇인지부터 찾습니다. 이 앱에서 바뀌는 값은 **카운트**와 **스텝** 두 가지 — useState 두 개면 충분합니다. "한계 도달 여부"는 상태로 만들지 마세요. `count >= 100`으로 **렌더 중에 계산하는 파생 값**입니다(같은 정보를 두 상태에 중복 보관하면 어긋날 위험만 생깁니다).

### 증가·감소 핸들러 작성하기

`setCount(count + step)` 형태로 작성하되, 감소는 `Math.max(0, count - step)`으로 하한을 지킵니다. setState 후 값이 바뀌는 시점이 "다음 렌더"라는 것(7편의 스냅샷)을 의식하며 작성하세요.

### 스텝 선택 UI 만들기

버튼 세 개 또는 select 하나로 스텝 상태를 바꿉니다. 선택된 스텝 버튼만 굵게 표시하는 조건부 스타일도 시도해 보세요(4편의 조건부 렌더링).

### 한계 처리하기

문구는 `count >= 100 && ...` 패턴의 조건부 렌더링으로, 버튼 비활성화는 `disabled` 어트리뷰트에 같은 조건을 넣어 처리합니다. **같은 파생 값 하나가 두 군데 화면을 결정**하는 구조를 만들어 보세요.

</Steps>

## 실습 2 — 유효성 검증이 있는 가입 폼

### 요구사항

- 이름·이메일·비밀번호 세 입력칸을 가진 **제어 컴포넌트** 폼이다.
- 검증 규칙: 이름은 2자 이상, 이메일은 `@` 포함, 비밀번호는 8자 이상.
- 규칙을 어긴 칸 아래에 빨간 안내 문구를 실시간 표시한다.
- 세 규칙을 모두 통과해야 제출 버튼이 활성화된다.
- 제출하면 입력 내용을 alert로 보여주고 폼을 비운다.

### 단계 안내

<Steps>

### 객체 상태 하나로 폼 잡기

`{ name: "", email: "", password: "" }` 객체 상태 하나로 시작합니다. onChange 핸들러 하나에서 `event.target.name`으로 어느 칸인지 구분하고, `{ ...form, [name]: value }`로 **불변 업데이트**하는 공용 핸들러를 만드세요(7편). input마다 `name` 어트리뷰트를 붙이는 것을 잊지 마세요.

### value와 onChange 연결하기

각 input의 `value`를 상태에, `onChange`를 공용 핸들러에 연결해 제어 컴포넌트를 완성합니다. 타이핑할 때마다 리렌더가 일어나며 화면과 상태가 항상 일치하는 구조입니다(6편).

### 검증을 파생 값으로 계산하기

에러 여부를 상태로 만들지 말고, 렌더 중에 계산합니다 — `const nameError = form.name.length < 2;` 식으로. 세 검증의 논리곱으로 `isValid`를 만들고 제출 버튼의 `disabled`에 씁니다. 실습 1과 같은 원리 — **상태는 최소로, 나머지는 파생**.

### 제출 처리하기

form의 `onSubmit`에서 `event.preventDefault()`로 새로고침을 막고(6편), alert 후 상태를 초기 객체로 되돌립니다.

</Steps>

## 실습 3 — 할 일 목록 CRUD와 컴포넌트 분리

### 요구사항

- 할 일을 추가·삭제하고, 체크박스로 완료를 토글할 수 있다.
- 완료된 항목은 취소선으로 표시한다.
- 남은 할 일 개수를 상단에 표시한다.
- **컴포넌트를 세 개로 분리**한다: `App`(상태 보유) / `TodoInput`(입력·추가) / `TodoItem`(항목 한 줄).
- 상태는 App에만 두고, 자식들은 props로 값과 함수를 받는다 — **상태 끌어올리기** 구조.

### 단계 안내

<Steps>

### 한 파일로 먼저 동작시키기

분리는 나중 일입니다. 먼저 App 하나에 todos 배열 상태와 추가·토글·삭제를 전부 구현합니다. 추가는 전개 구문, 삭제는 `filter`, 토글은 `map` + 조건부 전개 — 7편의 불변 업데이트 3종 세트입니다. `key`에는 배열 인덱스가 아닌 **고유 id**를 쓰세요(4편의 이유를 기억하는지 점검!).

### 파생 값 표시하기

남은 개수는 `todos.filter((t) => !t.done).length`로 렌더 중 계산합니다. 상태 추가 금지.

### TodoItem 분리하기

항목 한 줄의 JSX를 `TodoItem`으로 뽑아냅니다. 필요한 데이터(todo 객체)와 **행동**(onToggle, onDelete 함수)을 props로 내려줍니다. 자식이 부모의 상태를 직접 바꿀 수 없으므로, "바꿔달라고 부를 함수"를 내려주는 것 — 5편에서 배운 함수 props 패턴입니다.

### TodoInput 분리하기

입력창과 추가 버튼을 `TodoInput`으로 뽑습니다. 입력 중인 텍스트는 **TodoInput의 지역 상태**로 두고(다른 컴포넌트는 이 값이 필요 없으므로 끌어올릴 이유가 없음), 추가 확정 시에만 `onAdd(text)`로 부모에게 보고합니다. "상태는 그것을 필요로 하는 컴포넌트들의 **가장 가까운 공통 부모**에" — 끌어올리기의 판단 기준을 몸으로 익히는 단계입니다.

</Steps>
