## 완성할 앱과 학습 전략

이번에는 설명을 읽고 예제를 따라 치는 데서 끝나지 않습니다. 제목과 우선순위를 입력해 할 일을 추가하고, 완료 상태와 필터를 바꾸며, 새로고침 뒤에도 목록이 남는 **할 일 보드**를 만듭니다.

> **쉽게 말하면:** 하나의 작은 앱을 완성하면서 지금까지 배운 도구가 각각 어떤 문제를 맡는지 확인하는 종합 실습입니다.

완성 앱의 요구사항은 다음과 같습니다.

1. 제목과 우선순위를 입력해 할 일을 추가한다.
2. 할 일을 완료하거나 삭제할 수 있다.
3. 전체·진행 중·완료 필터를 제공한다.
4. 남은 개수와 완료 개수를 계산해 보여준다.
5. 목록을 브라우저 저장소에 보존한다.
6. 항목 추가 뒤 제목 입력란으로 포커스를 되돌린다.
7. 테마 이름을 Context로 하위 컴포넌트에 전달한다.

여기서 중요한 것은 훅을 많이 쓰는 일이 아닙니다. **문제에 맞는 도구를 최소한으로 고르는 일**입니다.

| 문제 | 선택한 도구 | 선택 이유 |
|---|---|---|
| 여러 종류의 목록 변경 | `useReducer` | 추가·완료·삭제 행동을 한곳에서 설명할 수 있다 |
| 필터 선택 | `useState` | 서로 연관된 복잡한 전이가 없는 단순 값이다 |
| 새로고침 뒤 보존 | `useEffect` | 브라우저 저장소라는 외부 시스템과 동기화한다 |
| 입력란 포커스 | `useRef` | DOM 노드를 직접 참조하되 렌더를 일으킬 필요가 없다 |
| 테마 전달 | `useContext` | 여러 단계 아래에서 같은 값을 읽는다 |

## 1. 먼저 상태를 설계한다

코드를 쓰기 전에 화면이 기억해야 할 값을 구분합니다. React에서 **상태**(state)는 시간이 지나며 바뀌고, 바뀐 결과가 화면에 반영되어야 하는 값입니다. 반대로 기존 상태에서 계산할 수 있는 값은 별도 상태로 만들지 않습니다.

```js
// 원본 상태
const todos = [
  { id: 1, title: 'React 복습', priority: 'high', done: false },
];
const filter = 'all';

// 파생 값: state로 저장하지 않고 렌더할 때 계산한다
const visibleTodos = todos.filter((todo) => {
  if (filter === 'active') return !todo.done;
  if (filter === 'done') return todo.done;
  return true;
});
const remainingCount = todos.filter((todo) => !todo.done).length;
```

파생 값(derived value)을 다시 state로 저장하면 원본과 복사본을 함께 갱신해야 합니다. 장부 두 권에 같은 거래를 적는 것과 같아서 한쪽을 빼먹기 쉽습니다. 렌더는 컴포넌트 함수 호출이므로, 값이 필요할 때 원본에서 다시 계산하는 편이 더 안전합니다.

<Callout type="warning">
  `visibleTodos`, 남은 개수, 완료 개수는 state가 아닙니다. `todos`와 `filter`만 있으면 언제든 계산할 수 있으므로 렌더 중에 파생합니다.
</Callout>

## 2. reducer로 행동의 사전을 만든다

할 일 배열에는 추가·완료 전환·삭제라는 여러 변경 규칙이 있습니다. `useReducer`의 reducer는 현재 상태와 행동(action)을 받아 다음 상태를 계산하는 순수 함수입니다.

> **쉽게 말하면:** reducer는 앱에서 허용하는 상태 변경 명령을 한 페이지에 모은 사전입니다.

```js
function todoReducer(state, action) {
  switch (action.type) {
    case 'added':
      return [...state, action.todo];
    case 'toggled':
      return state.map((todo) =>
        todo.id === action.id ? { ...todo, done: !todo.done } : todo
      );
    case 'deleted':
      return state.filter((todo) => todo.id !== action.id);
    default:
      throw new Error('알 수 없는 행동: ' + action.type);
  }
}
```

모든 분기에서 기존 배열과 객체를 직접 바꾸지 않고 새 값을 반환합니다. React는 이전 값과 다음 값의 참조를 비교해 변경을 감지하므로 **불변 업데이트**(immutable update)가 필요합니다. `push`로 원본 배열을 바꾸거나 `todo.done = true`로 원본 객체를 고치지 않습니다.

행동을 보내는 쪽은 다음 상태를 계산하지 않습니다. 무슨 일이 일어났는지만 설명합니다.

```js
dispatch({
  type: 'added',
  todo: { id: crypto.randomUUID(), title, priority, done: false },
});

dispatch({ type: 'toggled', id });
dispatch({ type: 'deleted', id });
```

이 구조 덕분에 클릭 핸들러는 짧아지고, 모든 변경 규칙은 reducer 하나에서 검토할 수 있습니다.

## 3. 저장소와 동기화한다

브라우저의 `localStorage`는 React 바깥에 있는 외부 시스템입니다. 따라서 목록을 저장하는 일은 `useEffect`가 맡습니다. 초기값은 지연 초기화 함수로 한 번만 읽습니다.

```js
function readInitialTodos() {
  try {
    const saved = localStorage.getItem('zeno-todos');
    return saved ? JSON.parse(saved) : [];
  } catch {
    return [];
  }
}

const [todos, dispatch] = useReducer(todoReducer, [], readInitialTodos);

useEffect(() => {
  localStorage.setItem('zeno-todos', JSON.stringify(todos));
}, [todos]);
```

초기값을 `readInitialTodos()`처럼 바로 호출하지 않고 함수 자체를 넘기는 이유는 렌더마다 저장소를 읽지 않게 하기 위해서입니다. `todos`가 바뀐 뒤에는 effect가 최신 배열을 직렬화(serialization, 데이터를 문자열 형태로 바꾸는 과정)하여 저장합니다.

저장 실패 가능성도 기억해야 합니다. 시크릿 모드나 저장 공간 부족 등으로 저장소 접근이 실패할 수 있으므로 실제 서비스라면 쓰기에도 `try...catch`를 적용하고 사용자에게 상태를 알려야 합니다.

## 4. ref로 포커스를 관리한다

새 항목을 추가한 뒤 다시 입력하기 쉽도록 제목 입력란에 포커스를 돌려줍니다. 포커스는 DOM 노드의 명령형 기능이며, 값이 바뀌어도 화면 내용을 다시 계산할 필요가 없습니다. 이때 `useRef`가 적합합니다.

```jsx
const titleRef = useRef(null);

function handleSubmit(event) {
  event.preventDefault();
  const trimmed = title.trim();
  if (!trimmed) {
    titleRef.current?.focus();
    return;
  }

  dispatch({
    type: 'added',
    todo: {
      id: crypto.randomUUID(),
      title: trimmed,
      priority,
      done: false,
    },
  });
  setTitle('');
  titleRef.current?.focus();
}

return <input ref={titleRef} value={title} onChange={(e) => setTitle(e.target.value)} />;
```

`ref.current`는 React가 실제 입력 DOM 노드를 연결한 뒤 채워집니다. 선택적 연결 연산자 `?.`를 사용하면 아직 노드가 연결되지 않은 순간에도 오류가 나지 않습니다.

## 5. Context는 넓게 읽는 값에만 쓴다

테마 이름처럼 여러 컴포넌트가 읽지만 자주 바뀌지 않는 값은 Context로 전달할 수 있습니다. 목록 자체까지 무조건 Context에 넣을 필요는 없습니다. 가장 가까운 공통 부모가 소유하고 props로 전달하는 편이 흐름을 읽기 쉬운 경우가 많습니다.

```jsx
const ThemeContext = createContext('light');

function App() {
  const [theme, setTheme] = useState('light');
  return (
    <ThemeContext.Provider value={theme}>
      <Toolbar onToggleTheme={() => setTheme((t) => t === 'light' ? 'dark' : 'light')} />
      <TodoBoard />
    </ThemeContext.Provider>
  );
}

function EmptyMessage() {
  const theme = useContext(ThemeContext);
  return <p data-theme={theme}>표시할 할 일이 없습니다.</p>;
}
```

Context 값이 바뀌면 그 값을 읽는 소비자(consumer)가 다시 렌더됩니다. 따라서 매 렌더마다 새 객체를 Context 값으로 만드는 습관은 피합니다. 이 과목에서는 문자열 하나로 단순하게 유지합니다.

  const theme = useContext(ThemeContext);
  if (todos.length === 0) return <p data-theme={theme}>표시할 할 일이 없습니다.</p>;
  return (
    <ul>
      {todos.map((todo) => (
        <li key={todo.id}>
          <label>
            <input
              type="checkbox"
              checked={todo.done}
              onChange={() => dispatch({ type: "toggled", id: todo.id })}
            />
            {todo.title} · {todo.priority === "high" ? "높음" : "보통"}

  useEffect(() => {

    if (filter === "active") return !todo.done;
    if (filter === "done") return todo.done;

## 7. 기능을 확장하는 순서

완성 코드를 그대로 끝내지 말고 다음 기능을 한 단계씩 추가해 보세요.

### 도전 1 — 수정 기능

`editingId`와 수정 문자열을 state로 두고, reducer에 `edited` 행동을 추가합니다. 수정 중인 항목만 입력란으로 바꾸되 key는 기존 id를 유지해야 합니다.

### 도전 2 — 전체 완료와 완료 항목 정리

`completedAll`, `clearedCompleted` 행동을 설계합니다. reducer 바깥에서 배열을 직접 바꾸지 말고, 행동만 dispatch합니다.

### 도전 3 — 저장 실패 표시

저장 effect의 `try...catch`에서 오류 state를 갱신하고, 사용자에게 저장되지 않았음을 알려줍니다. 단, 저장 오류를 다시 저장하려고 effect 의존성에 넣어 무한 루프를 만들지 않도록 주의합니다.

### 도전 4 — 로직을 커스텀 훅으로 추출

`useTodos`라는 훅에 reducer와 저장 effect를 옮기고 `{ todos, dispatch }`를 반환합니다. UI 컴포넌트는 저장소의 존재를 몰라도 동작해야 합니다.

## 자주 틀리는 점

- reducer 안에서 `push`, `splice`로 원본 배열을 바꾸지 않는다.
- 목록의 key로 배열 인덱스를 쓰지 않는다. 삭제·재정렬 시 항목의 정체성이 틀어진다.
- 파생 값을 effect와 state로 복제하지 않는다.
- ref에 저장한 값이 바뀌어도 리렌더되지 않는다는 점을 잊지 않는다.
- Context를 모든 state의 기본 저장소로 사용하지 않는다. 가까운 부모가 소유할 수 있으면 props 흐름이 더 명확하다.
- effect는 사용자 이벤트를 감시하는 장치가 아니다. 클릭으로 시작되는 일은 클릭 핸들러에서 처리한다.

## 핵심 정리

- 먼저 원본 state와 파생 값을 나누면 중복 상태와 동기화 버그를 줄일 수 있다.
- 복잡한 목록 전이는 reducer에 모으고, 이벤트 핸들러는 행동만 dispatch한다.
- effect는 `localStorage` 같은 외부 시스템과 동기화할 때 사용한다.
- ref는 DOM 포커스처럼 렌더 결과에 직접 포함되지 않는 명령형 작업에 적합하다.
- Context는 여러 단계에서 읽는 값을 전달하는 도구이며, 모든 상태를 넣는 전역 저장소가 아니다.
