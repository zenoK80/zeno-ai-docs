## 테스트가 있는데도 리팩터링이 무서운 이유

컴포넌트 내부 state 이름이나 함수 호출 횟수를 검사하는 테스트는 구현을 조금만 바꿔도 깨집니다. 반대로 버튼을 눌러도 주문이 전송되지 않는 실제 버그는 놓칠 수 있습니다. 이런 테스트는 코드의 현재 모양을 얼려둘 뿐 사용자의 계약을 보호하지 못합니다.

> **쉽게 말하면:** React Testing Library는 컴포넌트 안을 들여다보는 대신, 사용자가 화면을 찾고 조작한 뒤 무엇을 보게 되는지 검사하게 합니다.

**RTL**(React Testing Library)은 테스트 러너가 아닙니다. DOM에 React를 렌더하고 사용자 관점으로 요소를 찾는 도구입니다. Jest나 Vitest가 테스트 실행, 단언(assertion), 모킹 환경을 제공하고 RTL이 React UI와 상호작용합니다.

## 1. 테스트 하나의 기본 흐름

좋은 컴포넌트 테스트는 대개 준비·행동·확인의 세 단계입니다.

```jsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

test('이름을 입력하고 인사한다', async () => {
  // 준비
  const user = userEvent.setup();
  render(<GreetingForm />);

  // 행동
  await user.type(screen.getByRole('textbox', { name: '이름' }), '지수');
  await user.click(screen.getByRole('button', { name: '인사하기' }));

  // 확인
  expect(screen.getByRole('status')).toHaveTextContent('안녕하세요, 지수님');
});
```

사용자는 `input[name="name"]`이나 컴포넌트 state를 보지 않습니다. "이름"이라고 표시된 입력과 "인사하기" 버튼을 찾습니다. 테스트도 같은 기준을 쓰면 접근 가능한 UI와 테스트 가능한 UI가 같은 방향을 향합니다.

## 2. 쿼리 우선순위

`screen` 쿼리는 요소를 찾는 방법입니다. 가장 먼저 역할(role)과 접근 가능한 이름(accessible name)을 사용합니다.

```jsx
screen.getByRole('button', { name: '저장' });
screen.getByLabelText('이메일');
screen.getByText('주문이 완료되었습니다.');
screen.getByTestId('price-chart');
```

권장 순서는 대체로 다음과 같습니다.

1. `getByRole`: 버튼·제목·체크박스처럼 사용자와 보조 기술이 인식하는 역할
2. `getByLabelText`: label로 연결된 폼 입력
3. `getByPlaceholderText`, `getByText`, `getByDisplayValue`: 보이는 콘텐츠
4. `getByAltText`, `getByTitle`: 이미지·보조 설명
5. `getByTestId`: 의미 있는 다른 선택 방법이 없는 마지막 수단

`data-testid`가 항상 나쁜 것은 아니지만, 버튼을 test id로만 찾으면 버튼의 접근 가능한 이름이 사라져도 테스트가 통과합니다. `getByRole`은 사용 가능성과 접근성을 함께 확인합니다.

## 3. getBy, queryBy, findBy의 차이

| 계열 | 요소가 없을 때 | 기다림 | 대표 용도 |
|---|---|---|---|
| `getBy` | 즉시 예외 | 없음 | 지금 반드시 존재해야 함 |
| `queryBy` | null | 없음 | 존재하지 않음을 검사 |
| `findBy` | 제한 시간 뒤 예외 | 있음 | 비동기적으로 나타날 요소 |

```jsx
expect(screen.queryByRole('alert')).not.toBeInTheDocument();
await user.click(screen.getByRole('button', { name: '불러오기' }));
expect(await screen.findByText('불러온 상품')).toBeInTheDocument();
```

`getBy`를 try...catch로 감싸 기다리지 않습니다. 비동기 UI에는 `findBy`나 `waitFor`를 사용합니다. 반대로 즉시 존재해야 하는 제목까지 모두 `findBy`로 찾으면 불필요하게 느리고 잘못된 지연을 숨깁니다.

## 4. userEvent가 fireEvent보다 사용자에 가까운 이유

`fireEvent.change`는 단일 DOM 이벤트를 발생시킵니다. `userEvent.type`은 포커스, 키 입력, input·change 이벤트 등 실제 상호작용에 가까운 연쇄를 수행합니다.

```jsx
const user = userEvent.setup();

await user.click(screen.getByRole('checkbox', { name: '약관 동의' }));
await user.selectOptions(screen.getByRole('combobox', { name: '권한' }), 'admin');
await user.keyboard('{Tab}{Enter}');
```

대부분의 userEvent API는 비동기이므로 `await`합니다. await를 빼면 React 업데이트가 끝나기 전에 단언이 실행되어 act 경고나 간헐적 실패(flaky test)를 만들 수 있습니다.

`fireEvent`는 브라우저가 일반 사용자 조작으로 만들기 어려운 저수준 이벤트를 정밀하게 재현할 때 남겨둡니다.

## 5. 폼 행동을 테스트한다

다음 테스트는 내부 `errors.email` 객체가 만들어졌는지 검사하지 않습니다. 사용자가 잘못된 이메일을 제출했을 때 오류를 읽을 수 있고, 수정 후 성공하는지를 확인합니다.

```jsx
test('잘못된 이메일을 고친 뒤 제출한다', async () => {
  const onSubmit = jest.fn();
  const user = userEvent.setup();
  render(<SignupForm onSubmit={onSubmit} />);

  const email = screen.getByRole('textbox', { name: '이메일' });
  await user.type(email, 'wrong');
  await user.click(screen.getByRole('button', { name: '가입' }));

  expect(screen.getByRole('alert')).toHaveTextContent('이메일');
  expect(onSubmit).not.toHaveBeenCalled();

  await user.clear(email);
  await user.type(email, 'hello@example.com');
  await user.click(screen.getByRole('button', { name: '가입' }));

  expect(onSubmit).toHaveBeenCalledWith(
    expect.objectContaining({ email: 'hello@example.com' })
  );
});
```

콜백 payload는 컴포넌트 외부 계약이므로 검증할 가치가 있습니다. 그러나 RHF의 `register` 호출 횟수나 내부 state 이름은 라이브러리·구현 세부이므로 검사하지 않습니다.

## 6. 비동기 화면과 로딩·오류 상태

네트워크 요청 자체를 `global.fetch = jest.fn()`으로 매 테스트마다 조립하면 요청 형식에 과도하게 결합될 수 있습니다. 다음 09편에서는 MSW로 네트워크 경계에서 성공·오류를 재현합니다. 여기서는 비동기 UI의 관찰 원칙을 봅니다.

```jsx
test('저장 중 버튼을 잠그고 성공 뒤 안내한다', async () => {
  const user = userEvent.setup();
  render(<ProfileForm />);

  await user.type(screen.getByRole('textbox', { name: '표시 이름' }), '제노');
  await user.click(screen.getByRole('button', { name: '저장' }));

  expect(screen.getByRole('button', { name: '저장 중...' })).toBeDisabled();
  expect(await screen.findByRole('status')).toHaveTextContent('저장했습니다');
});
```

비동기 테스트에서 임의의 `setTimeout`으로 기다리지 않습니다. 사용자가 관찰할 수 있는 상태가 나타나거나 사라지는 조건을 기다립니다.

## 7. 무엇을 테스트하지 않을 것인가

모든 조합을 컴포넌트 테스트로 만들면 느리고 중복됩니다. 경계를 나눕니다.

- 순수 계산 함수: 빠른 단위 테스트
- 한 컴포넌트의 사용자 행동: RTL 컴포넌트 테스트
- 여러 화면과 실제 라우팅: 소수의 통합 또는 E2E 테스트
- React·RHF·라우터 라이브러리 자체 동작: 우리 테스트 대상이 아님
- 픽셀 위치와 색상: 시각 회귀 도구 또는 브라우저 검사 영역

테스트는 요구사항의 위험에 비례해야 합니다. 결제 제출, 권한 가드, 데이터 손실처럼 실패 비용이 큰 흐름에는 성공·오류·재시도 경로를 두껍게 검증합니다. 정적인 장식 컴포넌트에 내부 구현 테스트 수십 개를 만들 이유는 없습니다.

## 8. Provider를 포함한 렌더 헬퍼

라우터·QueryClient·테마 Provider가 필요한 컴포넌트는 테스트 전용 렌더 헬퍼로 최소 환경을 조립합니다.

```tsx
function renderApp(ui: React.ReactElement, { route = '/' } = {}) {
  const queryClient = new QueryClient({
    defaultOptions: { queries: { retry: false } },
  });

  return render(
    <MemoryRouter initialEntries={[route]}>
      <QueryClientProvider client={queryClient}>
        {ui}
      </QueryClientProvider>
    </MemoryRouter>
  );
}
```

각 테스트에 새 QueryClient를 만들어 캐시가 테스트 사이에 새지 않게 합니다. 테스트 환경에서 retry를 끄면 의도한 오류가 불필요한 재시도 시간 때문에 늦게 나타나는 일을 막을 수 있습니다.

## 자주 틀리는 점

- CSS 선택자와 컴포넌트 인스턴스로만 요소를 찾지 않는다.
- userEvent 호출의 await를 빠뜨리지 않는다.
- `queryBy`로 존재를 확인하지 않는다. 존재해야 하면 `getBy`를 사용한다.
- 비동기 결과를 고정 시간 sleep으로 기다리지 않는다.
- 하나의 테스트에서 전혀 다른 사용자 시나리오를 모두 수행하지 않는다.
- 테스트 간 공유 QueryClient·mock 상태를 남기지 않는다.

## 핵심 정리

- RTL 테스트는 구현 내부보다 사용자가 찾고 조작한 뒤 관찰하는 결과를 검증한다.
- 역할과 접근 가능한 이름을 우선 사용하면 테스트 가능성과 접근성이 함께 좋아진다.
- `getBy`는 즉시 존재, `queryBy`는 부재, `findBy`는 비동기 등장을 검사한다.
- `userEvent`는 실제 상호작용 연쇄에 가깝고 대부분 await가 필요하다.
- 단위·컴포넌트·통합·E2E 테스트의 경계를 위험과 책임에 맞게 나눈다.
