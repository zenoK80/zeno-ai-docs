## 과제 — 지원 요청 보드

고객 지원팀이 사용하는 작은 SPA를 설계합니다. 사용자는 요청 목록을 조회하고, 상태와 담당자로 필터링하고, 상세 내용을 열며, 새 요청을 등록하거나 상태를 변경할 수 있습니다.

### 필수 요구사항

1. `/tickets`에서 요청 목록과 필터를 제공한다.
2. `/tickets/:ticketId`에서 상세를 보여준다.
3. 새 요청 폼은 제목·이메일·설명·우선순위를 받는다.
4. 이메일 형식과 설명 최소 길이는 클라이언트에서 검증한다.
5. 중복 제목·권한 부족 같은 서버 오류를 사용자 행동과 연결한다.
6. 상태 변경은 빠르게 보이되 실패 시 되돌린다.
7. 목록·상세·폼의 로딩·빈 상태·오류·재시도를 제공한다.
8. 핵심 사용자 흐름을 자동 테스트한다.
9. 상세 route를 지연 로딩하고 정적 호스팅에 배포한다.

> **쉽게 말하면:** 화면부터 그리지 말고 서버 데이터의 주소, 변경 규칙, 실패 복구와 검증 가능한 사용자 계약부터 설계합니다.

## 1. 데이터와 API 계약

```ts
type Ticket = {
  id: string;
  title: string;
  requesterEmail: string;
  description: string;
  priority: 'low' | 'normal' | 'high';
  status: 'open' | 'in_progress' | 'closed';
  assigneeId: string | null;
  updatedAt: string;
  version: number;
};
```

권장 API 계약은 다음과 같습니다.

| 메서드·경로 | 목적 | 대표 실패 |
|---|---|---|
| `GET /api/tickets?status=&assignee=` | 필터된 목록 | 401, 500 |
| `GET /api/tickets/:id` | 상세 | 404, 500 |
| `POST /api/tickets` | 새 요청 | 400 필드 오류, 409 충돌 |
| `PATCH /api/tickets/:id/status` | 상태 변경 | 403, 409 버전 충돌 |

서버 오류는 `{ code, message, fieldErrors? }` 형태로 정규화합니다. `version`은 동시에 두 사용자가 수정했을 때 오래된 변경이 최신 변경을 덮는 일을 감지하는 낙관적 동시성 제어에 사용할 수 있습니다.

## 2. 서버 상태 모델

query key 팩토리를 한곳에 둡니다.

```ts
const ticketKeys = {
  all: ['tickets'] as const,
  lists: () => [...ticketKeys.all, 'list'] as const,
  list: (filters: TicketFilters) => [...ticketKeys.lists(), filters] as const,
  details: () => [...ticketKeys.all, 'detail'] as const,
  detail: (id: string) => [...ticketKeys.details(), id] as const,
};
```

필터 객체는 직렬화 가능한 값으로 정규화합니다. 빈 문자열과 undefined를 제각각 사용하면 의미상 같은 목록이 여러 캐시 주소에 저장됩니다.

상태 변경 mutation은 다음 순서를 따릅니다.

1. 관련 상세·목록 refetch를 취소한다.
2. 이전 캐시를 스냅샷으로 저장한다.
3. 상세와 현재 목록의 해당 항목을 낙관적으로 변경한다.
4. 실패하면 스냅샷으로 되돌리고 오류를 알린다.
5. 종료 시 관련 상세·목록을 invalidate한다.

충돌 가능성이 높거나 되돌리기 어려운 작업에는 낙관적 UI를 적용하지 않습니다. 이 과제에서는 상태 변경만 낙관적으로 처리하고 새 요청 등록은 서버 성공 뒤 목록을 무효화합니다.

## 3. 폼과 오류 흐름

```ts
const ticketSchema = z.object({
  title: z.string().trim().min(3, '제목을 3자 이상 입력하세요.'),
  requesterEmail: z.string().trim().email('올바른 이메일을 입력하세요.'),
  description: z.string().trim().min(20, '설명을 20자 이상 입력하세요.'),
  priority: z.enum(['low', 'normal', 'high']),
});
```

RHF는 필드 값·클라이언트 오류·포커스를 맡고 mutation은 제출 요청을 맡습니다. 400의 `fieldErrors`는 `setError`로 필드에 매핑하고, 409는 폼 상단에 제목 충돌과 수정 방법을 표시합니다. 401은 로그인 복귀 경로를 보존하고, 네트워크 오류는 입력을 유지한 채 재시도 버튼을 제공합니다.

성공 뒤 서버가 반환한 id로 상세 route에 이동합니다. 이동 전에 임의의 임시 id를 만들지 않습니다. 서버가 제목 공백 제거·시간·버전 값을 정규화할 수 있으므로 성공 응답이 최종 데이터입니다.

## 4. 화면 상태표

| 화면 | 로딩 | 빈 상태 | 오류 | 성공 |
|---|---|---|---|---|
| 목록 | 행 스켈레톤 | 필터 해제·새 요청 행동 | 다시 시도 | 목록과 갱신 시각 |
| 상세 | 본문 스켈레톤 | 404 안내와 목록 링크 | 다시 시도 | 내용과 상태 변경 |
| 등록 폼 | 제출 버튼 진행 상태 | 해당 없음 | 필드·root 오류 | 상세로 이동 |

이 표는 구현과 테스트의 공통 계약입니다. 빈 배열을 오류처럼 표시하거나, 404를 일반 500과 같은 문구로 뭉개지 않습니다.

## 5. 테스트 전략

필수 테스트는 다음 여덟 개입니다.

1. 목록 성공과 빈 상태
2. 필터 변경 시 URL과 결과 갱신
3. 상세 404 회복 링크
4. 등록 폼 클라이언트 오류와 첫 오류 포커스
5. 등록 성공 뒤 상세 이동
6. 서버 필드 오류 매핑
7. 상태 변경 낙관적 성공
8. 상태 변경 실패 롤백과 재시도 안내

MSW handler는 성공 기본값을 제공하고 각 테스트에서 필요한 실패만 일시적으로 덮습니다. 테스트마다 새 QueryClient와 MemoryRouter를 사용합니다. 단언은 `useMutation` 호출 횟수보다 사용자가 보는 상태와 실제 요청 body를 중심으로 합니다.

## 6. 코드 스플리팅과 배포

목록은 첫 진입 화면이라 기본 번들에 두고, 상세·등록 route를 `lazy`로 나눌 수 있습니다. 각 route 가까이에 Suspense와 Error Boundary를 배치해 헤더·탐색은 유지합니다.

배포 전 체크리스트입니다.

- `npm run build`가 경고 없이 완료되는가?
- 직접 `/tickets/123`에 접근해도 index 엔트리로 fallback되는가?
- API base URL은 환경별 공개 설정이고 비밀 키가 번들에 없는가?
- 404·500·오프라인·느린 응답을 미리 재현했는가?
- 번들 분석에서 실제로 큰 route가 분리됐는가?
- 키보드만으로 폼 제출·오류 이동·상태 변경이 가능한가?

## 7. 제출물과 코드 리뷰 기준

제출물에는 코드뿐 아니라 다음 기록을 포함합니다.

1. route와 화면 상태표
2. API·오류 계약
3. query key 구조와 무효화 범위
4. 낙관적 업데이트 롤백 설명
5. 폼 오류 매핑 규칙
6. 테스트 목록과 제외한 범위
7. 배포 rewrite와 환경 변수 설명

리뷰에서는 "동작한다"보다 다음 질문을 봅니다.

- 같은 서버 데이터가 두 state에 복제되지 않았는가?
- query key가 요청 입력을 모두 포함하는가?
- mutation 실패 뒤 화면이 진실로 돌아오는가?
- 사용자가 오류를 발견하고 수정·재시도할 수 있는가?
- 테스트가 구현 이름이 아니라 사용자 계약을 보호하는가?
- 클라이언트 가드를 서버 권한 검사로 착각하지 않았는가?

## 핵심 정리

- 요구사항을 route·데이터 계약·화면 상태·실패 복구로 먼저 번역한다.
- Query 캐시는 서버 상태의 단일 출처이며 필터와 id를 key에 포함한다.
- RHF·Zod는 입력과 클라이언트 검증을, 서버는 최종 무결성과 권한을 맡는다.
- 낙관적 업데이트에는 취소·스냅샷·롤백·재검증이 한 묶음으로 필요하다.
- 테스트·코드 스플리팅·배포 설정은 마지막 장식이 아니라 설계 계약의 일부다.
